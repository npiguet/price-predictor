# `effects` — ability effect model

Entry point: `python -m effects <subcommand>` (see `src/effects/__main__.py` and `infrastructure/cli.py`). A pretrained model of **what each card ability does in play**, shipping two artifacts: a per-ability embedding cache (one fixed-width vector `e` per unique ability line, computed offline) and a state-conditional effect head that predicts an ability's effect on a given game state. `effects` **imports from** `sealed` and `price_predictor` (tokenizer, `tokenizer_store`, `build_vocabulary`, `forge_jvm`, `torch_checkpoint`, `torch_training.clip_per_group`, `append_only`, `ridge_probes`, `compute_basic_lands`, `ConvertedCardLocator`, `card_embedding_layout`, `embedding_store`); never the reverse, and never `sealed.application`. The boundary is asserted by `tests/unit/effects/test_import_boundaries.py`.

The design is staged: each stage widens the corpus without invalidating what came before. **Stage one needs no Forge patch at all** — it collects through the public event bus and a bracket around stack resolution — so the first embeddings and all three evaluation gates exist before any engine patch is written.

Subcommands:

- **`extract-keyword-definitions`** — spawns Java `KeywordDefinitionMain` to write keyword → reminder-text template for every Forge keyword to `--output` (default `output/effects/keyword-definitions.json`). The encoder expands an *unknown* keyword unconditionally, so this file is what makes a set the vocabulary predates readable rather than a bare `[UNK]`.
- **`build-vocab`** — wraps `price_predictor.application.build_vocabulary`, scanning **three** sources: converted cards, converted token scripts, and the keyword-definition file (expansion substitutes reminder text in, so unscanned reminder text would expand to `[UNK]`). Seeds `[PAD]`, `[UNK]`, `cardname`, `[MASK]`, `[CLS]` at low ids so `--target-size` (default 5000) cannot truncate them away. `--surface prose` (default) writes `models/effects/vocab.txt`; `--surface script` scans the sidecars' script lines and writes `models/effects/vocab-script.txt` — **a path of its own**, so a stage-four rebuild never overwrites the vocabulary a stage-one-to-three checkpoint recorded and can still load against.
- **`train-effect-model`** — trains both transformers jointly from random init. The split holds out **ability texts**, not cards: a text at most `--holdout-max-carriers` cards carry is held out when `crc32` of its normalized script text modulo 1000 falls below `--holdout-permille`, and a card carrying one is a held-out card. Keyed on the text because the model never reads a card's name and functional reprints compile to the same script — a name-keyed holdout trains on Lightning Strike while holding out Searing Spear. Membership depends on the text's own bytes, so a Forge upgrade never reassigns an existing text, which is what lets a depleted corpus stay valid. It then **excludes from training every game holding a record that names a held-out card** — records from one game share a board, so a held-out card in the context of a training record leaks through its context role even when it is not the acting ability. That exclusion applies in every shard the run reads, not only the reserved ones, and on a corpus collected at full strength it is expensive — roughly three quarters of a shard's records belong to a tainted game. That is what **depleted collection** removes: training pools generated with `sealed generate-pools --exclude-cards` cannot contain a held-out card, so no training game is ever discarded, and a separate full-strength run supplies the card-disjoint stratum. Every shard holding a held-out card reserves itself, so nothing has to name which run a shard came from. An empty card-disjoint stratum stops the run rather than training for its full patience, validating `nan` every epoch and saving no checkpoint. Game-disjoint validation is the reserved shards' remaining games. The corpus is read **one shard at a time** (`--reserved-shards`, `--shards-per-epoch`), never whole. The per-batch mixture is the eight-class one, renormalized over the classes present (a stage-one corpus has three of eight), and fields whose record kinds are absent contribute no loss. Within a class, records weight ∝ `effective_games^(−0.5)` capped at 20× the most-observed text's weight — **games, not records**, so one long game producing hundreds of records of one ability does not make it look well-observed. Best checkpoint by card-disjoint validation loss; `--patience` early stop. `--variant {full,identity,state-only,no-state,taxonomy}` trains the four evaluation baselines on the identical pipeline, and every variant run **must** pass `--split-from` (a baseline that saw different games is not a baseline). `--withhold-keyword` holds one implemented keyword's token out of training so the zero-shot check has something to measure. `--context-cache` is the documented 8 GB fallback: a stop-gradient momentum cache refreshed every `--cache-refresh` batches.
- **`build-corpus`** — reads the raw shard corpus under `--records-dir` once and writes a fixed dataset under `--output` (default `output/effects/corpus/`): `training/`, `validation/card-disjoint/`, `validation/game-disjoint/` — each an ordinary shard directory, so every existing reader loads it unchanged — and `manifest.json`. `train-effect-model --corpus DIR` reads the dataset instead of the raw corpus, so two runs differing only in hyperparameters read the same records in the same order; it refuses `--records-dir`, `--reserved-shards`, `--split-from` and the two holdout flags, each of which names a decision the manifest already records. Training records are selected per record; both validation strata are selected per **game**, which is what keeps an intra-game join — a probe's `mirror_of` — intact, since a stratum holding one half of a matched pair scores nothing and reports the keyword as under-sampled rather than as broken. The split is the trainer's own rule under `--holdout-permille`/`--holdout-max-carriers`: a game with a record naming a held-out card goes to the card-disjoint stratum, `--game-disjoint-games` (default 1000) of the remainder go to the game-disjoint stratum, and the rest are training candidates. The training corpus holds at most `--text-cap` (default 200) records per unique ability text, the excess dropped at random under `--seed` — a ceiling and never a floor, so the tail `collect-coverage` exists to fill survives curation whole — and the card-disjoint stratum separately holds at most `--card-disjoint-text-cap` (default 50) **games** per held-out text — a held-out game is admitted only while every held-out text it carries is under the cap, and one carrying no held-out text is dropped rather than trained on — so every held-out text weighs comparably in gate 1's averages and in best-checkpoint selection. `--class-mix` sets the on-disk proportions over the eight sampling classes (default: the training mixture); a class the raw corpus cannot supply at its share is written in full with the shortfall recorded rather than silently under-filled — availability is measured against the corpus-wide cap, and the manifest records the proportions delivered beside the ones requested — and `--training-records` (default 0, no ceiling) subsamples the capped result within each class to a total. `--vocab-path` decides the encoding surface the manifest's rarity table keys its texts on — built on the other surface, the table would key every text differently while looking exactly as valid, which is why `train-effect-model --corpus` refuses a `--vocab-path` on the other one. A build that would produce a dataset gate 1 cannot be scored on writes nothing and exits non-zero: an empty holdout, refused before the survey, or an empty card-disjoint stratum, refused after it. Two passes: a parallel survey (`--workers`, default CPU count) reads every shard once keyed by provenance key rather than by ability text — resolving a key to its text needs a `SidecarCache` over tens of thousands of files, and building one per worker would cost more than the scan — then one process folds every key to its text, computes the rarity table and the per-text/per-class thresholds, and a second parallel pass re-reads each shard and writes the three outputs under them. The dataset is a pure function of the raw corpus, the flags and `--seed`, all recorded in the manifest alongside the source shard names and byte sizes, per-class and per-stratum record counts, and the unique-ability-text count of each output — the count that says whether curation preserved the tail, since no record count can. A grown raw corpus is rebuilt whole rather than extended in place, because the split and the rarity table are both corpus-wide quantities — the three output directories are cleared before the write pass, so no shard of an earlier build survives into a dataset the manifest does not describe; `--verify` reports the manifest's drift against the corpus on disk (shards added, removed, resized) and writes nothing. A checkpoint trained with `--corpus` pins the manifest's digest alongside its split (§ Model artifacts); `evaluate-effect-model` fails fast when the dataset it reads has been rebuilt since.
- **`encode-abilities`** — computes the cache once, offline; every downstream consumer reads it rather than the encoder. `--variant` resolves the **checkpoint and the output suffix together**, so a baseline is never encoded with another variant's weights and never lands on the shipping cache. The `taxonomy` variant has no encoder and emits a hash embedding of the sidecar's API type and parameter keys into the same row layout, so every `e`-geometry check reads one file shape. Idempotent; `--clean` removes only the files this variant wrote. The vocabulary and keyword-definition hashes are checked against the checkpoint before anything is written.
- **`collect-coverage`** (stage two) — sealed self-play only ever plays what sealed pools contain, so a card in no sealed-legal set never appears in a record at all. This builds decks over the **whole** converted corpus, weighted toward the cards with the fewest records, and plays rounds until every card is satisfied or retired. Each round plays `--decks-per-round` (default 500) of those decks as matches, counted from a per-run progress file under `--effect-records` — not itself a sealed corpus, and read by nothing downstream — which is what lets a round end at all rather than running until signalled. Three rules: the castability consult **only ranks** (never drops — being in a game is the precondition a stage-three intervention forks from, and a card the consult calls uncastable is exactly the one an intervention has to force into play); satisfaction counts acting hosts, event subjects and referenced refs but **not** mere snapshot presence (a card sitting on the battlefield while something else resolves teaches nothing about that card); and a card with no new qualifying record for `--no-progress-rounds` retires, which is the only thing that makes the run terminate. `--training-corpus DIR` names the corpus this run extends and the `holdout-cards.txt` it was depleted against in one flag, refusing a directory without a list rather than running undepleted, and refusing either flag it implies beside it. Point it at the **depleted** corpus: discovery recurses, so a tree also holding the full-strength corpus would count validation records toward coverage and a card whose only records are held out would read as satisfied. `--exclude-cards` names the held-out cards to keep out of every deck, reading the list `holdout-cards` writes; it needs no trained model, so this command no longer waits on a training run that is supposed to follow it. `--split-from` is the alternative for adding coverage to a corpus an existing checkpoint trained on, and passing both is refused — two spellings of one holdout is a disagreement nothing would report. It reports **two residues** — cards judged uncastable, and castable cards short of `--target-records` — each retired card under its consult verdict; both fall to stage-three interventions. The coverage unit and the deck candidates come from `output/cardsfolder/` alone: a token script is not a deckable card and could never be satisfied or retired.
- **`collect-variants`** (stage four) — reads Forge's **source** scripts (not the converted ones), perturbs one parameter, and plays the result. A whitelisted numeric parameter shifts by up to ±3 or doubles, floored at zero; a selector swaps from a checked-in whitelist. Both whitelists exist because a shifted `CounterType` or a generated selector produces a script that fails to load rather than a card that plays differently. `--variant-volume` (default 0.2) caps variant records as a fraction of the real records already present, so the cap scales with the corpus. **No variant is generated from a held-out card** — perturbing a parameter changes the text, so the variant's text is not itself held out and would reach training, teaching that card's mechanics under an edit the split cannot see. A variant exists on the script surface only and is never converted to prose. A sidecar pass (`VariantSidecarMain`) runs before the first game: a variant without one produces records nothing can join, and the join is designed to fail loudly. The corpus is counted before and after the round and the command exits non-zero when it did not grow: every deck materializing as basic lands — which is what a staged script Forge's card database never registered produces — otherwise plays its matches, writes its progress lines and reports success having collected nothing.
- **`holdout-cards`** — writes the depletion list `sealed generate-pools --exclude-cards` reads: one Forge canonical card name per line, every card carrying a held-out ability text. The one coupling between the two packages, and deliberately a plain file rather than an import — `sealed` must never depend on `effects`. It selects texts through the trainer's own rule, so the two cannot disagree; the same `--holdout-permille` and `--holdout-max-carriers` must be passed here and at training, because a depleted corpus was composed against them and a checkpoint records them.
- **`validate-corpus`** — measures the corpus invariants over a shard directory and exits non-zero on any breach: `record_id` uniqueness, one game per `game_id`, link-half pairing, whether trigger/rewrite/resolution records name an acting line and whether an empty one says why, whether every `keyword` provenance key joins the sidecar of the card it names, whether every record was collected in `patched` mode, whether `outcome` and the cost fields carry anything at all, snapshot-tier uniformity across kinds, the per-kind exact-duplicate rate, the duplicate-**event** rate inside a single record, the trigger fired:not-fired ratio per evaluated mode as well as in aggregate, and whether a fork's snapshot agrees with the record it mirrors about the turn. Every invariant reports **the number it measured** whether it passed or not, because a threshold a run barely clears is what an operator needs to see. Meant for the first few minutes of a collection pass, not for a finished corpus.

  Two rules keep the report worth reading. **Judged and watched are separate**: a check with no settled threshold prints `[WATCH]`, reports its number every pass and cannot fail a run — that is how the `zone_change` `from_zone` share, the `attributed_to` breakdown (per resolution record and, separately, per fork record), the `cause` population rate, the non-keyword provenance join and the probe count are carried, and giving one a floor (`--min-attributed-rate`, `--min-zone-change-from-zone-rate`, `--min-fork-attributed-rate`, `--min-cause-rate`) promotes it to a verdict without changing what is measured. A new number is published watched **first**; failing runs on a check nobody has calibrated is the same mistake as an invariant that fails on every good run. And **an invariant that fails on every good run is worse than no invariant**: "each `game_id` names one game" failed 168 of 177 games on a healthy smoke corpus, every one of them the mana-reservoir flush documented below, so that case is exempted precisely — a resolution half whose every event is `mana_produced`, recognised by its payload rather than by the acting card — and the measurement says how many records the exemption covered.

- **`evaluate-effect-model`** — the three gates and the reported checks. **Splits are never a flag**: the held-out card list and both `game_id` sets come from `--checkpoint`, because the corpus is append-only and a recomputed split would score the gates partly on games the model trained on. A `--variant-checkpoint NAME=PATH` recording a different split or different vocabulary hashes fails fast. `--corpus` defaults to the dataset `--checkpoint` recorded and fails the same way when its manifest digest has changed — a rebuilt dataset is a different split, so scoring the gates against it would score them partly on games the model trained on.

## Collection

Instrumentation is an opt-in on a command that already exists:

```bash
python -m sealed match-outcomes --effect-records output/effects/records/
```

`--effect-records` has **no default** there — collection is the opt-in, not the point, and a default would quietly turn every self-play run into a collection run. Absent the flag nothing changes: no shard is opened, and `match-outcomes.txt` and `cards-played.txt` keep their exact format and content. The instrumentation costs no extra simulation; it rides matches that were going to be played anyway.

Attribution mode is **detected at worker startup**, not compiled in: the patch lives in the sibling `../forge` checkout, which is rebuilt independently and re-patched by hand after every Forge upgrade, so a build-time switch would silently mislabel a corpus collected after the patch lapsed. Every record carries the detected `mode`.

`MatchWorkerMain` also has a **records-only mode**: with `-Deffect.records.dir` set and `-Doutput.file` absent, neither sealed writer is constructed at all. The coverage and variant collectors reuse this worker, and their decks are built for coverage rather than for a fair self-play sample — mixing them into the sealed corpus would corrupt the scorer's training data.

### Why the workers are short-lived, and what follows from it

Every collecting supervisor runs its Forge workers under `-Xmx1200m` and has `ForgeWorkerPool` kill the longest-running one every status interval (60 s), restarting it at once. **Neither is a tuning knob, and they are one measure rather than two.** Forge misbehaves late in a JVM's life — loops that do not terminate, allocation that grows without bound — and the pair is the containment: the small heap turns a runaway worker into an early, cheap death the pool restarts instead of one worker dragging the machine down hours into a run, and the hard recycle bounds the pathologies that do not allocate. Raising the heap or lengthening the interval hides the pathology rather than containing it. The price — a handful of GC crashes per overnight run, each costing the block of records in flight and nothing else — is paid deliberately. Do not propose removing either without saying what contains Forge instead; a corpus analysis nearly recommended undoing the heap setting before learning why it exists.

**What follows is a correctness constraint, not a throughput one.** Restarts are the normal operating condition: an eight-hour run is roughly 530 JVM lifetimes across six worker slots, many of them killed mid-game by `taskkill /F /T`, which runs no shutdown hook. So record identity, game boundaries, and any resume logic have to be correct across hundreds of restarts *and* across a JVM killed mid-game:

- Anything a worker counts from zero must be namespaced by the JVM **lifetime**, not by the worker slot. The first corpus was not: 71–75% of its `record_id` values were repeats and 804 `game_id` values covered 31,662 games, merging unrelated games under the corpus's own join key. That is why the lifetime segment is in the id and in the shard name.
- A file boundary is not a game boundary. A game can be cut in half by a kill and its remainder never written.
- A shard ends at its last complete 256-record block, so the last ≤255 records of each lifetime — about 0.5% of a run, always a game's tail — are absent. A resume that assumes a clean shutdown left a marker is wrong.
- Catch this in minutes, not hours: `python -m effects validate-corpus --effect-records <dir>` over the first few minutes of a pass. Every defect above was visible in the first minute of shards and none of them raised anything for eight hours.

### The engine hooks

The hooks live on the **`effect-record-hooks` branch of the sibling `../forge` checkout**, one commit per hook. There is no exported patch series in this repository: the branch is the history, and a directory of `.patch` files beside it was a second copy of that history maintained by hand, which git already does better.

`PatchHooks.REQUIRED` is the inventory — every class, method, and the record channel it feeds. It is the specification of what a patched Forge must have, and it is load-bearing rather than documentation: `AttributionMode` probes its first entry, `PatchedCollectors.CAN_SUPPRESS` reads the three `…Without` entries, and `PatchHooks.report()` prints what is missing at worker startup. A **partly-applied** patch is the state that matters — the mode still reads `patched`, because that is one hook's answer, while a channel the run meant to collect is quietly empty — so read that line, not just the mode.

```bash
cd ../forge && git checkout effect-record-hooks   # or: git rebase master, after an upgrade
mvn -pl forge-core,forge-game,forge-ai -am install -DskipTests
cd ../price-predictor/forge-connector && mvn package -DskipTests
```

Rebuild the fat JAR afterwards, always: the worker links against the freshly installed Forge jars. Applied, a run reaches **all eight** sampling classes; unapplied, three, and every record is stamped `degraded`.

**Where the events come from.** Forge's bus publishes an event of its own only for outcomes that have one — damage, counters, zone changes, taps. A pump, an anthem recompute, an animation and a colour change all publish the same thing, that a card's stats changed, and name only the card. `StatDiffer` remembers each card's computed characteristics and describes the difference, which is where `pt_change`, `keyword_change`, `type_change`, `color_change` and `control_change` come from; a draw, a discard and a mill are classified from the zone pair, since Forge has no event for any of the three. Without those the whole "gets +2/+2 and gains flying" family — most of what a limited deck does — resolved into an empty event list.

An event's `duration` is read from the acting script's `Duration$` and bucketed to the head's three values; `attributed_to` is the resolving sub-ability's chain index, counted **upward** from the clause via `getParent()` rather than downward from the bracket's root, because Forge resolves a copy and the two chains are not the same objects.

`python -m effects field-coverage` names every record field a corpus never varied. It exists because the failure it looks for leaves no trace: a collector that writes `"blocking":[]` produces records byte-identical to ones for a creature that genuinely is not blocking, so the shape is right, the contract tests pass, and the field is dead. Fourteen such fields were found one at a time before it was written and it found six more immediately, including the reason `pt_duration` and `type_color_duration` are the only two head fields no target path writes — an `Event`'s `duration` has a setter that nothing calls. `KNOWN_CONSTANT_FIELDS` lists the ones that are known dead; the integration test fails when one of them starts carrying data, so the list can only shrink. It is asserted in that direction only, because a field that is merely rare looks exactly like a field that is unwired.

A `continuous` record's snapshot is **the board without its own static**, which is the premise of the kind: the label is what the static does, so a snapshot carrying that static's work would hand the model the answer with the question. The board is recomputed with the static's layer entries dropped rather than stripped of the tokens it contributed, and the difference is not academic — a creature printed with trample keeps trample when the anthem granting it is removed, and subtracting the contribution would describe a board that never existed. Expect a few percent of contributions to survive their own snapshot for exactly that reason. A checkout whose patch predates the three `…Without` methods collects no continuous records at all rather than leaking ones.

A `continuous` record's `types` and `colors` are each one flat token list, because the record schema fixes a contribution's six fields: a bare token is a type or colour the static adds, `-x` one it removes, and a lone `=` marks a line the static sets outright rather than adds to. Contract in `specs/023-ability-effect-model/contracts/record-schema.md`. Two consequences worth knowing. Subtypes and supertypes are recorded and then dropped at target derivation, because `types_gained` / `types_lost` cover the core types only — the record is the archive and a head reads a subset of it. And a `=` leaves `types_lost` unset rather than naming what it displaced: the snapshot beside the record is the board *after* the static applied, so reading the entity's types back would name what it still has.

Three collectors repeat themselves, and all three are capped **by identity rather than by count**: continuous effects reapply on every recompute, the AI re-asks who may block while it evaluates a combat, and a Mountain taps a dozen times for the same R. The repeats describe a board that did not move, so one carries the observation and the rest are duplication — legality records were four fifths of the corpus before coalescing, and mana fell from 33 a game to under 5. A count cap would keep the first N and then nothing, concentrating a card's records in whichever games came first; one per game spreads them across every game the card appeared in. `--mana-cap` is keyed on the mana produced as well as the ability, so a dual land records each colour it makes.

Mana is **reservoir-sampled** (Algorithm R) rather than taken first, and the reason is the whole point of the cap: a land's first tap is turn one against an empty board, so keeping it would make every mana record describe the same early game — a bias in the one input the model conditions on. The records are therefore held until `close()`, because which activation survives is not known until the game ends; a JVM that dies loses that game's reservoir, which is bounded by `--mana-cap` per ability and cheap against a crash that already cost the rest of the game. Two consequences worth knowing: the state snapshot is taken when the mana was made rather than at flush, and the expensive part is paid a logarithmic number of times rather than once per activation.

Both samplers scramble their seed through SplitMix64's finalizer first. Games are seeded consecutively, and a linear congruential generator's first output is nearly a linear function of its seed, so without it consecutive games take nearly the same first sampling decision — a correlation across the whole run that no test of one game can see.

The seven cap flags (`--mana-cap`, `--playability-rate`, `--legality-rate`, `--interventions-per-game`, `--probes-per-game`, `--probe-keywords`, `--snapshot-tiers`) are per-worker-process quantities the Python supervisor cannot observe, so they reach the JVM as `-Deffect.*` system properties and `CollectionCaps.fromSystemProperties()` reads them back, each falling back to its default rather than failing. `sealed` restates the defaults rather than importing them — it never imports `effects` — and `tests/unit/effects/domain/test_collection_caps.py` pins the two sides together, **and pins both against the Java record's own property literals**: `effect.snapshot.tiers` and `effect.legality.rate` were read by the JVM and settable by no command, so stage three's tier-4 snapshot took a code edit to request and the legality sampler ran at a rate a javadoc called `--legality-rate`, a flag that did not exist. A property one side reads and the other never writes is invisible from both. `--snapshot-tiers` is validated Python-side because both JVM failure modes are worse: an unparseable vector falls back to the default silently, and a parseable non-prefix throws once a game is already running.

`--probe-keywords` defaults to empty and empty takes **no probe fork at all**, whatever `--probes-per-game` says, so the two flags together are a trap: the one that reads like the switch is the budget. A run launched without the keyword list collects a corpus with zero probe evidence in it, and nothing said so for eight hours. Every collecting command now prints its probe state — enabled with the keyword list, or `Damage-step probes DISABLED` naming the flag to pass — before the first worker spawns, and `validate-corpus` reports the probe count as a watched number. The default itself is deliberately unchanged: probes are the expensive mechanism, and turning them on by accident is the other failure.

Nothing here depends on the patch being applied: the connector builds against **stock** Forge, reaches every hook by name through `PatchHooks`, and falls back to bracket attribution when it finds none. The cost of the reflective approach is that a typo in a hook's name shows up at runtime as `degraded` rather than at compile time, which is why every record carries the detected mode and `tests/integration/test_effects_patched.py` asserts it. For the same reason the tests read the checkout rather than assuming it — one that pinned `degraded` would fail the day the patch landed, with nothing wrong.

### Forks (stage three)

Some abilities are never cast in any game Forge's AI plays — it judges them bad, cannot afford them, or never draws them into a board where they do anything — so no amount of observation produces a record. An **interventional resolution** forks the game and forces one, writing the effect half alone (there was no real activation, so there is no cost half to link to). A **damage-step probe** re-runs one combat with a keyword stripped; it carries `fork = true` and `interventional = false`, which distinguishes it from an intervention by flags alone, plus `mirror_of`.

Two choices in `intervene` are what make it produce anything. The ability goes **on the fork's stack directly** rather than through `ComputerUtil.handlePlayingSpellAbility`, because the cost is usually the reason the record is missing: routing through cost payment succeeds only on free plays, which is how a first attempt produced nothing but land drops. And the candidate is chosen at a **phase boundary**, not from the playability hook that knows exactly which candidates the AI declined — that hook fires inside the AI's own evaluation, and forking there copies a game mid-decision and re-enters the rules engine underneath it.

A probe forks at the **phase event**, which fires before the turn-based action that deals the damage — the only moment the copy can diverge from a board where nothing has been dealt yet. The keyword comes off through the layer system rather than the printed list, so a printed, equipped and until-end-of-turn keyword all go the way the rules would take them. The fork then runs `assignCombatDamage` and `dealAssignedDamage` itself.

The branch is **held rather than written**, because it mirrors the real combat record and that record has no id until the step the probe forked ahead of has finished; `BusBracketCollector.onCombatRecord` hands the id over when it writes one. Reconstructing the pairing from board state instead would break on two identical-looking combats in one turn.

A probe's payload names **both the keyword and the carrier** (`probed_keyword`, `probed_entity`). The keyword alone is ambiguous on a board with two tramplers, and an evaluator reproducing the perturbation model-side would strip the wrong creature — comparing against a counterfactual nobody ran. Both fields are absent on an observed combat record, which perturbs nothing.

Three rules the budgets depend on: every fork is score-checked against the live game **before** any perturbation (a copy that already disagrees is measuring the copier); a discarded fork **still counts against its budget** (otherwise a systematically failing copy retries until the game ends); and at most **two** forks may target one real resolution — a fixed constant no flag can raise. `--probe-keywords` is the runtime switch and is deliberately separate from the build decision gate 2 drives, so a checkout with the machinery takes no fork unless asked.

The real-versus-fork difference is computed at **evaluation time** and never becomes a training target: a model trained on its own disagreements would learn to reproduce its errors rather than correct them.

## The gates

| Gate | What it asks | Blocks? |
|---|---|---|
| **1** — identity baseline | Is the encoder reading text? All three margins must hold on the card-disjoint split's unique-text stratum — resolution records whose acting text appears on **no training card**, which is the only slice where a baseline holding a free vector per text cannot simply recall the answer. ≥ 0.05 absolute affected-gate F1 gain, ≥ 0.05 absolute zone-outcome accuracy gain, ≥ 5% relative Poisson-deviance reduction. Three margins because they fail differently — the gate F1 says whether the model knows *that* something happens, the zone accuracy *what*, the deviance *how much*. | **Yes** |
| **2** — damage-step keyword canary | Per keyword over the eight damage-step keywords: ≥ 200 qualifying records and ≥ 70% direction agreement under a **model-side** perturbation (remove the keyword from the ability token, or from the overlay's temporarily-granted channel where it is not printed). Under-sampled routes the same way as wrong — treating untested as passed is how a canary stops being one. | **No** — its per-keyword verdict is what decides whether stage three builds probe machinery at all |
| **3** — collapse canaries | Mean pairwise cosine ≤ 0.5 over 10,000 random pairs, top principal component ≤ 30% of variance, over one vector per unique ability text. Checked on the geometry rather than the loss, because a collapsed space passes every average-case metric. | **Yes** |

## File formats

**Effect-record shards** (`output/effects/records/{run_id}.{worker}-{lifetime}.jsonl.gz`): one JSON record per line, append-only. A shard per worker rather than one shared file because records are far larger than a match-outcome row, so concurrent appends would interleave mid-record; and a shard per worker JVM *lifetime* rather than per worker slot, because the supervisor recycles the longest-running worker every status interval and restarts crashed ones — hundreds of JVMs per run. Each file is a concatenation of complete gzip members, one per block of 256 records: every member stands alone, so a worker killed mid-write truncates the last and the reader stops there, which is the trailing-partial-line rule applied a block at a time. A game costs 4.3 MB of JSON and 80 KB gzipped, and the corpus is what fills the disk on an overnight run. Plain `*.jsonl` still reads — the corpus is append-only and older shards cannot be regenerated. Discovery **recurses**, so a depleted collection run and a full-strength one can be kept in subdirectories of `--effect-records` and still read as one corpus; anything else placed under that tree is read as corpus too. `record_id` is `{run_id}.{worker}-{lifetime}.{counter}` and `game_id` is `{run_id}.{worker}-{lifetime}.{game counter}` — both carry the worker slot because workers count independently, and the JVM lifetime because each worker JVM counts from zero and is replaced hundreds of times per run; `game_id` is the join key for a checkpoint's recorded split, so a repeated one merges unrelated games. The envelope is **frozen before stage-one collection**: later stages make new `kind` values reachable and add snapshot tiers, but never redefine a field. Four compatibility rules govern that and are enforced by `tests/unit/effects/domain/test_schema_compatibility.py` rather than by a version stamp. Full schema: `specs/023-ability-effect-model/contracts/record-schema.md`.

**Provenance sidecars** (`<name>.provenance.json`, beside each converted `.txt`): the join between runtime Forge trait objects and converted ability lines, written by `python -m price_predictor convert`. Converted-line ordinals cannot be the key — the converter runs one per-face bracket counter across five mixed line kinds, emits keyword-derived lines first though Forge appends them last, and merges and deduplicates relative to the runtime objects — so the key is printed provenance: `(script_file, face, trait_kind, index_within_kind)`, the script file including its tree. A rendered line merged from several traits carries **several** keys; a trait the converter deduplicated away maps to **no** line and is listed in `dropped_keys` (still live at runtime, so a record naming it is kept); a key in neither **fails loudly**, because that means a reconversion happened between collection and training. A key naming a script file with **no sidecar at all** is a different case and does not fail: the converted corpus never held that card, so the ability contributes no text. Token entities on the board do this — the collector files a token's provenance as `cardsfolder/<letter>/<sanitized token name>.txt` while tokens convert into `output/tokenscripts/` under Forge's own script filenames — and it reaches about 0.07% of records. `SidecarCache` raises `UnconvertedScript` and tallies it per script file, which is what a trainer logs: the share is small today, and a conversion that broke would raise it without otherwise changing the shape of a run. Row *i* of the ability cache is `lines[i]`. Full contract: `specs/023-ability-effect-model/contracts/provenance-sidecar.md`.

**Ability cache** (`output/effects/abilities/<tree>/…`): one `.npz` per source file holding a `float32` array of shape `(n_lines, e_dim)` under the key `e`, row-aligned with that source's sidecar. It lives **outside** `output/cardsfolder/` because the sealed pipeline's `encode-cards --clean` deletes every `.npz` under that tree. A variant writes `<name>.{variant}.npz` beside the shipping `<name>.npz` rather than over it.

**Keyword definitions** (`output/effects/keyword-definitions.json`): `{"<display name>": {"reminder_template", "generated_script"}}`, keyed by display name because that is what a card's keyword line and the converted text both spell. `generated_script` is captured at Forge's keyword factory — the traits it generates, rendered as script — and is null for the engine-coded minority, which generates none and keeps its template. On the script surface a keyword expands to that script; on the prose surface, to the reminder text.

**Variant scripts** (`output/effects/variant-scripts/`): perturbed Forge **source** scripts, flat, each filed under `sanitize_card_name(<variant name>).txt` — the filename **is** the path its provenance key resolves to, so it cannot be derived from the source file's own stem. Each gets a sidecar from `VariantSidecarMain`, which runs the ordinary converter with the text output suppressed: a key's `index_within_kind` is the trait's position in Forge's runtime trait list, so only the parser that builds that list can number it the way a record will. The tree is therefore the one whose sidecars sit beside a *source* script rather than a converted one, and it has **no prose surface at all** — `SidecarCache.prose_for` returns None for it, and the prose surface falls back to the script.

Loaded into a worker by staging them into Forge's custom-cards directory before `FModel.initialize` — the card database is read once at startup, and a script that appears afterwards is invisible for the life of the JVM. Staging also registers every name with `VariantRegistry`, which is what makes `ProvenanceKey` say `variant-scripts/`: once loaded, a variant is an ordinary non-token card and nothing on it says otherwise.

## One pipeline, two callers

`application/surface_batching.py` turns records into the trunk's keyword arguments, and both the trainer and gate 1's evaluator go through it. They have to agree exactly: when they did not — one keying the batch's encodings by prose, the other looking them up by script — the effect head trained on an all-zero `e`, every loss still fell, and the four evaluation baselines came out byte-identical to the shipping model. The encoding text therefore has **one** definition (`SurfaceBatcher.text_of`), and so do the variant masks, which are the whole difference between a baseline and the model gate 1 compares it against.

`infrastructure/model_runner.py` is the other half: it rebuilds encoder, model and batcher from a saved checkpoint. The `identity` baseline is the case that would break quietly — its `e` comes from a free embedding table rather than the encoder, so the table rides in the checkpoint's `extra` and a run that rebuilt it empty would score the baseline on random vectors and hand gate 1 a margin nobody earned.

## Performance invariants

Four things on the hot paths are load-bearing rather than incidental, and each has a failure mode that looks like a working run.

**`e` enters the head by row index, never by value.** A training surface's `Slot.e` is an `int` naming a row of the batch's encoded-ability matrix, and `scatter_e_rows` turns rows into vectors on the device in one gather. Reading the vectors back to the host per ability slot would both stall once per slot and **sever the gradient** — the effect head's loss reaches the ability encoder through this path and no other, so a model trained that way would optimize the head against a frozen random encoder and still report a falling loss.

**The loss decomposition is opt-in.** `per_entity_loss(..., report_parts=True)` reads each term back as a Python float, and each read synchronizes; with fifteen active fields that is fifteen stalls per batch for numbers the training loop discards. The epoch's running loss accumulates on the device and is read once when the epoch closes.

**`encode-abilities` batches by unique text.** The corpus repeats itself heavily — every *Flying*, every *deals 3 damage to any target* — so `AbilityEncoderRunner` deduplicates a card's lines before the forward pass and encodes 256 texts at a time. It loads the checkpoint once for the whole run and calls `eval()`, which matters beyond dropout: the encoder adds noise to `e` while training, and a cache built without it would differ between two runs of the same command.

**The trainer holds one shard, never the corpus.** A parsed record costs about 45 KB resident, so the corpus as it stands — 701 shards, 14M records — would need hundreds of gigabytes, and `list(read_records(...))` was an out-of-memory crash that printed nothing first because the load ran before the first log line. `load_shard` parses one shard (about a gigabyte), `_train_on_shard` takes that shard's share of the epoch's steps, and the records are released before the next shard is read.

Three things follow from never seeing the whole corpus at once, and each is a deliberate trade rather than an oversight. Rarity weighting counts the games of the resident shard, so an ability that is rare corpus-wide but appears in several of one shard's games is under-weighted while that shard is resident — except under `--corpus`, which reads the manifest's corpus-wide rarity table instead of counting the resident shard at all. That is the one place the per-shard count is actively wrong rather than merely approximate: coverage and variant shards are built dense in scarce texts on purpose, so a per-shard count reads exactly those texts as common and down-weights the records those collectors exist to supply. The split is **accumulated** instead of derived — which is sound only because a game never spans two shards, each shard having its own `game_id` namespace — so a checkpoint enumerates the games the run actually read and a run that stops early enumerates fewer. And validation records are captured once from the reserved shards and reused every epoch, because a set redrawn each epoch would make `--patience` measure which records got drawn rather than whether the model improved.

Everything else streams already (`read_records` is an iterator, `count_records` counts lines without parsing them).

## Model artifacts

Checkpoints live under `models/effects/effect-model/` (`{timestamp}.pt` plus a rolling `latest.pt`); a variant writes to `models/effects/effect-model/{variant}/`, so a baseline run can never overwrite the checkpoint the cache was built from. Beyond weights, a checkpoint records **the split it trained against** (the held-out card list and both `game_id` sets, enumerated rather than derived), the vocabulary and keyword-definition paths and their content hashes, the keyword withheld from training, and — for a `--corpus` run — the curated dataset's manifest path and digest. Every inference command re-hashes what it actually loaded and fails fast on a mismatch: encoding a cache against a different vocabulary produces vectors that look fine and mean nothing, and evaluating against a corpus rebuilt since training would score the gates partly on games the model trained on. The MLM, script-API and pairing heads are training-only and are filtered out at save time.
