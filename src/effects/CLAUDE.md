# `effects` — ability effect model

Entry point: `python -m effects <subcommand>` (see `src/effects/__main__.py` and `infrastructure/cli.py`). A pretrained model of **what each card ability does in play**, shipping two artifacts: a per-ability embedding cache (one fixed-width vector `e` per unique ability line, computed offline) and a state-conditional effect head that predicts an ability's effect on a given game state. `effects` **imports from** `sealed` and `price_predictor` (tokenizer, `tokenizer_store`, `build_vocabulary`, `forge_jvm`, `torch_checkpoint`, `torch_training.clip_per_group`, `append_only`, `ridge_probes`, `field_default`, `compute_basic_lands`, `ConvertedCardLocator`, `format_generated_deck`, `effect_collection_flags`, and `ManaCost` for the value head's cost targets); never the reverse, and never `sealed.application`. The boundary is asserted by `tests/unit/effects/test_import_boundaries.py`.

The record schema is fixed within a generation before that generation's first record is collected, so a later capability widens the corpus without invalidating what came before; a new generation may change a field's meaning, and every consumer but `rule-counts` reads gen-3 records only. Collection also runs on stock Forge, through the public event bus and a bracket around stack resolution, stamping every record `degraded`; what gen 3 collects beyond that needs the hooks of the `effect-record-hooks` branch (§ The engine hooks). The three generations are three features: 023 (`specs/023-ability-effect-model/`), 024 (§ Generation 2) and 025 (§ Generation 3).

Subcommands:

- **`extract-keyword-definitions`** — spawns Java `KeywordDefinitionMain` to write keyword → reminder-text template for every Forge keyword to `--output` (default `output/effects/keyword-definitions.json`). The encoder expands an *unknown* keyword unconditionally, so this file is what makes a set the vocabulary predates readable rather than a bare `[UNK]`.
- **`build-vocab`** — wraps `price_predictor.application.build_vocabulary`, scanning **three** sources: converted cards, converted token scripts, and the keyword-definition file (expansion substitutes reminder text in, so unscanned reminder text would expand to `[UNK]`). Seeds `[PAD]`, `[UNK]`, `cardname`, `[MASK]`, `[CLS]`, `[SEG]` at low ids so `--target-size` (default 5000) cannot truncate them away. The generated keyword scripts are not scanned: the definition both surfaces expand to is the reminder template. Set codes are not seeded either: the shared builder seeds them from `AllPrintings.json` for the price model's enriched card texts, and an ability line never names a set. `--surface prose` (default) writes `models/effects/vocab.txt`; `--surface script` scans the sidecars' script lines and writes `models/effects/vocab-script.txt` — **a path of its own**, so a script-surface rebuild never overwrites the vocabulary a prose-surface checkpoint recorded and can still load against.
- **`train-effect-model`** — trains both transformers jointly from random init. `--corpus` is required and is the trainer's only input (FR-125 withdrawn): a curated dataset built by `build-corpus` carries the split, both validation strata and the rarity table, so the trainer neither computes a holdout nor sweeps the raw corpus at startup — everything it reads comes from the manifest or from `validation/samples/`, and `--variant-scripts` defaults to the tree the manifest records, as evaluation's does. The split holds out **ability texts**, not cards, decided once by `build-corpus`: a text at most `--holdout-max-carriers` cards carry is held out when `crc32` of its normalized script text modulo 1000 falls below `--holdout-permille`, and a card carrying one is a held-out card. Keyed on the text because the model never reads a card's name and functional reprints compile to the same script — a name-keyed holdout trains on Lightning Strike while holding out Searing Spear. Membership depends on the text's own bytes, so a Forge upgrade never reassigns an existing text, which is what lets a depleted corpus stay valid. Every game holding a record that names a held-out card was already excluded from the training stratum when the dataset was built — records from one game share a board, so a held-out card in the context of a training record would otherwise leak through its context role even when it is not the acting ability — so the trainer never filters a shard it reads: it refuses one holding a game the manifest places in a validation stratum (`ValidationGameInTrainingError`, exit 1), since that shard and the manifest come from different builds. Card-disjoint and game-disjoint validation are the dataset's own `validation/samples/card-disjoint.jsonl.gz` and `validation/samples/game-disjoint.jsonl.gz`, captured once when the dataset was built and reused every epoch rather than swept from the raw corpus at startup. An empty card-disjoint stratum stops the run rather than training for its full patience, validating `nan` every epoch and saving no checkpoint. The training corpus is read **one shard at a time** (`--shards-per-epoch`), never whole, and an epoch's shards are **drawn at random across the whole training-shard list** rather than taken as a contiguous run of it — the list is in path order, so a block is one collection run's consecutive worker lifetimes and never leaves the family that sorts first. `--seed` seeds the draw along with weight init and batch planning; omitted it is drawn from the OS and logged, so runs differ by default and any one repeats by passing its seed back. Each shard's line carries its mean loss, the loss by field, each **parameter group's** pre-clip gradient norm, learning rate and step rate, read back on the shard's last step alone because each read is a device sync. The optimizer holds **two** parameter groups, `encoder` and `head` (plus `identity` for that variant), so `clip_per_group` reports — and clips — the encoder apart from the head: whether the encoder's gradient is reaching it at all through the `e` path is exactly what its own number now has to show, rather than one norm the head's larger gradient could dominate. Within the resident shard, records weight ∝ `effective_games^(−0.5)`, normalized within each sampling class and capped at 20× the weight of the text at the 99th percentile of effective games — **games, not records**, so one long game producing hundreds of records of one ability does not make it look well-observed — and that weight drives a **weighted shuffle without replacement** over the whole shard rather than a per-batch class re-draw: one shuffle cuts the shard into full `--batch-size` batches, dropping the ragged tail and beginning a fresh shuffle, instead of resampling the shard with replacement batch by batch. The eight-class sampling mixture is fixed once, on disk, by `build-corpus --class-mix`; the trainer samples what the corpus holds rather than re-mixing per batch, and fields whose record kinds are absent from the corpus contribute no loss. The sparse field group — keywords gained/lost, control change, attached-to, duration, type/color delta, counters delta — enables at the first step of `--curriculum-epoch` (default 3); validation scores the field set the epoch trained with, and the early stopper resets at that boundary. Per-epoch validation is scored in `--batch-size` batches over the shuffled sample, never one game per batch: `active_fields` keeps a field only while some class in the batch supervises it, so a whole-game batch measures a smaller objective than the training batch printed beside it, and a stratum's loss becomes a mean over as many numbers as it has games. Each epoch line also carries gate 1's three margins over the whole card-disjoint sample, read off that validation pass, so they are a progress reading rather than the evaluator's gate, which scores the unique-text stratum alone. Validation, gate 1, the breakdowns, the knowledge probes and the control score read the model through one chunked forward (`application/record_forward.py`): evaluation mode, no gradient, and bf16 autocast on CUDA for all of them, so a checkpoint is reported at the precision it was selected at. Validation, early stopping and every saved checkpoint read the **averaged weights** (`application/weight_average.py`, research T4): an exponential moving average of the encoder's, the model's and the identity table's parameters, started from the weights at warmup's end and lerped after each optimizer step at rate `--grad-accum / (--steps-per-epoch × --ema-epochs)` (`torch._foreach_lerp_`), one extra copy of the weights on the device (about 48 MB at the default sizes) that validation swaps into the modules by exchanging storage, so the trained weights come back bit for bit; an epoch ending before warmup does is validated on the current weights, is no best candidate and counts toward no patience. The run keeps one best checkpoint, encoder, trunk and heads together, from the epoch with the best **control score** on the averaged weights (FR-069; `training_schedule.ControlScoreStopper`, higher is better): `--patience` counts epochs without a new best, a new best copies `resume.pt` to `resume-best.pt`, and the curriculum switch resets the best and the patience. The control score (`application/control_score.py`) reads the selection set frozen for the corpus, found by the corpus digest under `--reports-dir` (default `output/effects/reports/`); without one `train-effect-model` exits 1 at startup (`SelectionSetError`). At startup the validator prepares every probe, grid-cell, rule-test and deviance-sample record of both strata's selection halves once (`Validator.prepare`, after the step workers start, so they prepare the first epoch meanwhile) and keeps them packed on the host (`application/host_cache.py`: each tensor in its smallest exact form — non-zero elements, non-zero rows, bits, int16/int32 — and one grid record's cells, filling chunks of their own, as their first row plus the elements where each cell differs, the relation triples kept once per run of equal rows); each epoch it runs only the forward, in chunks and deviance steps of 128 records, the reads of a chunk vectorized per readout, and scores each stratum's four components, each item rescaled and clipped below at -1, the stratum score their mean and the control score the two strata mixed by `--stratum-weight` (0.5, in [0, 1]). The deviance component's items are every shipped head's output terms, the ones the loss denominators divide by: each per-entity field and the gate (named by the field), each verdict field at `[ACT]`, each global field at `[GLOBAL]` and each created-objects slot column summed over the slots plus the overflow flag (named `<head>.<term>`, `selection_set.deviance_item`); a term's loss comes from the deviance steps under the run's mask (`StepLoss.head_parts` for the record heads, asked for through `FieldParts(heads=True)`), its constant loss from `loss_floor.constant_predictor_losses` over the same steps, and a term whose constant loss is at or below `--deviance-floor` is left out; a component with nothing to score raises `ControlScoreError` (exit 1), naming stratum, half and component. The epoch line prints each stratum's `probes`, `grids`, `rule_tests`, `deviance` and `score`, then `control` and `best`; a second line (`deviance by head:`) each stratum's mean explained deviance per head over the items it scored, with their count; and a third what scoring cost against the epoch's training time (research E2 targets at most a fifth). On pilot3 under a lenient freeze the cache holds about 0.2 GB for 34,000 forward records and copies and an epoch's scoring takes about 27 s. The card-disjoint validation loss stays reported, with its per-field breakdown; each field there carries its explained deviance against a constant-predictor floor — the loss the best constant prediction for that field reaches on the same sample, logged on its own line and recomputed only when the curriculum changes the active field set — because a loss in nats alone cannot say whether the head learned the field or learned how often it fires. `--variant {full,identity,state-only,no-state,taxonomy}` trains the four evaluation baselines on the identical pipeline; every variant run inherits its split from `--corpus`'s manifest, which is the only place a split comes from — the trainer has no `--split-from`, `--context-cache` or `--cache-refresh`, and context abilities are always re-encoded live. `--withhold-keyword` holds one implemented keyword's token out of training so the zero-shot check has something to measure. One tokenizer path does it, `AbilityTokenizer.encoding_tokens`: it force-expands the withheld keyword to its reminder text wherever it appears, then drops the keyword's token everywhere it is left, inside another keyword's expansion included (flying's reminder text names flying). Training, evaluation and `encode-abilities` all encode through it, the last reading the keyword from the checkpoint's provenance, so the model reads what the keyword does and never the token itself, and the cache matches. `--seed`'s value — the drawn one when the flag is absent — is recorded in the checkpoint's training settings. `--grad-accum` counts its micro-steps within the epoch, so a partial accumulation left at an epoch's end is dropped rather than shifting every later epoch's optimizer boundary. On CUDA the forward pass and loss run under bf16 autocast, the per-process CUDA memory reservation is capped, and the allocator's cache is released once per shard — the caching allocator otherwise fragments on the corpus's variable batch shapes and reserves far more than it ever allocates, which a Windows driver pages to host RAM instead of raising an out-of-memory error.
- **`build-corpus`** — reads the raw shard corpus under `--records-dir` once and writes a fixed dataset under `--output` (default `output/effects/corpus/`): `training/`, `validation/card-disjoint/`, `validation/game-disjoint/` — each an ordinary shard directory, so every existing reader loads it unchanged — and `manifest.json`. `train-effect-model --corpus DIR` reads the dataset instead of the raw corpus, so two runs differing only in hyperparameters read the same records in the same order; `--corpus` is the trainer's only input and the two holdout flags are no longer flags of its own, since the manifest already records the decision they would have named. Training records are selected per record; both validation strata are selected per **game**, the unit the split is decided in, so the card-disjoint cap admits or declines a whole game rather than trimming records inside one. No evaluator resolves a probe's `mirror_of` within a stratum. The split is the trainer's own rule under `--holdout-permille`/`--holdout-max-carriers`/`--holdout-unit`, over the card tree and the token tree alike: a token script printing a held-out text is a carrier, its script file is held out like a card, and a game holding it is held out. A game with a record naming a held-out card or token script goes to the card-disjoint stratum, a game whose `crc32(game_id) mod 10⁶ / 10⁶` falls below `--game-disjoint-share` (default 0.01; `--game-disjoint-keyword-share`, default 0.15, for a game holding a qualifying combat for a keyword in `--game-disjoint-keywords`) goes to the game-disjoint stratum, and the rest are training candidates. That draw is where placement starts, not where it ends. Placement (`domain/stratum_placement.py`, `place_games`) runs once over the whole corpus after the survey, from per-game inventories of rule-test-eligible records: the game-disjoint stratum takes only games two Forge AIs played, and the card-disjoint stratum every game naming a held-out card, random-seat games included (a random-seat game naming none trains); games of a candidate pool (draw below ten times `--game-disjoint-share`) carrying a (rule, polarity) short of its rule-test records are promoted to the game-disjoint stratum, smallest `crc32` first, and the stratum is topped up to two halves of at least 300 games; held-out games carrying a short (rule, polarity) are admitted first under the card-disjoint cap; and each validation stratum is split by game into a `selection` and a `reporting` half, balancing every (rule, polarity) count. Placement therefore depends on every game, not on the game alone: a rebuild over a grown corpus can move a game it placed before, and only the split a checkpoint records says where each game went. A record of a training game that acts through a held-out text — a token or a variant script printing it, or its template under `--holdout-unit template` — is not trained on: both passes route it away and the manifest counts it under the `dropped-held-out-text` stratum, while the rest of its game still trains. Training records are selected per class by copy counts (see Generation 2 below): within a cell a text supplies at most `min(--reuse-cap × n, --text-cap)` written records, repeats included — and the card-disjoint stratum separately holds at most `--card-disjoint-text-cap` (default 50) **games** per held-out text. A game counts toward a held-out text only through a **resolution** record acting through it, the only kind gate 1 scores; a held-out game is admitted only while every held-out text it resolves is under the cap, and one resolving no held-out text is dropped rather than trained on — so every held-out text weighs comparably in gate 1's averages and in best-checkpoint selection. `--class-mix` sets the on-disk proportions over the eight sampling classes (default: the training mixture); a class the raw corpus cannot supply at its share is written in full with the shortfall recorded rather than silently under-filled — availability counts the records of training games only, under the per-text cap, and the manifest records each class's target (`class_targets`) and the proportions delivered beside the ones requested, the run warning on a class delivered short of its target — and `--training-records` (default 0, no ceiling) subsamples the capped result within each class to a total. `--variant-scripts` names the perturbed-script tree: a variant line's provenance names that tree, so without the root it resolves to no ability text, and a resolution record acting through it is refused as `no-acting-text`. `--vocab-path` decides the encoding surface the manifest's rarity table keys its texts on — built on the other surface, the table would key every text differently while looking exactly as valid, which is why `train-effect-model --corpus` refuses a `--vocab-path` on the other one. A build that would produce a dataset gate 1 cannot be scored on writes nothing and exits non-zero: an empty holdout, refused before the survey, or an empty card-disjoint stratum, refused after it. Two passes: a parallel survey (`--workers`, default CPU count) reads every shard once keyed by provenance key rather than by ability text — resolving a key to its text needs a `SidecarCache` over tens of thousands of files, and building one per worker would cost more than the scan — then one process folds every key to its text, computes the rarity table and the per-text/per-class thresholds, and a second parallel pass re-reads each shard and writes the three outputs under them. The survey tags every record with the catalogue's detectors (`tag_record`, as `rule-counts` does) and splits each game at the end of its shard (a raw shard is one JVM lifetime, which no game outlives) by what placement can still do with it: a game outside the candidate pool, or a random-seat game naming no held-out card, trains whatever placement decides and folds into the training supply there; a candidate game — a Forge-AI game of the pool, or any game naming a held-out card, random seat or not — keeps its records and its rule inventory until placement, after which a candidate it trained folds in. The write pass applies the game sets placement built rather than deciding again. Only training games' records size the class, family and text quotas and the copy plans, so the plan never counts a record the write pass routes away; the rarity table, the legality mode counts, the rule counts, the condition counts, the closed subtype and keyword lists (`closed_lists.subtypes_named`/`keywords_named`: what effects grant, remove or give a created object) and the held-out texts' game counts stay whole-corpus. **Gen-3 curation** (FR-054–FR-060a): a records set holding any shard but gen-3 exits 1 before a record is read; `rules/scenarios/` and `rules/heads/` are read once (`RuleCatalogue`, a `rules_dir` config field with no flag), and the manifest's `rule_map` snapshots every tagged or drawn rule's verdict and outputs with the map's digest, beside `effective_outputs`: of each rule's map outputs, those at least one of its tagged records carries (`domain/rule_output_carriage.py`: a per-entity output supervised at an outcome entity of the tag, the gate on a record that trains it, a verdict, global or created-objects output the record supervises; the survey counts them per rule and output), which is all the rule mask and the rule tests read. After gen-2's natural share (`plan_selection`), `domain/rule_budgets.py` adds copies per class to the rules the map marks `trained` — the training stratum's over its natural shares, each validation stratum's over its own natural copies (FR-068a). A validation stratum is written in the training stratum's `--class-mix` (FR-059a, `corpus_curation.validation_multipliers`): no record is dropped, the class most over its share is written once a record, each other class repeats toward its share at most `--reuse-cap` times a record (`natural_copies` draws the fractional part from the record hash), and a class the mix omits is written once — and the write pass writes every copy with a `curation` member (`natural_share`, `copies`, `drawn_rule`, `drawn_rules`, `condition_entities`, `outcome_entities`; an added copy carries its drawn rule and that rule's tag entities in both roles, a natural copy none). A record a rare protection quality can be copied onto (`domain/protection_copies.py`) enters the budgets a second time, under its protection hash, natural share zero, and each protection copy drawn is written as a synthetic record `<record_id>~pc<i>`. Gate one takes a card-disjoint record's natural copy alone. `turn_action` records are written to no stratum and counted by subkind (`turn_action_left_out`); a permanent spell's resolution, acting through the implicit cast spell no line carries (`record_quality.is_permanent_spell`), is kept, keyed to the permanent's card by that key; a decision whose candidate key is unjoinable is refused as `unjoinable-key`. Once the corpus and its manifest are written, the build exits 1, naming each stratum and half, when a half's rule-test component already misses its precision target (`stratum_placement.rule_test_misses`: a rule enters at a Hanley–McNeil standard error of 0.1 or less, the component needs 0.05 or less, its standard error being √(Σ SEᵢ²) / m over the m rules that enter, so a half where a few dozen frequent rules enter passes even on a pilot's few dozen games; the 300 games a half needs is the selection-set freeze's exit, not this one) — the corpus is still read after an exit 1; the thresholds of research E5 (`min_games_per_half`, `max_item_error`, `max_component_error`) are config fields with no flag, so a test can lower them. Only the rule tests are judged here: the probes, grids and explained deviance wait for the selection set's freeze. Each family row in the manifest carries its `planned` count beside `share` and `written`. The written strata are then repacked: whole games are dealt to about `ceil(records / --shard-records)` shards by a hash of `game_id` seeded by `--seed`, and each shard is shuffled under `--seed` before it is written, so a shard mixes games from across the stratum and a record's copies are spread through it; the trainer still draws whole shards. A failed build leaves no stale manifest: `manifest.json` is moved to `manifest.previous.json` before the strata are cleared, and the new one is written atomically, last. The dataset is a pure function of the raw corpus, the flags and `--seed`, all recorded in the manifest alongside the source shard names and byte sizes, per-class and per-stratum record counts, and the unique-ability-text count of each output — the count that says whether curation preserved the tail, since no record count can. A grown raw corpus is rebuilt whole rather than extended in place, because the split and the rarity table are both corpus-wide quantities — the three output directories are cleared before the write pass, so no shard of an earlier build survives into a dataset the manifest does not describe; `--verify` reports the manifest's drift against the corpus on disk (shards added, removed, resized) and writes nothing. A checkpoint trained with `--corpus` pins the manifest's digest alongside its split (§ Model artifacts); `evaluate-effect-model` fails fast when the dataset it reads has been rebuilt since. The manifest still carries `token_keys_remapped`, `token_keys_ambiguous` and `forge_tokenscripts` from a since-removed token-key remap; a build writes them as `0`, `{}` and `""`, and they stay because every manifest on disk holds them and its digest is pinned by the checkpoints trained on it.
- **`encode-abilities`** — computes the cache once, offline; every downstream consumer reads it rather than the encoder. `--variant` resolves the **checkpoint and the output suffix together**, so a baseline is never encoded with another variant's weights and never lands on the shipping cache. The `taxonomy` variant has no encoder and emits a hash embedding of the sidecar's API type and parameter keys into the same row layout, so every `e`-geometry check reads one file shape. Idempotent; `--clean` removes only the files this variant wrote. The vocabulary and keyword-definition hashes are checked against the checkpoint before anything is written.
- **`collect-coverage`** — sealed self-play only ever plays what sealed pools contain, so a card in no sealed-legal set never appears in a record at all. This builds decks over the **whole** converted corpus, weighted toward the cards with the fewest records, and plays rounds until every card is satisfied or retired. Each round plays `--decks-per-round` (default 500) of those decks as matches, counted from a per-run progress file under `--effect-records` — not itself a sealed corpus, and read by nothing downstream — which is what lets a round end at all rather than running until signalled. Three rules: the castability consult **only ranks** (never drops — being in a game is the precondition an interventional fork starts from, and a card the consult calls uncastable is exactly the one an intervention has to force into play); satisfaction counts acting hosts, event subjects and referenced refs but **not** mere snapshot presence (a card sitting on the battlefield while something else resolves teaches nothing about that card), and only in the gen-3 records `build-corpus` keeps (no `turn_action`, none its refusal rule refuses), a `continuous` record crediting its static's host, and every entity counted as the converted card its printed script file is (a sidecar's `card`), so "Fire // Ice" in hand, "Ice" on the stack or a back face credit `fire`; and a card with no new qualifying record for `--no-progress-rounds` rounds whose games showed it retires, which is the only thing that makes the run terminate. A round charges a stalled round only to the cards its games showed, because a worker draws its decks with replacement and some written decks are never played; a card written into decks but never shown retires after `UNSEEN_RETIRE_FACTOR` (3) times as many rounds. Shard counting runs on `--workers` processes, and each run's decks go to its own `coverage-decks.<run_id>.txt` (`variant-decks.<run_id>.txt` for `collect-variants`), since every worker reloads the file at its start. Both collectors exit 1 at startup without a holdout source — `--exclude-cards`, `--split-from` or `--training-corpus` (FR-058g); the held-out round, `--only-cards`, needs none — and when the connector JAR, `java` or a list file it reads is missing; a worker pool none of whose slots can start a worker ends the run with exit 1 (`ForgeWorkerPool` gives up after `MAX_FAILED_STARTS` failed starts in a row in every slot). `--training-corpus DIR` names the corpus this run extends and the `holdout-cards.txt` it was depleted against in one flag, refusing a directory without a list rather than running undepleted, and refusing either flag it implies beside it. Point it at the **depleted** corpus: discovery recurses, so a tree also holding the full-strength corpus would count validation records toward coverage and a card whose only records are held out would read as satisfied. `--exclude-cards` names the held-out cards to keep out of every deck, reading the list `holdout-cards` writes; it needs no trained model, so this command no longer waits on a training run that is supposed to follow it. `--split-from` is the alternative for adding coverage to a corpus an existing checkpoint trained on, and passing both is refused — two spellings of one holdout is a disagreement nothing would report. It reports **two residues** — cards judged uncastable, and castable cards short of `--target-records` — each retired card under its consult verdict; both fall to interventional resolutions. The coverage unit and the deck candidates come from `output/cardsfolder/` alone: a token script is not a deckable card and could never be satisfied or retired. Cards of a non-deck type (scheme, vanguard, plane, phenomenon, conspiracy, contraption, attraction, dungeon) leave both too, in the held-out round as well: Forge's card database does not load them as deck cards, so a deck holding one never materializes, and with no records they weigh the most and land in most decks. `--wording-cards PATH` (one card name per line, FR-038) runs the card round over the listed cards alone — the coverage unit and the decks both, the holdout still kept out — and is refused beside `--only-cards`. `--directed-fork-rules LIST` is a label only here: no directed fork runs and no startup check applies, and the rules go to every record's `aimed_at`. Every record of `collect-coverage` and `collect-variants` carries `aimed_at`, `[]` where the run names no rule (`CollectorConfig.caps` defaults to `aimed_at=()`).
- **`collect-variants`** — takes `--directed-fork-rules`, `--directed-forks-per-game` (2) and `--directed-fork-probability` (0.25) as `match-outcomes` does, startup check included (§ Forks), the listed rules also aiming every record. Reads Forge's **source** scripts (not the converted ones), perturbs one parameter, and plays the result. A whitelisted numeric parameter shifts by up to ±3 or doubles, floored at one, never zero (a zero amount can make a free ability one that changes nothing, which the Forge AI re-activates without end: gen-2's Sage of Hours at `CounterNum$ 0`); a signed one (`NumAtt$ +2`, `NumDef$ -2`) keeps its sign and a magnitude of at least one, so a pump stays a pump and a debuff a debuff; deck-building hints (`DeckHints:`, `DeckNeeds:`, `DeckHas:`) and `AIPreference` SVars are never perturbed; a card-selecting parameter (`Valid…`, `…Valid`, `ChangeType`, `Affected` and a few more, `script_variants.selects_cards`) swaps its selector from a checked-in whitelist, never a duration, type name, chain label or description that reads like one (gen-2's `Duration$ Permanent` swapped to a selector ended an animation at once and a state trigger re-fired it, thousands of records a game); a protection keyword line (`K:Protection from black`) swaps its quality to a rare one from `PROTECTION_QUALITY_WHITELIST` — card types, conditions, everything and fifteen common creature types, spelled as `ProtectionQuality.fragment` spells them (FR-058). The whitelists exist because a shifted `CounterType` or a generated selector produces a script that fails to load rather than a card that plays differently. `--round` runs one of two rounds (root spec § 8.15; `domain/variant_rounds.py`). **`untargeted`** (default) makes one variant of every eligible source script (single-faced, not held out, perturbable) and plays rounds of `--decks-per-round` matches, each variant weighted by the games it lacks, until every variant has `--variant-games` (2) games or has retired after `--no-progress-rounds` (3) rounds whose games showed it without a new game (one written into decks no game showed retires after `UNSEEN_RETIRE_FACTOR` times as many); a variant's games are the distinct games holding a record whose acting key, or decision candidate's key, names its file, counted from **this run's own shards** (`{run_id}.*`, `VariantGameCounter`), so another run writing to the directory never counts. **`steered`** (`application/steered_variants.py`) needs `--rule-counts`, the corpus's own gen-3 counts (exit 1 without it, or on a counts file whose `generation` is not `gen-3`): a short pair is a rule the map marks `trained` with a declared detector and a polarity with fewer than `--steer-floor` (100) records over all sources, a rule the counts omit short in both; each pair takes `--steer-variants` (2000) × its shortfall ÷ the summed shortfall variants, at least one, made on its carriers (the cards its scenarios name and the cardsfolder carriers the counts list, read from Forge's source scripts; no held-out or multi-faced card): first the `script_edit` of every scenario variant of the pair's rule and polarity that names the carrier, then near misses, one numeric shift or selector swap on a source line the rule's tags act through (the counts' line keys, matched to source lines through the converted sidecar's chained text, `variant_rounds.acting_lines`); a (carrier, edit), the script it makes, yields one variant in the whole round. A steered deck holds one rule's variants and names the rule in a fourth deck-file column (`LABEL;SET_CODE;Cards;RULE`, `deck_file`; Java `GeneratedDeck.parse` splits it with limit 4, so the rule never folds into the last card's name). A game is steered when either of its decks carries a rule (`FE/DeckRules.java`; no cap property): every record it writes carries both decks' rules, de-duplicated and sorted, as `aimed_at` in place of the run's `[]` (a directed fork's record keeps its own rule), and its intervention scheduler first forces the lines of the variant cards each player holds, under the same budget and once-per-line sets, before the pass for lines that branch on whose turn it is (FR-058e). The round iterates: generate for the short pairs not retired, play until each has its games or retires, count this run's shards again (`RunRuleCounter`, added to the file's counts), retire every rule whose short polarities gained fewer than `--steer-min-gain` (1) records, until no short pair is left or after `--steer-iterations` (5). `--variant-volume` and `--corpus-records` are gone. A variant is named `<card> Variant <h>`, `h` the first eight hex digits of the SHA-256 of its perturbed script before renaming (`script_variants.variant_digest`), so a file already under that name is the same script: it is reused as it stands and never rewritten, since an earlier run's records join it by key. Every variant, steered ones included, is written with its sidecar before any deck holds it and stays in the tree. **No variant is generated from a held-out card** — perturbing a parameter changes the text, so the variant's text is not itself held out and would reach training, teaching that card's mechanics under an edit the split cannot see. Nor may a variant of any other card print a held-out text, or its template under `--holdout-unit template`: a perturbation can land on one, so once the sidecars exist every variant whose lines print one, under the holdout `build-corpus` chooses, is left out of the decks, and deleted with its sidecar only when this run wrote it (a reused one may have records already); the command takes `build-corpus`'s `--cards-folder` and three holdout flags with the same defaults, and has to be passed the same values. A variant exists on the script surface only and is never converted to prose. A sidecar pass (`VariantSidecarMain`) runs before the first game: a variant without one produces records nothing can join, and the join is designed to fail loudly. It writes the names Forge's card database loaded to `loadable.lst` in the tree (`collect_variants.LOADABLE_FILE`) — never a `.txt`, because the whole tree is staged into Forge's custom-cards directory and Forge reads every `.txt` there as a card script — and only those are decked. When the run ends, however it ends, the staged scripts are taken back out of Forge's custom-cards directory (`infrastructure/variant_staging.py`, by the staging's `.staged-by-effects.list`). The records of the run's shards are counted, and the command exits 1 when there are none: every deck materializing as basic lands — which is what a staged script Forge's card database never registered produces — otherwise plays its matches, writes its progress lines and reports success having collected nothing.
- **`holdout-cards`** — writes the depletion list `sealed generate-pools --exclude-cards` reads: one Forge canonical card name per line, every card carrying a held-out ability text; a split card under its combined name ("Fire // Ice"), the one Forge's exact-name depletion compares, which the collectors' `read_name_list` reads back as the converted first face too. The one coupling between the two packages, and deliberately a plain file rather than an import — `sealed` must never depend on `effects`. It selects texts through the trainer's own rule, so the two cannot disagree; the same `--holdout-permille` and `--holdout-max-carriers` must be passed here and at training, because a depleted corpus was composed against them and a checkpoint records them.
- **`validate-corpus`** — measures the corpus invariants over a shard directory and exits non-zero on any breach: `record_id` uniqueness, one game per `game_id`, link-half pairing, whether trigger/rewrite/resolution records name an acting line and whether an empty one says why, whether every `keyword` provenance key joins the sidecar of the card it names, whether every record was collected in `patched` mode, whether `outcome` and the cost fields carry anything at all, snapshot-tier uniformity across kinds, the per-kind exact-duplicate rate, the duplicate-**event** rate inside a single record, the trigger fired:not-fired ratio per evaluated mode as well as in aggregate, and whether a fork's snapshot agrees with the record it mirrors about the turn. Every invariant reports **the number it measured** whether it passed or not, because a threshold a run barely clears is what an operator needs to see. Meant for the first few minutes of a collection pass, not for a finished corpus.

  Two rules keep the report worth reading. **Judged and watched are separate**: a check with no settled threshold prints `[WATCH]`, reports its number every pass and cannot fail a run — that is how the `zone_change` `from_zone` share, the `attributed_to` breakdown (per resolution record and, separately, per fork record), the `cause` population rate, the non-keyword provenance join and the probe count are carried, and giving one a floor (`--min-attributed-rate`, `--min-zone-change-from-zone-rate`, `--min-fork-attributed-rate`, `--min-cause-rate`) promotes it to a verdict without changing what is measured. A new number is published watched **first**; failing runs on a check nobody has calibrated is the same mistake as an invariant that fails on every good run. And **an invariant that fails on every good run is worse than no invariant**: "each `game_id` names one game" failed 168 of 177 games on a healthy smoke corpus, every one of them the mana-reservoir flush documented below, so that case is exempted precisely — a resolution half holding a `mana_produced` and otherwise only the `tapped` events of what its cost tapped, recognised by its payload rather than by the acting card — and so is a fired trigger record, which the per-line trigger reservoir also writes at the game's end with the board of the turn it fired (an unfired one is written as drawn and stays checked); the measurement says how many records the exemption covered. A gen-3 cost half standing alone, its item countered or still on the stack at the game's end, is a paired link: it was written at the cast with its `link_id`, before anyone knew the item's fate.

- **`field-coverage`** — names every record field a corpus never varied (§ Collection says why it exists); on a corpus holding gen-3 records it ends with one row per field of the gen-3 snapshot (`field_coverage.GEN3_FIELDS`): varies, constant or absent.
- **`rule-counts`** — tags every record of `--records-dir` with the catalogue's detectors (§ Generation 3) and writes `rule -> polarity -> source -> records` to `--output` (default `output/effects/rule-counts.json`) beside `records`, `not_countable`, `none` (the rules declared without a detector, with their reasons) and `review` (`record_id`, scenario); it prints one line per rule by unit, `fires` and `does_not_fire` each split `random_seat / forge_ai / aimed`, then the `none` rules, the uncountable ones and the review list's size. The file also holds `generation` (`gen-2` or `gen-3`, which the steered variant round checks) and `carriers` (FR-058f): per rule, `[{script_file, records, lines: [{key, records}]}]`, most records first — the script file of every card that is a condition entity of the rule's tags (a card entity with no printed line names none), and the lines the tags act through on it: the record's acting key (or decision candidate's) on that script, else the carrier's keyword line of the keyword the tagging scenario's detector names, from the entity's lines or its sidecar. A rule no record tags is omitted, so absent is not "not countable". Gen-2 or gen-3 shards, never mixed (exit 1, as on an empty directory). Each `--workers` process reads its shards once with its own detector index and sidecar cache; `--rules-dir` (default `rules`), `--cards-folder` and `--variant-scripts` default as `build-corpus`.
- **`evaluate-effect-model`** — the three gates and the reported checks. **Splits are never a flag**: the held-out card list and both `game_id` sets come from `--checkpoint`, because the corpus is append-only and a recomputed split would score the gates partly on games the model trained on. A `--variant-checkpoint NAME=PATH` recording a different split or different vocabulary hashes fails fast. `--corpus` defaults to the dataset `--checkpoint` recorded; a checkpoint that records none is refused, and so is a corpus whose manifest digest has changed — a rebuilt dataset is a different split, so scoring the gates against it would score them partly on games the model trained on. `--variant-scripts` defaults to the tree that corpus's manifest recorded. The three FR-116 checks never built — matched real-vs-fork agreement, the probe-diff re-check and the role-polarity probe — report `NOT_IMPLEMENTED`, printed `[todo]` with what each would measure, on every run; they are not skips, because the corpus holds the fork, probe and mana records they would read. Every geometry check keys the cache on the checkpoint's encoding surface (`surface_of` its recorded vocabulary), so on a script checkpoint two lines sharing prose but not script stay two points. The ward canary's lines (`domain/ward_twins.py`) and the nearest-neighbour queries are `LineQuery`s — converted prose as `convert` spells it (`ward {2}`, `destroy target creature.`, `CARDNAME`), pinned to a card wherever that prose compiles to more than one script — resolved to the encoded key and printed back in prose; one that resolves to nothing is named in the report as unresolved, never dropped. The report is printed; the one check that draws a picture, UMAP (`application/umap_check.py`), writes `umap.png` and `umap.csv` into `<checkpoint stem>.evaluation/` beside `--checkpoint` and names both on its line. The picture has one panel per script API type, the twelve most frequent and the rest as `other`, each panel's texts over every other text: a dozen hues in one scatter cannot be told apart. The table holds each unique text's coordinates and its own API type, so a cluster seen in the picture can be looked up.

## Generation 2

Feature 024 (`specs/024-ability-effect-model-gen2/`) changed what is decided at collection time, what curation keeps, and what training and evaluation report. Run order: `specs/024-ability-effect-model-gen2/quickstart.md`.

**Encoding text.** A sidecar line's `script_text` is the trait's whole chain — root segment, a trigger's `Execute$` ability, every sub-ability including `RepeatSubAbility`, a replacement's `ReplaceWith$` ability — joined by ` [SEG] `, each later segment opened by its label. Chain labels are renamed `SV1…` by first appearance per line, so two cards differing only in an author's SVar name share a text. A charm root carries its own segment (`Choices$ SV1,SV2,…`) and each mode is an `option` line keyed root + `option` with its own chain and API type. `convert` reports every undefined SVar once per run. The converted `.txt` is byte-identical to before, which the connector's `golden-024` tests guard.

**Script tokenization.** One grammar, `tokenize`, on both surfaces; the surface is fixed at construction from `surface_of(vocab_path)`, so every new `AbilityTokenizer` takes `surface=`. A checkpoint records the rules it trained under (`training_settings["tokenizer_rules"] = "gen-2"`), and every loader picks the grammar through `tokenizer_surface`: a gen-1 checkpoint records none and is read with the prose grammar it trained on, because the script rules below would turn about one of its script tokens in thirty into `[UNK]`. On the script surface camel case splits (`ConditionCompare$` → `condition compare $`), `$` is always its own token, `TokenScript$` values split at `_`, and these stay whole: the values of `Execute$`, `SubAbility$`, `RepeatSubAbility$`, `ReplaceWith$` and `CounterType$`, segment openers, and `Choices$` items of the five chooser APIs (`Charm`, `GenericChoice`, `AssignGroup`, `VillainousChoice`, `Vote` — elsewhere `Choices$` is a selector). `build-vocab --surface script` stages script lines before the prose files and seeds `[SEG]`, `sv1…svN`, every template word and every key part, so `--target-size` cannot drop them; it fails when a definition would expand to `[UNK]`. A keyword line expands by its display name (the text before the first colon), filled through `domain/keyword_formatting.py`, which mirrors Forge's per-`Keyword.type` formatting. Validation, evaluation and the cache expand at `INFERENCE_KEYWORD_EXPAND_P = 0`, so only unknown keywords expand there. Every encoding command reports each line it truncates at 512 tokens, by provenance key.

**Random seat.** `match-outcomes --random-seat-share F --random-seat-probability P`: in a share `F` of matches one seat is a `RandomSeatController`, a `PlayerControllerAi` subclass; Forge itself is unchanged. At every priority, attack, block and target decision it draws uniformly from the legal options with probability `P`. It never passes while a non-mana ability is playable, and it leaves the land drop, mana payment and mulligans to the Forge AI. A play it drew has every casting choice drawn at random too. On a random draw it writes the `decision`, `attackers` and `blockers` records the AI's hooks would have. Its matches write effect records only, never a match-outcome or cards-played row. `collect-coverage` and `collect-variants` take the same two flags, with the same refusal of a share above 0 without a probability: the AI never casts some cards at all, and a random seat casts them for real where an intervention forks past their cost and choices. Records carry `random_seat`; blockers records carry `what_if` (`false` for the declaration actually made, `true` for an AI query about a hypothetical), and so did gen-2's attackers records, which gen 3 replaces by one record per attacker with none. Every real decision is written and no what-if is, because the AI re-asks one combat many times while planning and a query drawn before de-duplication survives in proportion to how often it was asked. Blocks against attacks the AI rejected reach the corpus instead as real decisions against the random seat. On gen-2 and gen-3 `playability` records `actor_player` is the deciding player. A shard's generation is its records' `generation` (gen-3), else the presence of `random_seat` (gen-2), else gen-1 (`domain/shard_generation.py`). `build-corpus`, `train-effect-model`, `evaluate-effect-model` and the knowledge probes read gen-3 only (`ACCEPTED_GENERATIONS`, `require_generation`: exit 1 naming the first other shard and its generation), and `rule-counts` reads gen-2 or gen-3; every reader refuses a mix. A curated shard keeps its source's generation, because the codec writes a record back as it read it.

**Modal resolutions.** A patched worker writes one cost half through the charm's root key and one effect half per chosen mode resolution through root key + `option`, all sharing one `link_id`, each with a snapshot taken at its mode's first clause; a fizzled or declined charm likewise writes one empty half per chosen mode (FR-029c), a charm fizzled as a whole, whose clauses never run, each on the board at its resolution's start; a degraded worker writes one root effect half. `validate-corpus` accepts several effect halves per `link_id` only when they are modes of one root.

**Holdout.** `--holdout-unit template` (the default on `holdout-cards` and `build-corpus`; `train-effect-model` takes the manifest's) holds out masked templates: the chained text with every digit run outside chain labels, `CARDNAME` and description values masked, so `NumDmg$ 2` and `NumDmg$ 3` fall on one side. `text` reproduces feature 023. Token scripts count as carriers, toward `--holdout-max-carriers` too, and a token script printing a held-out text is held out by its script file, so a game holding that token is held out; `holdout-cards`, `build-corpus` and the trainer's recompute all read the token tree for it. `HeldOutCards.holds_text` tests any script text against the held-out units, a template under `--holdout-unit template`, which is what lets `collect-variants` and `build-corpus` refuse a variant or token printing one. The trainer recomputes the holdout over its `--cards-folder` sidecars and refuses a disagreement with the manifest. `collect-coverage --only-cards <holdout list>` builds decks from those cards alone, under the run's own caps (the three decision-sampling rates included, FR-059a), and counts random-seat games too, since they go to the card-disjoint stratum, and counts distinct games per text until `--min-text-games` (default 5). A game counts toward the text `build-corpus` credits it to — its first acting key whose text `holds_text`, through the one `HeldOutCards.text_acted_through` both commands call — so under `template` a game whose first acting key prints a held-out template no listed card carries counts toward no listed text at all; the round therefore takes the three holdout flags with `build-corpus`'s defaults, and has to be passed the same values.

**Curation.** Every record has one effect family (`domain/effect_families.py`): the acting line's API type for resolutions, the trigger's `Mode$`, the static's `Mode$`, the replacement's `Event$`, the damage-step keyword set for combat, the restricting static's mode or first failing verdict bit for a decision, the rarest single restricting mode for a legality record (a `Mode$` list counts as each mode; the survey's per-mode counts go in the manifest as `legality_mode_counts`, and the trainer and evaluator place legality records by the same table), and a keyword line's display name whatever the kind. Each class budget is split equally over families, then (for effects, rewrites, combat and continuous) over outcome signatures, the set of distinct (zone outcome, changed) pairs. One water-filling allocator (`domain/budget_allocation.py`) does every split: a short family's records repeat up to `--reuse-cap` (default 4) and its unused share passes on. Real legality decisions fill up to half the legality class first. Each record is written `copies` times, every choice a function of its hash and `--seed`. The manifest reports per-family shares, repeats and shortfalls, records per signature, on/off-policy and real/what-if counts, keyword-threshold games and held-out texts with too few games. Each new manifest field is omitted at its gen-1 value, so a gen-1 manifest's digest is unchanged.

**Training.** Noise on `e` is applied in the batcher, in training only, as Gaussian noise with covariance `r²Σ`. `Σ` is the running covariance of the batch's `e` (seeded from the first batch, decay 0.99, no gradient), and `r` ramps to `--e-noise` (default 0.1) over the first epoch. A training-only value head reads `e` alone and predicts script-stated amounts and cost flags (`domain/value_targets.py`; spell lines mask mana costs) at `--value-weight` (0.05). Its targets are read from the line's sidecar `script_text` on both surfaces, since prose has no `$` parameter to read, and so are the script-API head's. Power and toughness changes sum `NumAtt$`/`AddPower$` and `NumDef$`/`AddToughness$`; `counters_placed` reads `CounterNum$` on `PutCounter`/`PutCounterAll` and `counters_removed` on `RemoveCounter`/`RemoveCounterAll`; `cards_drawn` reads `NumCards$` on `Draw` only. An absent amount key takes Forge's default — one card for `Draw`, one counter for `PutCounter`, `PutCounterAll` and `RemoveCounter` — and `RemoveCounterAll`, which has none, is masked. `MoveCounter`, `AddOrRemoveCounter` and `ReplaceCounter` mask both counter targets, and any non-literal value masks its target; beside each amount it predicts whether the magnitude is at least k for k = 1…40 (`AT_LEAST_SLICES`, averaged so the block weighs one binary target), which pushes `e` to carry amounts as a thermometer the trunk can compare. The verdict, created-objects, MLM and script-API losses are wired, and a `decision` record's `[ACT]` reads its candidate's `e`. The MLM pass zeroes a masked position's numeric value and its number flag along with the token, since the encoder adds the number embedding beside the token's and would otherwise hand a masked digit back. `--api-weight` defaults to 0.003, which starts the script-API term beside the other auxiliaries rather than above them. **Input layout** (`effect_head_input.py`): a checkpoint records `training_settings["input_layout"]`, and `effect_model_store` refuses on load (`CheckpointLayoutError`, exit 1) any checkpoint recording another layout or none, so every loader reads only the layout this code builds; earlier layouts no longer load. The layout is `gen-3` (§ Generation 3), and `layout_settings()` records beside it the relation types, the subtypes and named counters and the closed output lists, whose orders fix table rows and columns, so a checkpoint whose lists differ is refused the same way. Gen-2 maps Forge's `combat_*` phase names, `+1/+1`/`-1/-1` counters and `protection_from_<x>` onto the vocabularies' slots (they used to land in "other"), appends a `landwalk` keyword slot, and ends each card slot with thermometer codes of total power, total toughness and toughness minus marked damage and each player slot with one of life (`THERMOMETER_STEPS = 40`, the magnitude cap, since life often passes 20), so a stated amount compares with them in one attention score. Charm option rows follow their root row with a learned option-kind embedding that starts at zero. Every count and signed-delta magnitude is scored at no more than 40 (`MAGNITUDE_CAP`), in the field losses, the created-objects counts, the constant-predictor floor and the evaluation's deviance: above that an amount is the game compounding, not the text, and one Bristly Bill game's +2,098,760 power spiked a shard's loss to 169k. `--lethality-copies K` (`domain/lethality_counterfactuals.py`, FR-063e) appends to each training step K copies of every damage or -X/-X resolution whose chain cannot turn on the death and whose real outcome obeys rule 704.5f-g: one hit creature's toughness and the amount (in the text under a `counterfactual/<amount>/…` key the step's batcher reads as an override, `SurfaceBatcher.override_text` — the script's amount on the script surface, the converted prose's amount on the prose surface with its role spans shifted by the edit — or in `refs.x` for a paid X) are redrawn from 1 to 8 and the deaths relabelled by the rule. Forge's AI aims removal at creatures it can kill, so without them the corpus rarely shows damage falling short and the model learns "small creatures die" instead of comparing the amount with the toughness. K = 0 trains bit for bit as before. `--patience 0` turns early stopping off, and `--resume` decides under this run's patience and epochs whether anything is left, so a run that stopped early can be continued; `--lr-scale` multiplies the learning rate and may change on a resume; `--save-every-epoch` keeps every epoch's checkpoint under `epochs/`; and a new best epoch copies `resume.pt` to `resume-best.pt`, which another run directory can continue from (FR-063f). Each epoch line reports the share of trained records per rarity bucket (`domain/rarity.py`: 1, 2–4, 5–19, 20+ games) and per family, and every loss term.

**Losses.** Every head reduces one way (`effect_losses.per_row`): a row's loss is summed over its targets, then averaged over the batch's rows, a row being a record for the per-entity, created-objects and verdict heads and an encoded text for the value, script-API and MLM heads; the value head's forty at-least bits are still averaged into one binary target's weight. On the per-entity head the affected gate trains on every entity of a record that is not a playability record (`EntityTargetBatch.gated`, root spec § 11.4: a decision or declaration observes which entities could be chosen, not what changed), and a field trains only where the gate's target fires **and** the field is present (`EntityFieldTargets` in `entity_field_targets.py`); the legality fields (`FieldSpec.gated` false: `target_legal`, `attacker_legal`, `blocker_legal`, `min_blockers`, `attack_target_legal`, `combat_requirement`) train wherever present, gate or no gate, `target_legal` on every card and player of a decision whose candidate has a targeting clause (1 in `legal_targets`, 0 elsewhere). A field is present where the record wrote it, or where it has a silent value, the record's sampling class supervises it and the entity is of the field's `FieldScope` (a player is never scored on a zone, a permanent never on life). Silent values: zone = stayed; damage, counters and P/T change = 0; types, colours and keywords gained or lost = none; control and attached-to change = 0; a player's life, cards drawn/discarded/milled, library events, poison and mana = 0. `tap_state`, both durations, the legality bits and `min_blockers` have none and train only where an event or a payload sets them, because a creature no event mentions is neither tapped nor untapped. `continuous` records supervise the P/T, keyword, type and colour fields too, and a `=` in a contribution's `types` or `colors` marks the matching `*_lost` field unknown, which no silent value overrides. A `trigger` record derives no per-entity targets — its events are what caused it, and what it then does arrives as its resolution record — so it supervises the verdict head's fired bit, and the gate trains on its entities as negatives. Per-entity count fields are scored from 0 to the cap, never below zero (`damage_taken` nets healing). Every count and amount term — per-entity counts and signed-delta magnitudes, the created-objects counts, the verdict head's mana paid, cost adjustment and effects created, the global head's turn-structure counts, the value head's amounts — is a negative binomial (`field_kinds.negative_binomial`, FR-063) with one learned log-dispersion per field (`EffectModel.*_dispersion`, in the `head` group, the value head's training-only), read in [-6, 10] and started at log 10; it is the Poisson in the limit. Every shipped term — the gate and each per-entity field, each verdict and global field, each created-objects slot column — is divided by its loss denominator (FR-062): its constant-prediction loss in nats per record (`loss_floor.constant_predictor_losses`) over eight training shards drawn under `--seed` before the first step (`application/denominator_pass.py`), clamped below at `--deviance-floor` (0.04), and a term the sample never supervised divides by the floor. The denominators go into `resume.pt` and every checkpoint (`loss_denominators`), and a resume reuses them rather than recomputing. The loss training descends and validation's loss are both scaled; the parts the shard and epoch lines print stay in nats, so they still compare with the constant-predictor floor. The constant-predictor floor reads the same presence. **The rule mask** (`--rule-mask`, FR-061, `domain/rule_mask.py`) weighs each curated copy's outputs from its `curation` and each rule's effective outputs (`CorpusFacts.rule_outputs`, the manifest's `effective_rule_outputs`): under `hard` (default) a copy rule budgets added trains only the effective outputs of every rule its record was drawn for — per-entity fields wherever the record supervises them, verdict and global fields, `created_objects` as one head — and the affected gate on its drawn rule's tag entities alone, condition and outcome alike (`Curation.rule_entities`), so a copy whose rule names no entity in either role trains no gate and one whose rule names an output the record lacks trains the gate alone; under `soft` every copy trains every output, the drawn rules' at weight 1 and the rest at `natural_share / copies`. A natural copy of a record with no added copy, a natural copy of an aimed record and a lethality copy train everything at full weight; the value, script-API and MLM heads read texts and no mask reaches them. The host half builds it (`StepPreparer.rule_mask` → `entity_target_tensors`' `weights`, a weight-zero field cleared from presence, a fractional one in `EntityFieldTargets.weights`; the gate's per-entity weight in `EntityTargetBatch.gate_weight`, applied in `effect_losses._gate_term`; a record head's mask turned float); training, validation and the denominator pre-pass all prepare through it, and the floor weighs each target as the run does (its constant fitted unweighted). Evaluation (`per_entity_targets`) reads records unmasked. Feature 025 (`specs/025-ability-effect-model-gen3/`, root spec `specs/2026-10-30-ability-effect-model-gen3.md`) ties the corpus, the model's inputs and outputs, curation and checkpoint selection to the rules of the game. **Record moments** (root spec § 8.14, FR-042a–FR-042f; connector `BusBracketCollector`, `HeldResolutionWindow`, `ManaChannel`, `RewriteChannel`). Each record's board is read just before the moment it describes, and its events are what the moment changed. ## Collection

Instrumentation is an opt-in on a command that already exists:

```bash
python -m sealed match-outcomes --effect-records output/effects/records/
```

`--effect-records` has **no default** there — collection is the opt-in, not the point, and a default would quietly turn every self-play run into a collection run. Absent the flag nothing changes: no shard is opened, and `match-outcomes.txt` and `cards-played.txt` keep their exact format and content. The instrumentation costs no extra simulation; it rides matches that were going to be played anyway.

Attribution mode is **detected at worker startup**, not compiled in: the patch lives in the sibling `../forge` checkout, which is rebuilt independently and re-patched by hand after every Forge upgrade, so a build-time switch would silently mislabel a corpus collected after the patch lapsed. Every record carries the detected `mode`.

`MatchWorkerMain` also has a **records-only mode**: with `-Deffect.records.dir` set and `-Doutput.file` absent, neither sealed writer is constructed at all. The coverage and variant collectors reuse this worker, and their decks are built for coverage rather than for a fair self-play sample — mixing them into the sealed corpus would corrupt the scorer's training data.

### Why the workers are short-lived, and what follows from it

Every collecting supervisor runs its Forge workers under `-Xmx1200m` and has `ForgeWorkerPool` kill the longest-running one every status interval (60 s), restarting it at once. **Neither is a tuning knob, and they are one measure rather than two.** Forge misbehaves late in a JVM's life — loops that do not terminate, allocation that grows without bound — and the pair is the containment: the small heap turns a runaway worker into an early, cheap death the pool restarts instead of one worker dragging the machine down hours into a run, and the hard recycle bounds the pathologies that do not allocate. Raising the heap or lengthening the interval hides the pathology rather than containing it. The price — a handful of GC crashes per overnight run, each costing the block of records in flight and nothing else — is paid deliberately. Do not propose removing either without saying what contains Forge instead; a corpus analysis nearly recommended undoing the heap setting before learning why it exists.

**What follows is a correctness constraint, not a throughput one.** Restarts are the normal operating condition: an eight-hour run is roughly 530 JVM lifetimes across six worker slots, many of them killed mid-game by `taskkill /F /T`, which runs no shutdown hook. So record identity, game boundaries, and any resume logic have to be correct across hundreds of restarts *and* across a JVM killed mid-game:

- Anything a worker counts from zero must be namespaced by the JVM **lifetime**, not by the worker slot. The first corpus was not: 71–75% of its `record_id` values were repeats and 804 `game_id` values covered 31,662 games, merging unrelated games under the corpus's own join key. That is why the lifetime segment is in the id and in the shard name.
- A file boundary is not a game boundary. A game can be cut in half by a kill and its remainder never written.
- A shard ends at its last complete 256-record block, so the last ≤255 records of each lifetime — about 0.5% of a run, always a game's tail — are absent. A resume that assumes a clean shutdown left a marker is wrong.
- Catch this in minutes, not hours: `python -m effects validate-corpus --effect-records <dir>` over the first few minutes of a pass. Every defect above was visible in the first minute of shards and none of them raised anything for eight hours.

### The engine hooks

The hooks live on the **`effect-record-hooks` branch of the sibling `../forge` checkout**, an ordinary branch: changes land as new commits on top, and a Forge upgrade is merged in rather than rebased under them. There is no exported patch series in this repository: the branch is the history, and a directory of `.patch` files beside it was a second copy of that history maintained by hand, which git already does better.

`PatchHooks.REQUIRED` is the inventory — every class, method, and the record channel it feeds. It is the specification of what a patched Forge must have, and it is load-bearing rather than documentation: `AttributionMode` probes `PatchHooks.SUB_ABILITY`, `PatchedCollectors.CAN_SUPPRESS` reads the three `…Without` entries, and `PatchHooks.report()` prints what is missing at worker startup. A **partly-applied** patch is the state that matters — the mode still reads `patched`, because that is one hook's answer, while a channel the run meant to collect is quietly empty — so read that line, not just the mode.

```bash
cd ../forge && git checkout effect-record-hooks   # or: git merge master, after an upgrade
mvn -pl forge-core,forge-game,forge-ai -am install -DskipTests
cd ../price-predictor/forge-connector && mvn install -DskipTests
```

Rebuild the fat JAR afterwards, always: the worker links against the freshly installed Forge jars. Applied, a run reaches **all eight** sampling classes; unapplied, three, and every record is stamped `degraded`.

**Where the events come from.** Forge's bus publishes an event of its own only for outcomes that have one — damage, counters, zone changes, taps. A pump, an anthem recompute, an animation and a colour change all publish the same thing, that a card's stats changed, and name only the card. `StatDiffer` remembers each card's computed characteristics and describes the difference, which is where `pt_change`, `keyword_change`, `type_change`, `color_change` and `control_change` come from; a draw, a discard and a mill are classified from the zone pair, since Forge has no event for any of the three. Without those the whole "gets +2/+2 and gains flying" family — most of what a limited deck does — resolved into an empty event list. A record's stat changes are changes after its own snapshot: the differ re-reads the battlefield when a bracket opened at a cast, a mode's half, a damage step or a fork's forced cast takes its snapshot (`BusEventReader.rebaselineStats`), because Forge can apply a change long before publishing it — the state-based loop applies statics on every pass and announces them once at its end, after a dies trigger it stacked has opened its bracket. A change the re-read swallows reaches no record and is counted as dropped. Not while an ability resolves: its bracket keeps the events, and its snapshot is older.

An event's `duration` is read from the acting script's `Duration$` and bucketed to the head's three values; an undeclared one is what Forge applies — instant for an outcome with no lasting state, end of turn for a P/T, keyword, type or colour change by an API Forge ends at end of turn by default (Pump, Animate, Debuff, Protection, Effect and their `All` forms, ChangeText, ExchangePower), permanent for any other, such as a counter; `attributed_to` is the resolving sub-ability's chain index, counted **upward** from the clause via `getParent()` rather than downward from the bracket's root, because Forge resolves a copy and the two chains are not the same objects.

`python -m effects field-coverage` names every record field a corpus never varied. It exists because the failure it looks for leaves no trace: a collector that writes `"blocking":[]` produces records byte-identical to ones for a creature that genuinely is not blocking, so the shape is right, the contract tests pass, and the field is dead. Fourteen such fields were found one at a time before it was written and it found six more immediately, including the reason `pt_duration` and `type_color_duration` are the only two head fields no target path writes — an `Event`'s `duration` has a setter that nothing calls. `KNOWN_CONSTANT_FIELDS` lists the ones that are known dead; the integration test fails when one of them starts carrying data, so the list can only shrink. It is asserted in that direction only, because a field that is merely rare looks exactly like a field that is unwired.

A resolution's effect half is **held across the state-based loop that follows it** and written at the loop's end signal (FR-028), rather than when Forge reports the spell resolved. Forge runs state-based actions after that report, so a record written at it lost every death its own effects caused: a burn spell's target appeared damaged and never dead, and a model trained on that learns damage kills nothing. The loop is `PhaseHandler.checkStateBasedEffects`, whose begin and end the `state-based-loop` hook signals (`FE/PhaseSignals.java` delivers them to `BusBracketCollector.phaseSink()`); while held, the half takes every battlefield-leaving move between the two signals, every pass included, frozen tracker or not. The check before the resolution found nothing to do, so whatever this one finds the resolution caused: a burn spell's kill, a −X/−X Aura's, the creatures that die as a shrinking static enters, the legend rule, an Aura falling off its host. Triggers reach the stack between two passes; such a trigger opens its own bracket without closing the held half, so a dies trigger's records hold none of the check's deaths, while a death its own resolution later causes is the trigger's. Moves after the loop stay out, so a Treasure the spell made and later sacrificed for the next spell does not join it. A state-based death with no held half and no open damage step — a creature a -1/-1 counter cost leaves at 0 toughness, Maro shrinking as its controller casts the last card in hand — reaches **no** record (FR-029), not the open cast bracket it used to join; the fork sink refuses it the same way. On a worker without the loop hook the half falls back to closing at the next action — the next cast or trigger, another resolution, a phase change, combat, a land played, game end — and a move counts as the check's while `game.getTracker().isFrozen()`. On a modal resolution, and on a modal fork, a death goes to the mode half whose events named the permanent, otherwise to the last half. The held half takes deaths only, never a stat change. A combat damage step's record holds its own check: a trigger put on the stack inside that loop no longer closes it, the loop's end does. Interventional forks run the check themselves.

Every event that reaches no record — one at a player's action at priority that is no cast, an orphan discarded rather than rescued at game end, a state-based death nothing took — is counted per game by event type and engine phase (`FE/DroppedEvents.java`). Under `--count-dropped-events` (`effect.count.dropped.events`; `match-outcomes`, `collect-coverage`, `collect-variants`; default off) each game's counts are appended to `{run_id}.{worker}-{lifetime}.dropped-events.tsv` beside its shard — per game, because workers are killed with their process tree and run no shutdown hook — and the supervisor sums its run's files and prints the table when the run ends (`dropped_events_report` in `sealed/infrastructure/effect_collection_flags.py`, FR-041).

A `continuous` record's snapshot is **the board without its own static**, which is the premise of the kind: the label is what the static does, so a snapshot carrying that static's work would hand the model the answer with the question. The board is recomputed with the static's layer entries dropped rather than stripped of the tokens it contributed, and the difference is not academic — a creature printed with trample keeps trample when the anthem granting it is removed, and subtracting the contribution would describe a board that never existed. Expect a few percent of contributions to survive their own snapshot for exactly that reason. Every channel of the entity reads that board through one object (`StaticSuppression`): type, colour, keywords, set base P/T (layers 7a and 7b) and boosts, controller, summoning sickness, the lines the static granted (gone) and the lines it removed (back, keyed to their printed lines), and no static lists what it affects. A contribution carries `set_pt` when its static sets a base and `controller` when it gives control, each only then, so a static whose only change is a set base (Godhead of Awe) or control (Control Magic) is a record of its own, and continuous targets derive `base_*_delta` against the board's base and `control_change`. A checkout whose patch predates the `…Without` methods (`PatchHooks.TYPE_WITHOUT` … `TRAITS_WITHOUT`) collects no continuous records at all rather than leaking ones.

A `continuous` record's `types` and `colors` are each one flat token list, because the record schema fixes a contribution's fields: a bare token is a type or colour the static adds, `-x` one it removes, and a lone `=` marks a line the static sets outright rather than adds to. Contract in `specs/023-ability-effect-model/contracts/record-schema.md`. Two consequences worth knowing. Subtypes and supertypes are recorded and then dropped at target derivation, because `types_gained` / `types_lost` cover the core types only — the record is the archive and a head reads a subset of it. And a `=` on a gen-1 or gen-2 record leaves `types_lost` unset rather than naming what it displaced; on a gen-3 record, whose snapshot is the board without the static (`StaticSuppression`), the lost fields are the entity's own types, subtypes, supertypes and colours there, less what the `=` sets (`effect_targets._displaceable`).

An entity's `token_script_id` changed value space on 2026-09-17 (FR-078): before, it was the token's printed name (`card.getName()`); after, it is the token's script stem (`c_a_food_sac`), falling back to the printed name only for a token whose script cannot be named. A shard collected before that date carries the printed name regardless of which token it names, so a reader spanning shards from both sides sees both value spaces in the same field.

Three collectors repeat themselves, and all three are capped **by identity rather than by count**: continuous effects reapply on every recompute, the AI re-asks who may block while it evaluates a combat, and a Mountain taps a dozen times for the same R. The repeats describe a board that did not move, so one carries the observation and the rest are duplication — legality records were four fifths of the corpus before coalescing, and mana fell from 33 a game to under 5. A count cap would keep the first N and then nothing, concentrating a card's records in whichever games came first; one per game spreads them across every game the card appeared in. `--mana-cap` is keyed on the mana produced as well as the ability, so a dual land records each colour it makes.

Mana is **reservoir-sampled** (Algorithm R) rather than taken first, and the reason is the whole point of the cap: a land's first tap is turn one against an empty board, so keeping it would make every mana record describe the same early game — a bias in the one input the model conditions on. The records are therefore held until `close()`, because which activation survives is not known until the game ends (gen-3 reads each record's board before the mana ability's costs are paid, `CostPayment`'s payment hook, so every activation renders one board, and a triggered mana ability's mana, Wild Growth's, joins the record of the activation that set it off); a JVM that dies loses that game's reservoir, which is bounded by `--mana-cap` per ability and cheap against a crash that already cost the rest of the game. Two consequences worth knowing: the state snapshot is taken when the mana was made rather than at flush, and the expensive part is paid a logarithmic number of times rather than once per activation.

Both samplers scramble their seed through SplitMix64's finalizer first. Games are seeded consecutively, and a linear congruential generator's first output is nearly a linear function of its seed, so without it consecutive games take nearly the same first sampling decision — a correlation across the whole run that no test of one game can see.

`--probe-keywords` is spelled as the JVM compares it (lower case, spaces as `_`, `effect_collection_flags.probe_keyword_list`), and a keyword gate 2 does not check is refused at parse time. The eight cap flags (`--mana-cap`, `--playability-rate`, `--zone-candidate-rate`, `--plain-candidate-rate`, `--interventions-per-game`, `--probes-per-game`, `--probe-keywords`, `--max-records-per-game`) are per-worker-process quantities the Python supervisor cannot observe, so they reach the JVM as `-Deffect.*` system properties and `CollectionCaps.fromSystemProperties()` reads them back, each falling back to its default rather than failing. `--max-records-per-game` (default 5000, FR-041a) bounds a game whose AIs loop: `RecordShardWriter` writes a game's first N records, its forks' included, withholds and counts the rest, and when the game's recording closes prints one line naming the game, the count and the turn and acting script most withheld records shared. These flags, `--count-dropped-events`, the directed-fork flags, the random-seat, candidate-rate and directed-fork startup checks, the dropped-events report and the probe startup line are defined once, in `sealed.infrastructure.effect_collection_flags`, which both CLIs import (`sealed` never imports `effects`); `tests/unit/effects/domain/test_collection_caps.py` pins its defaults against `CollectionCaps`, **and pins both against the property literals in `CollectionCaps.java`**: a property one side reads and the other never writes is invisible from both, and `effect.legality.rate` was once read by the JVM and settable by no command.

Snapshot depth is not a flag. `SnapshotBuilder` renders all four inclusion tiers into every record — referenced objects, the core board, the unreferenced stack, unreferenced hands and graveyards — and writes `state.tiers` as `[1,2,3,4]`. A depth that varied by collector or by run made `state.tiers` a proxy for how a record was collected: the first corpus put tier 4 on the interventional records and nowhere else, a perfect predictor of a flag the schema bars from the model. The field is still written because the schema is frozen and older shards carry `[1,2,3]` or `[1,2]`; readers keep treating an absent tier as uncollected rather than empty, and `validate-corpus` still checks that a pass's records share one tier vector.

`--probe-keywords` defaults to all eight damage-step keywords (`first_strike,double_strike,deathtouch,lifelink,trample,indestructible,wither,infect`, derived from gate 2's table in `domain/damage_step_keywords.py` and restated in `sealed`), so every collecting command probes unless a run narrows the list. An empty string takes **no probe fork at all**, whatever `--probes-per-game` says — the one that reads like the switch is the budget, and a run with zero probe evidence in it otherwise says nothing for eight hours. Every collecting command prints its probe state — enabled with the keyword list, or `Damage-step probes DISABLED` naming the flag — before the first worker spawns, and `validate-corpus` reports the probe count as a watched number. The JVM's own fallback, for a worker started with no `effect.probe.keywords` property, is the empty list; every supervisor sets the property.

Nothing here depends on the patch being applied: the connector builds against **stock** Forge, reaches every hook by name through `PatchHooks`, and falls back to bracket attribution when it finds none. The cost of the reflective approach is that a typo in a hook's name shows up at runtime as `degraded` rather than at compile time, which is why every record carries the detected mode and `tests/integration/test_effects_patched.py` asserts it. For the same reason the tests read the checkout rather than assuming it — one that pinned `degraded` would fail the day the patch landed, with nothing wrong.

### Forks

Some abilities are never cast in any game Forge's AI plays — it judges them bad, cannot afford them, or never draws them into a board where they do anything — so no amount of observation produces a record. An **interventional resolution** forks the game and forces one, writing the effect half alone (there was no real activation, so there is no cost half to link to). A **damage-step probe** re-runs one combat with a keyword stripped; it carries `fork = true` and `interventional = false`, which distinguishes it from an intervention by flags alone, plus `mirror_of`.

Two choices in `intervene` are what make it produce anything. The ability goes **on the fork's stack directly** rather than through `ComputerUtil.handlePlayingSpellAbility`, because the cost is usually the reason the record is missing: routing through cost payment succeeds only on free plays, which is how a first attempt produced nothing but land drops. And the candidate is chosen at a **phase boundary**, never inside the AI's own evaluation of its candidates: forking there copies a game mid-decision and re-enters the rules engine underneath it.

A probe forks at the **phase event**, which fires before the turn-based action that deals the damage — the only moment the copy can diverge from a board where nothing has been dealt yet. The keyword comes off through the layer system rather than the printed list, so a printed, equipped and until-end-of-turn keyword all go the way the rules would take them. The fork then runs `assignCombatDamage` and `dealAssignedDamage` itself.

The branch is **held rather than written**, because it mirrors the real combat record and that record has no id until the step the probe forked ahead of has finished; `BusBracketCollector.onCombatRecord` hands the id over when it writes one. Reconstructing the pairing from board state instead would break on two identical-looking combats in one turn.

A probe's payload names **both the keyword and the carrier** (`probed_keyword`, `probed_entity`). The keyword alone is ambiguous on a board with two tramplers, and an evaluator reproducing the perturbation model-side would strip the wrong creature — comparing against a counterfactual nobody ran. Both fields are absent on an observed combat record, which perturbs nothing.

Three rules the budgets depend on: every fork is score-checked against the live game **before** any perturbation (a copy that already disagrees is measuring the copier — both games are scored from one seeded random stream of the check's own, `Forks.score`, because before the second main phase the evaluator has the AI declare the coming combat in a copy, drawing from Forge's global `MyRandom`, and an exact copy scored from that stream simulated a different combat; a disagreement prints `score mismatch detail` with the evaluator's breakdown lines one game has and the other lacks, `ScoreMismatchReport`; the rating weighs only part of the board, so every copy is also audited against the live game's board snapshot, global block, players and entities by id and field, links as a multiset, and its differences printed as `fork fidelity:` lines naming entity and field — a report that keeps the fork, `ForkFidelity`); a discarded fork **still counts against its budget** (otherwise a systematically failing copy retries until the game ends); and at most **two** forks may target one real resolution — a fixed constant no flag can raise. `--probe-keywords` is the runtime switch and is deliberately separate from the build decision gate 2 drives; it names every damage-step keyword unless a run narrows or empties it.

A line whose text branches on whose turn it is (a clause carrying `ConditionPlayerTurn$` or `ConditionOpponentTurn$`, `FE/TurnConditions.java`) is forced twice a game at most: once on its holder's own turn, as every line is, and once at a boundary of another player's turn, for its holder (FR-057), where it shows its other branch. `InterventionScheduler` offers those first at each boundary, because the forced resolutions otherwise spend the whole per-game budget at the game's first boundary, under the same budgets and the per-resolution cap.

A **protection fork** (FR-058, `FE/ProtectionFork.java`) is an intervention played on: as a first main phase begins it copies the game, gives one creature a rare protection through the `keyword` operation (a card type, a creature type, a condition or everything that an opposing non-land permanent, an opposing hand card or a card attached to the creature has, spelled as `rule_outcomes.ProtectionQuality.fragment` spells it, `FE/ProtectionQualities.java`) and plays the copy to the end of the turn through `ForkPlayForward`. Every record it writes carries `interventional = true` and `fork = true`, and is of any kind, cost halves linked to their effect halves included. One a game, on a run taking interventions, drawn with probability 0.25 at each first main phase with a creature out (`ForkBudget.MAX_PROTECTION_FORKS_PER_GAME`, `ProtectionFork.PROBABILITY`): a budget of its own, because the forced resolutions spend theirs before any creature is out.

A **directed fork** is played on rather than stopped: `ForkPlayForward` begins the phase the copy was taken in (the copy sits before that phase's turn-based actions, so `PhaseHandler.onPhaseBegin` is reached reflectively) and loops `mainLoopStep` until its cleanup step leaves nothing to resolve (the next step would begin the next turn's untap step) or the game ends, with both seats choosing afresh; on stopping, the fork's bracket writes what no later event would close: the cleanup's turn-based actions and the held half, or, when the fork ended the game, everything the game's end writes (the lethal combat record and the outcome), since Forge publishes the game's end only from a match. It is recorded by a fork-bound `GameRecording` that installs no hook: the live game's `PatchedCollectors` hand every hook callback to the fork's collectors too while it plays, and each channel keeps its own game's — dispatch by game identity, because the AI evaluates on a thread of its own. The fork's lines are held and written only once it has played out, so a fork that throws leaves nothing. Its random seat is attached with draws from the game's fork seed (`GamePlayer.attachForkSeats`); nothing in a fork draws from the match's source, which would shift later games' seats. The copy carries the turn's pending state — delayed triggers, end-of-turn and leaves-the-battlefield commands, controller timestamps — through the `GameCopier` patch on `effect-record-hooks`; a command whose closure holds a reference the copy cannot map is left out rather than carried with a live reference into the real game. One known gap: the score check fails at the beginning-of-combat phase event (the evaluator reads a combat Forge has not built yet), so a fork there is always discarded, and neither the directed nor the intervention scheduler takes one there (`Forks.scoreCheckable`).

**When a directed fork is taken.** A rule is registered in `FE/directed/DirectedRules.java` as a `DirectedRule`: its rule id, the scenario whose base variant it waits for (a rule can have several scenarios, and two can share a variant label), a `BoardPrecondition` returning the `Binding` of live objects the variants act on, and per variant label an `Application` naming its `ForkOperation` and building the `BoardEdit` from the fork's binding. `DirectedRulesContractTest` checks every registration against `rules/scenarios/*.json`. Each registered rule is a class of its own in `FE/directed/rules/`, its precondition a hand-written read of the live board at a named phase boundary (`Boards` holds the shared reads), and `RegisteredRulesTest` builds each scenario's base on a `TestBoard`: the precondition binds there and not on a board missing the base, and a `GameCopier` copy edited by the variant differs from the live board by the variant's one fact. A precondition only finds the board where the rule can happen; it cannot force the live game's or the fork's decisions, so a precondition on a spell in hand (704.5f's -N/-N) holds only as long as the AI has not yet cast it. At each phase boundary `DirectedForkScheduler` (run last from `GameRecording.PhaseBridge`) asks each enabled rule that has not forked in this game for its binding, draws against `--directed-fork-probability` from a per-game generator, sorts the rules that drew a fork by the directed forks each took in this JVM's lifetime (`DirectedForkTally`, ties in `--directed-fork-rules` order) and takes them until `--directed-forks-per-game` is spent; the budget, the rule's one fork and the tally are spent when the fork is taken, before the score check. `DirectedFork` copies and score-checks the game, maps the binding into the copy, applies the edit, and only then hands the copy to `ForkPlayForward`, whose collectors start listening after the edit: the edits are silent to the rules but still publish bus events. Every record of the fork carries `aimed_at = [rule]`, `fork = true`, `interventional = false`, `directed = {variant, operation}`, and `mirror_of` only when a live record was still open at the fork point (the held resolution's half), which a phase boundary has already closed.

The supervisor's startup check is `directed_fork_error` in `sealed/infrastructure/effect_collection_flags.py`, called by `match-outcomes` and `collect-variants` (exit 1 naming the rule): a listed rule needs a detector declared in its scenarios (not `none`), a contrasting variant classified into an operation, and a registration, which one run of `DirectedRulesMain` lists; a probability outside (0, 1] is refused too. `sealed` may not import `effects`, so the check reads `rules/scenarios/` itself (`rule_readiness`), and `tests/unit/sealed/infrastructure/test_directed_fork_flags.py` pins it against `rules_catalogue_io` over the real catalogue.

The real-versus-fork difference is computed at **evaluation time** and never becomes a training target: a model trained on its own disagreements would learn to reproduce its errors rather than correct them.

## File formats

Append-only data contracts spanning the Java writers and the Python readers — no single source file teaches a whole one, and a mismatch silently corrupts a corpus that cannot easily be rebuilt.

**Effect-record shards** (`output/effects/records/{run_id}.{worker}-{lifetime}.jsonl.gz`): one JSON record per line, append-only. A shard per worker rather than one shared file because records are far larger than a match-outcome row, so concurrent appends would interleave mid-record; and a shard per worker JVM *lifetime* rather than per worker slot, because the supervisor recycles the longest-running worker every status interval and restarts crashed ones — hundreds of JVMs per run. Each file is a concatenation of complete gzip members, one per block of 256 records: every member stands alone, so a worker killed mid-write truncates the last and the reader stops there, which is the trailing-partial-line rule applied a block at a time. A gen-3 game costs about 7 MB of JSON and 350 KB gzipped (two-stage decision sampling, FR-033b, is what keeps it there), and the corpus is what fills the disk on an overnight run. Plain `*.jsonl` still reads — the corpus is append-only and older shards cannot be regenerated. Discovery **recurses**, so a depleted collection run and a full-strength one can be kept in subdirectories of `--effect-records` and still read as one corpus; anything else placed under that tree is read as corpus too. `record_id` is `{run_id}.{worker}-{lifetime}.{counter}` and `game_id` is `{run_id}.{worker}-{lifetime}.{game counter}` — both carry the worker slot because workers count independently, and the JVM lifetime because each worker JVM counts from zero and is replaced hundreds of times per run; `game_id` is the join key for a checkpoint's recorded split, so a repeated one merges unrelated games. The envelope is **frozen before the first record is collected**: a later capability makes new `kind` values reachable and adds snapshot tiers, but never redefine a field. Four compatibility rules govern that and are enforced by `tests/unit/effects/domain/test_schema_compatibility.py` rather than by a version stamp. Full schema: `specs/023-ability-effect-model/contracts/record-schema.md`, with gen 3's changes in `specs/025-ability-effect-model-gen3/contracts/record-schema-delta.md`.

**Record envelope**: `record_id` (`{run_id}.{worker}-{lifetime}.{counter}`), `generation` (gen-3: `3`, the member after `record_id`; absent before gen-3), `run_id`, `timestamp` (ISO 8601 UTC), `game_id` (`{run_id}.{worker}-{lifetime}.{game counter}` — the join key for a checkpoint's recorded split), `kind` (`resolution` | `rewrite` | `continuous` | `combat` | `trigger` | `playability` | gen-3 `turn_action`), `moment` (resolution kind only), `subkind` (playability kind only; on `turn_action` one of `draw`, `cleanup_discard`, `untap`, `phasing`, `day_night`, `lore_counter`, a record with no `ability` whose payload is its events and which no curated stratum holds), `link_id` (joins a cost half with its effect halves — one ordinarily, one per chosen mode resolution on a patched modal resolution, each acting through the mode's key; absent where a half has no partner: a mana record, the rescue record, an interventional half, and on gen-3 a triggered ability's or a copy's effect half, which nobody cast; a gen-3 cost half always carries one, and has no effect half when its item was countered), `mirror_of`, `variant_of`, `mode` (`patched` | `degraded`), `interventional` / `fork` / `synthetic`, `random_seat` (gen-2: `actor_player` is the random seat), `what_if` (gen-2 `attackers`/`blockers` only: `false` for a real declaration, `true` for an AI what-if query; legality recorded at Forge's declare steps is always `false`; gen-3 `attackers` records carry none), `aimed_at` (gen-3: the rule ids a record was collected for — every `collect-coverage` and `collect-variants` record lists its run's `--directed-fork-rules`, `[]` when it names none, and a directed fork `[rule]`; absent on every other record, which makes it natural), `directed` (gen-3 directed forks only: `{variant, operation}`, the scenario variant and the `ForkOperation` applied — `pt`, `keyword`, `colour_type`, `counters`, `tap`, `life`, `replace_card`, `remove_permanent`, `add_permanent`, `move_card`), `actor_player`, `ability` (provenance keys, a charm mode's carrying an `option` component; absent for `combat` and `playability`), `state`, `payload`. On a gen-2 `playability` record `actor_player` names the deciding player — the candidates' controller, the blockers' controller, the candidate ability's controller — where a gen-1 shard wrote the active or attacking player; this is the one named exception to the frozen schema, versioned by shard generation: a shard whose records carry `random_seat` is gen-2, one without it is gen-1 (its records read `random_seat = false`, `what_if` unknown), and every reader of a records set refuses one mixing the two. Gen-3 is a schema generation of its own: a reader takes a record's generation from `generation`, else `random_seat` (gen-2), else gen-1; relative to gen-2 a field may change meaning or go away (the contract's Gen-3 section lists each); `build-corpus`, `train-effect-model`, `evaluate-effect-model` and the probes read gen-3 only, and `rule-counts` alone reads gen-2 or gen-3, never mixed. A directed fork's flag signature is `fork = true`, `interventional = false`, `directed` set and `aimed_at = [rule]`, its `mirror_of` the live record open at the fork point, absent when none was; a protection fork's records are `fork = true`, `interventional = true`, of any kind, their cost halves linked as live ones. A `combat` payload additionally carries `probed_keyword` and `probed_entity` on a damage-step probe, naming what the fork stripped and from which creature — absent on an observed combat record. Both ids carry the worker index because workers count independently, and the lifetime because each JVM counts from zero — inside the middle segment, joined by `-`, so the number of `.`-separated segments is unchanged; corpora written before the lifetime segment existed stay readable and report an empty lifetime. **`mode`, `interventional`, `fork`, `synthetic`, `random_seat`, `what_if`, `generation`, `aimed_at` and `directed` are collection metadata and never reach the model.** A curated shard's records also carry `curation` (`natural_share`, `copies`, `drawn_rule`, `drawn_rules`, `rule_entities`), written by `build-corpus` and never on a collected shard: curation metadata the rule mask weighs a copy's outputs by, never a model input; a protection copy is a synthetic record `<record_id>~pc<i>`.

**Provenance sidecars** (`<name>.provenance.json`, beside each converted `.txt`, written by `python -m price_predictor convert`): the join between runtime Forge trait objects and converted ability lines. Converted-line ordinals cannot be the key — the converter runs one per-face bracket counter across five mixed line kinds, emits keyword-derived lines first though Forge appends them last, and merges and deduplicates relative to the runtime objects — so the key is printed provenance `(script_file, face, trait_kind, index_within_kind, option?)`, the script file including its tree, and `option` (written only when set) a charm mode's 0-based position in its root's `Choices$` (`cardsfolder` is letter-keyed, `tokenscripts` and `variant-scripts` are flat, and one filename occurs in more than one). Per rendered line: `prose_offset`, where the line's prose starts after its `kind[n]: ` prefix (zero on a continuation line of a multi-line description, which has none — recorded because cutting at the first `": "` would mis-cut such a line holding a `{T}: ` of its own; a sidecar written before the field existed is read by that cut, right for every line it holds), the provenance key list (**several** where the line merged several traits), sub-ability index paths, the trait's script API type, parameter keys and script text — the trait's whole chain, segments joined by `[SEG]` and chain labels renamed `SV1…` by position, so a charm root carries its own segment and each mode's `option` line carries the mode's key, chain and API type — and prose role spans tagged `cost` | `effect` | `trigger-condition` | `target-spec`, offsets into the prose after `prose_offset`. A trait with no text of its own, such as the implicit permanent spell on every permanent, maps to **no** line and appears in `dropped_keys`; a deduplicated or keyword-derived trait is claimed by the line that carries its text. `build-corpus` refuses a resolution record acting only through dropped keys — except a permanent spell's, whose implicit cast spell (a face's first spell trait) is dropped by design and which it keeps, keyed to the permanent's card (FR-059) — and the surface builder emits no token for one. A key **inside a declared `(face, trait_kind)` range** and in neither list **fails loudly** at the join: the sidecar does not describe the card the record was collected against. `build-corpus` refuses such a record as `unjoinable-key` and fails only past 20 of them and 0.1% of the records read, because a charm cast through Flashback produces a few legitimately (its mode keyed as the keyword trait plus an `option`). A key outside every declared range — another face, another trait kind, or an index past the last one declared for its pair — is a trait Forge attached at runtime: no line, and the record is kept. The collector (`ProvenanceResolver.indexedSlice`) counts an index over the list as the card prints it, not the live one: a line a static took away stays in its place, layer 4's land traits come from the printed type, and a trait a type change attached — Blood Moon's Mountain mana ability on a nonbasic land, Urborg's Swamp one on a Forest, which Forge lists before the Forest's own — is counted past every printed line and flagged `granted` in its card slot. Counted over the live list, such a trait would take a printed line's key. Row *i* of the ability cache corresponds to `lines[i]`. A key naming a script file with **no sidecar at all** is a different case and does not fail: the converted corpus never held that card, so the ability contributes no text. Token entities on the board do this — the collector files a token's provenance as `cardsfolder/<letter>/<sanitized token name>.txt` while tokens convert into `output/tokenscripts/` under Forge's own script filenames — and it reaches about 0.07% of records. `SidecarCache` raises `UnconvertedScript` and tallies it per script file, which is what a trainer logs: the share is small today, and a conversion that broke would raise it without otherwise changing the shape of a run. Full contract: `specs/023-ability-effect-model/contracts/provenance-sidecar.md`.

**Ability cache** (`output/effects/abilities/<tree>/…`): one `.npz` per source file holding a `float32` array of shape `(n_lines, e_dim)` under the key `e`, row-aligned with that source's sidecar (rendered lines for a converted tree, script lines for the variant tree). It lives **outside** `output/cardsfolder/` because the sealed pipeline's `encode-cards --clean` deletes every `.npz` under that tree. A variant writes `<name>.{variant}.npz` beside the shipping `<name>.npz` rather than over it.

**Dropped-event counts** (`output/effects/records/{run_id}.{worker}-{lifetime}.dropped-events.tsv`, written only under `--count-dropped-events`): append-only, one `event_type<TAB>phase<TAB>count` line per (event type, engine phase) pair per game, appended as each game ends — workers are killed, never stopped, so a count held until exit would be lost. `event_type` is the record schema's event wire name, `phase` Forge's `PhaseType` lower-cased (`none` before the game has one). Lines repeat across games and are summed by the supervisor, which skips a line cut short by a kill. Not a shard suffix, so no shard reader takes it for one.

**Selection set** (`output/effects/reports/selection-set-<corpus digest>.json`, written by `scripts/effect_knowledge_probes/run.py --freeze-probe-set --corpus DIR`): canonical JSON, `digest` a sha256 over the rest, frozen once per curated corpus and found by its digest. Per validation stratum and half (`selection` | `reporting`, the manifest's `halves`, never reassigned): the probe items (`record_id`, `game_id`, entity, label), the edit grids (cells with the rule's outcome, records), the rule tests (`fires` and `does_not_fire` records with their tag entities, balanced to `r` = 4), the deviance sample (`record_id`, `game_id`, `copy`); plus `probe_kinds`, `standard_errors` (`stratum/half/component/item`), `left_out` (item and reason, `untested` included) and `settings` (the thresholds it ran under). `train-effect-model` scores the selection halves each epoch and refuses a corpus with no set, or one frozen against another corpus or edited; `evaluate-effect-model` and the probes score the reporting halves. Contract: `specs/025-ability-effect-model-gen3/contracts/selection-set.md`.

**Keyword definitions** (`output/effects/keyword-definitions.json`): `{"<display name>": {"reminder_template", "generated_script", "formatter"}}`, keyed by display name because that is what a card's keyword line and the converted text both spell. `generated_script` is captured at Forge's keyword factory — the traits it generates, rendered as script — and is null for the engine-coded minority, which generates none. `formatter` is the simple name of the keyword's Forge `Keyword.type` class, which selects how an instance value is formatted into the template. Both surfaces expand a keyword to its reminder template; `generated_script` is still captured but neither scanned into a vocabulary nor used by any expansion. The typographic apostrophe is normalized to `'` at load.

**Variant scripts** (`output/effects/variant-scripts/`): perturbed Forge **source** scripts of both variant rounds, flat, each filed under `sanitize_card_name(<variant name>).txt`, the name `<card> Variant <first eight hex digits of the perturbed script's SHA-256>`, never rewritten once written; `loadable.lst` beside them lists the names Forge loaded, and is the only file in the tree not a variant script — the filename **is** the path its provenance key resolves to, so it cannot be derived from the source file's own stem. Each gets a sidecar from `VariantSidecarMain`, which runs the ordinary converter with the text output suppressed: a key's `index_within_kind` is the trait's position in Forge's runtime trait list, so only the parser that builds that list can number it the way a record will. The tree is therefore the one whose sidecars sit beside a *source* script rather than a converted one, and it has **no prose surface at all** — `SidecarCache.prose_for` returns None for it, and the prose surface falls back to the script.

Loaded into a worker by staging them into Forge's custom-cards directory before `FModel.initialize` — the card database is read once at startup, and a script that appears afterwards is invisible for the life of the JVM. Staging also registers every name with `VariantRegistry`, which is what makes `ProvenanceKey` say `variant-scripts/`: once loaded, a variant is an ordinary non-token card and nothing on it says otherwise.

## One pipeline, two callers

`application/surface_batching.py` turns records into the trunk's inputs (`TrunkInputs`), and both the trainer and gate 1's evaluator go through it. They have to agree exactly: when they did not — one keying the batch's encodings by prose, the other looking them up by script — the effect head trained on an all-zero `e`, every loss still fell, and the four evaluation baselines came out byte-identical to the shipping model. The encoding text therefore has **one** definition (`SurfaceBatcher.text_of`), and so do the variant masks (`SurfaceBatcher._masked`, FR-094), which are the whole difference between a baseline and the model gate 1 compares it against. `state-only` zeroes every `e`, `[ACT]`'s included. `no-state` zeroes the context abilities' `e` but keeps `[ACT]`'s, and zeroes every card and player feature and every `[GLOBAL]` input except the trailing record-kind, moment and subkind one-hots (`KIND_FLAG_WIDTH`): the average-effect control sees which ability acts and what kind of record it is, and nothing of the board. The masks zero inputs rather than drop slots, so the per-entity targets keep their shape.

`application/model_loading.py` is the other half: it rebuilds encoder, model and batcher from a saved checkpoint, the weights read by `effect_model_store.load_weights`. The `identity` baseline is the case that would break quietly — its `e` comes from a free embedding table rather than the encoder, so the table rides in the checkpoint's `extra` and a run that rebuilt it empty would score the baseline on random vectors and hand gate 1 a margin nobody earned. The table indexes texts exactly: one row per text the run's sidecars encode to (`ability_text.known_texts`), plus one shared row for any other text, such as a counterfactual copy's. Its texts are saved in the checkpoint beside the weights, and the runner rebuilds the table from them; a hashed table would let two texts share a row, which is the memorization the baseline exists to measure. Loading is strict: a model state missing anything but the training-only heads, or carrying an unexpected key, is refused rather than run at random initial weights, and the encoder and model come back in eval mode.

## Performance invariants

Six things on the hot paths are load-bearing rather than incidental, and each has a failure mode that looks like a working run.

**`e` enters the head by row index, never by value.** A training surface's `Slot.e` is an `int` naming a row of the batch's encoded-ability matrix, and `scatter_e_rows` turns rows into vectors on the device in one gather. Reading the vectors back to the host per ability slot would both stall once per slot and **sever the gradient** — the effect head's loss reaches the ability encoder through this path and no other, so a model trained that way would optimize the head against a frozen random encoder and still report a falling loss.

**Every per-field number is read back once, not once per field.** `per_entity_loss(..., report_parts=True)` returns its terms stacked on the device (`LossParts`), and `PartsMean`, the constant-predictor floor, the group norms and the head terms each read their values back with one `.tolist()`: each read synchronizes, and with some forty-five active fields a read per field stalled every validation batch that many times. The per-entity loss also scores its fields by kind rather than one by one: fields of one type and width are one call over every entity any of them is scored at, each weighted by where it is scored, which gives the field-by-field sums (`test_effect_losses.py` checks the loss, every part and the gradient against the loop), at a fraction of the loop's cost over the 300 gen-3 fields. The epoch's running loss accumulates on the device and is read once when the epoch closes.

**`encode-abilities` batches by unique text.** The corpus repeats itself heavily — every *Flying*, every *deals 3 damage to any target* — so `encode_tree` deduplicates every line of the whole tree by its encoder input (text and role spans) and `AbilityEncoderRunner` encodes the distinct inputs once, length-sorted through the same `TextStager` and `encode_by_length` path a training step uses, then copies the rows back into each sidecar's line order. It loads the checkpoint once for the whole run and calls `eval()`, which matters beyond dropout: dropout would otherwise make two runs of the same command write different caches. Noise on `e` is applied in the training batcher only, never here.

**A training step encodes its texts in length-sorted groups.** `encode_by_length` (`text_staging.py`) sorts a step's ability texts by length and encodes them `ENCODE_CHUNK` (32) at a time, each group padded to its own longest, for both the main pass and the MLM pass. Padded to the step's longest instead, one 512-token chain makes every line in the step cost 512 positions: on the gen-2 corpus four fifths of the encoder's input was padding, and the activations saved for backward overran the 8 GB card at 16 records per batch. Padding is masked out of attention, so grouping changes no output and no gradient; `test_encode_by_length.py` checks both.

**The trainer holds one shard, never the corpus.** A parsed record costs about 45 KB resident, so the corpus as it stands — 701 shards, 14M records — would need hundreds of gigabytes, and `list(read_records(...))` was an out-of-memory crash that printed nothing first because the load ran before the first log line. `load_shard` parses one shard (about a gigabyte), `_train_on_shard` takes that shard's share of the epoch's steps, and the records are released before the next shard is read. Under `--prefetch-workers N` (default 3) each worker process holds the one shard it is preparing, so a run holds `N` shards, none of them in the training process; under `--prefetch-workers 0` the training process reads each shard when its turn comes and holds only that one. The shard line reports `wait` rather than `load` because what it times is the part of reading and splitting a shard the steps before it did not hide.

Two things follow from never seeing the whole corpus at once, and each is a deliberate trade rather than an oversight. Rarity weighting reads the manifest's corpus-wide table (FR-141) rather than counting the resident shard, because a per-shard count would be actively wrong: coverage and variant shards are built dense in scarce texts on purpose, so a per-shard count would read exactly those texts as common and down-weight the records those collectors exist to supply. And the split itself is never accumulated from what a run happens to read — `build-corpus` enumerates the held-out cards and both strata's `game_id` sets once, over the whole raw corpus, and every training run reads that same enumeration whole from the manifest, so a run that stops early still records the same split as one that finishes. Validation records follow the same rule: `validation/samples/{card-disjoint,game-disjoint}.jsonl.gz` are captured once when the dataset was built and reused every epoch, because a set redrawn each epoch would make `--patience` measure which records got drawn rather than whether the model improved.

Everything else streams already (`read_records` is an iterator, `count_records` counts lines without parsing them).

**Each training step's host half is prepared in a worker process, and every draw it takes is seeded by the step's place in the run.** A step splits into a host half (`StepPreparer.prepare_training_step` in `application/step_preparation.py`, `SurfaceBatcher.prepare`): the plan, tokenizing, the surfaces and their collation, every target, the MLM mask, all CPU tensors; and a device half (`StepLossComputer.device_loss` in `application/step_loss.py`, `Materializer.materialize`): the copies, the encoder, the noise on `e`, the model, the losses, backward. The host half is pure Python and on threads it held the interpreter lock against the training step's own Python side, so `application/step_workers.py` runs it in `--prefetch-workers` spawned processes: shard `k` of the run goes to worker `k mod N`, which reads it, splits it, plans it and prepares every step onto a queue of its own (one shard's steps deep, so all `N` prepare at once); a receiver thread in the training process reads the shards back in run order, pins each step and hands it over; the epoch line's shares, the split, the unresolved-script tally and the truncation log come back as messages beside the steps. Three rules. **No `EffectRecord` crosses the boundary** — a task names a shard path and what returns is finished tensors, each step's packed into one flat buffer (`infrastructure/tensor_packing.py`), because `torch.multiprocessing` pays a shared-memory mapping per tensor and on Windows that cost is per tensor rather than per byte; pinning that one buffer, in the training process, pins the whole step. **No draw depends on where a step was prepared**: the shard's weighted shuffle draws from `plan_rng(seed, epoch, position)` and each step's keyword expansion, context dropout and MLM mask from `step_rng(seed, epoch, position, step)`, so a run is the same run under any worker count, `0` included, and `test_training_loop_workers.py` checks it bit for bit on the fixture records. And **`e` is never prepared ahead**: the encoder and the noise draw stay in the device half, or the gradient would not reach the encoder and the device generator would be read out of order. `--prefetch-workers 0` prepares each step in the training process just before its device half runs (`test_training_loop_in_process.py`). A worker never exits on its own while the run lasts, even after failing — on Windows a queued step's shared memory dies with the process that made it — so a worker's exception reaches the training process at the shard it belongs to, as the exception itself with the worker's traceback attached as a note (a `RuntimeError` carrying the traceback when it does not pickle), so the CLI maps a worker's refusal to the exit code the in-process path gives it, and the pool terminates every worker on every way out; a watchdog thread in each exits it if the training process is killed outright. Gate 1, gate 2, `model_loading` and the probes call `build`, which is the two halves back to back, in process; validation runs the same two halves through `prepare_scoring_step` and the training loop's own device half.

## Model artifacts

Checkpoints live under `models/effects/effect-model/` (`{timestamp}.pt` plus a rolling `latest.pt`); a variant writes to `models/effects/effect-model/{variant}/`, so a baseline run can never overwrite the checkpoint the cache was built from. Beyond weights, a checkpoint records **the split it trained against** (the held-out card list and both `game_id` sets, enumerated rather than derived), the vocabulary and keyword-definition paths and their content hashes, the keyword withheld from training, and — for a `--corpus` run — the curated dataset's manifest path and digest. Every inference command re-hashes what it actually loaded and fails fast on a mismatch: encoding a cache against a different vocabulary produces vectors that look fine and mean nothing, and evaluating against a corpus rebuilt since training would score the gates partly on games the model trained on. The MLM, script-API and value heads are training-only and are filtered out at save time. A checkpoint also records its encoder size (`--encoder-layers`, `--encoder-d-model`), the sidecar roots it trained against (`cards_folders`), the holdout unit, and the training settings (the seed, the noise ratio, the four loss weights, the script-API vocabularies). Every loader builds the encoder from those, so an arm at a non-default size loads without restating its flags, and a checkpoint that records no size loads at 4 layers and width 256.

`evaluate-effect-model` reads all of what a checkpoint records and recomputes none of it, because the corpus is append-only: a recomputed split would score the gates partly on games the model trained on. A gen-3 checkpoint's weights are the averaged ones, and it also records `best_control_score`, the loss denominators, `--rule-mask`, `--deviance-floor`, `--ema-epochs`, `--stratum-weight`, `--relation-values`, the manifest's `rule_map_digest` and the `selection_set_digest`; `training_settings` holds `input_layout` `gen-3` with the relation types, subtypes, named counters and closed output lists whose order fixes its tables, and a loader refuses a checkpoint whose layout or lists differ.

A training run also rewrites `resume.pt` beside its checkpoints at the end of every epoch (`effect_model_store.save_resume_state`, written to a temporary name and renamed). It is not a checkpoint. It carries the full model with the training-only heads, the optimizer, the step, the early stopper, the noise on `e`, the averaged weights (`weight_average`: `state`, None while warmup lasts, and `start_step`), the loss denominators, `best_control_score` (the stopper's best, with its state) and the CPU/CUDA generator states, which is everything a checkpoint drops. `train-effect-model --resume` (and `effect_sweep_arm.py --resume`) continues at the next epoch and trains bit for bit what the uninterrupted run would; `test_training_loop_workers.py` checks it across the curriculum switch. No other state needs saving because every draw is seeded by `(seed, epoch, position, step)`. For the same reason a resume under a different seed, corpus, size or batching is refused: every `TrainEffectModelConfig` field is compared except those in `resume_state.RESUME_MAY_CHANGE` (`--epochs`, `--patience`, `--lr-scale`, `--save-every-epoch`, `--prefetch-workers`, the output and input paths), so a new flag is checked by default — `--rule-mask`, `--deviance-floor`, `--ema-epochs`, `--stratum-weight` and `--relation-values` among them, a mismatch exiting 1. A gen-3 checkpoint also records those five flags, `best_control_score`, the manifest's `rule_map_digest` and `selection_set_digest` (the set the control score read; a resume compares it) under their own names; the relation types and their target indices ride `training_settings`. `train-effect-model` exits 1 at startup on a manifest with no per-rule counts (FR-066).

## Inputs on disk

- `output/effects/records/` — append-only effect-record shards from `sealed match-outcomes --effect-records`; the input to `effects train-effect-model`.
- `rules/` — the rules catalogue: `scenarios/<unit>.json` with each scenario's detector, variants and departure, `heads/<unit>.jsonl` the rules-to-fields map; read by `effects rule-counts`, `build-corpus` and the selection-set freeze.
- `output/effects/reports/selection-set-<corpus digest>.json` — the selection set frozen for a curated corpus; `train-effect-model` refuses to start without it.
- `output/effects/keyword-definitions.json` — Forge's keyword table, from `effects extract-keyword-definitions`; scanned by `build-vocab` and read by the encoder's keyword expansion.
- `output/effects/abilities/` — the per-ability embedding cache from `effects encode-abilities`.
- `output/effects/variant-scripts/` — perturbed Forge source scripts from `effects collect-variants`, on the script surface only and never converted to prose.
- `../forge` on its `effect-record-hooks` branch (an ordinary branch: changes land as new commits, and a Forge upgrade is merged in) — the engine hooks the collectors look up reflectively. This repo carries no exported patch copy; `PatchHooks.REQUIRED` is the inventory and is what detection reads. Unpatched, collection still runs and stamps every record `degraded`.
