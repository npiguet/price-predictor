# Checkpoints and resume state

Rules to respect when changing what a checkpoint or `resume.pt` holds, a loader, or `--resume`. The code is `infrastructure/effect_model_store.py`, `application/model_loading.py` and `resume_state`; what a checkpoint contains is specified in `specs/2026-10-30-ability-effect-model-gen3.md` § 16.

## Checkpoints

- A training run writes its checkpoints (`{timestamp}.pt` plus a rolling `latest.pt`) to `--model-output`, and under `--save-every-epoch` one `epochs/epoch-NN.pt` per epoch (NN is the training log's epoch number, from 01; there is no `epochs/latest.pt`), its run directory under `models/effects/<gen>/effect-model/`. A baseline variant trains into a model directory of its own (`effect-model-identity`, ...), which the command names, so a baseline run can never overwrite the checkpoint the cache was built from.
- A checkpoint records the split it trained against, enumerated rather than derived: the held-out card list and both `game_id` sets. No command recomputes a split, because the corpus is append-only and a recomputed one would score the gates partly on games the model trained on.
- It also records the vocabulary and keyword-definition paths with their content hashes, the withheld keyword, the curated dataset's manifest path and digest, the sidecar roots, the holdout unit, the encoder size and the training settings.
- Every inference command re-hashes what it actually loaded and fails fast on a mismatch, a hash recorded empty (no keyword file then) included: a file present now differs, and `--keyword-definitions` at a missing path is refused, never read as no definitions. Encoding a cache against a different vocabulary produces vectors that look fine and mean nothing.
- A training run takes both hashes once, at startup (`application/tokenizer_inputs.py`), carries them on its `RunSpec` and records those at every save (`latest.pt`, `epochs/` files, `resume.pt`); a file rewritten mid-run is never re-read. Startup refuses a `--keyword-definitions` that is no file and one whose hash differs from the corpus manifest's `keyword_definitions_digest` (the same sha256 of the bytes); a manifest recording none, built without a keyword table, gives nothing to compare and is warned of.
- Every loader builds the encoder from the recorded size, so an arm at a non-default size loads without restating its flags. A size the recorded encoder config leaves out is refused by name (`KeyError`).
- The MLM, script-API and value heads are training-only and are filtered out at save time.
- Every checkpoint file, `resume.pt` and `resume-best.pt` included, is written to a temporary name beside its target and moved with `os.replace` (`torch_checkpoint.write_atomically`, `copy_atomically`, also the copy that makes `latest.pt`): a kill leaves the previous file whole, and a move that fails, such as onto a file another process holds open on Windows, raises naming the target path and removes the temporary file.
- A gen-3 checkpoint's weights are the averaged ones, except in an `epochs/` file of an epoch that ended before warmup did, which holds the raw weights; `averaged` says which. It records `control_score`, the score of the epoch whose weights the file holds (a non-best `epochs/` file holds its own), beside `best_control_score`, the run's best so far (the two are equal in a best checkpoint); the evaluation prints `control_score` as `selection_control`. It records the loss denominators, `--rule-mask`, `--deviance-floor`, `--ema-epochs`, `--stratum-weight`, `--relation-values`, the manifest's `rule_map_digest` and the `selection_set_digest`. The evaluation's reporting half scores under the recorded `--stratum-weight` and `--deviance-floor` and refuses a checkpoint recording none.
- `training_settings` holds `input_layout`, `relation_target_indices` and, as `<name>_digest`, the sha256 of each name list in `domain/checkpoint_layout.LAYOUT_VOCABULARIES`, whose order fixes the model's tables: the relation types, the slot kinds, the id lists, the keyword flags, every list an input slot one-hots over, and each output head's fields with their types and classes. A loader refuses a checkpoint whose layout, cap or any digest differs ("records another `event_types` order"), and one that records no digest of a registered list ("records no `event_types` digest"): an order is never assumed. The refusal runs first on every load (`EffectModelStore.load`) and names the checkpoint's generation: no recorded `input_layout` is gen-1, `"gen-2"` is gen-2. `tokenizer_rules` (`"gen-2"`, the grammar's version label, not a generation) is required too; a checkpoint recording none is refused. The payload's members are declared once, in `effect_model_store.PAYLOAD_MEMBERS` (attribute, key, how written, how read), and `save` and `load` both walk that table: a payload missing a member raises `KeyError` naming its key, and none is read with a default. A variant's extra payload is nested under the `extra` key, so no name in it collides with a member.

## Loading

- `application/model_loading.py` rebuilds encoder, model and batcher from a saved checkpoint, the weights read by `effect_model_store.load_weights`. The trunk is built at the widths its `model_config` records and the batcher at the layout's (`model-layout.md` § Input slots), which agree on a checkpoint trained under this layout; nothing reads a width off the records being scored. Which fields a loaded model is scored on follows the classes of those records (`model_loading.evaluation_fields`).
- The `config` (model config) and `encoder_config` members are read field by field (`effect_model_store.model_config_from`, `encoder_config_from`): a field the checkpoint leaves out raises `KeyError` naming it and is never built at the dataclass's default. `EffectModelStore.load` reads the file itself, not through the shared `torch_checkpoint.load_checkpoint`.
- Loading is strict: a model state missing anything but the training-only heads, or carrying an unexpected key, is refused, and so is an empty `encoder_state_dict` (`EffectModelStore.load`, `load_weights`). Loaded leniently, the missing part would run at random initial weights. The encoder and model come back in eval mode.
- The `identity` baseline's `e` comes from a free embedding table and not from the encoder, so the table rides in the checkpoint's `extra` with its texts, and the runner rebuilds it from them. Rebuilt empty, the baseline is scored on random vectors and gate 1 gets a margin nobody earned, so an `identity` checkpoint with no `identity_table` in `extra` is refused (`model_loading._identity_table`); every other variant has no table.
- The table indexes texts exactly: one row per text the run's sidecars encode to (`ability_text.known_texts`), plus one shared row for any other text, such as a counterfactual copy's. A hashed table would let two texts share a row, which is the memorization the baseline exists to measure.

## `resume.pt`

- It is not a checkpoint. It is rewritten at the end of every epoch, atomically, and carries everything a checkpoint drops: the training-only heads, the optimizer, the step, the early stopper, the noise on `e`, the averaged weights, the loss denominators, the best control score and the generator states.
- `--resume` continues at the next epoch and trains bit for bit what the uninterrupted run would; `test_training_loop_workers.py` checks it across the curriculum switch. No other state needs saving because every draw is seeded by `(seed, epoch, position, step)`.
- A resume without `--seed` takes the resume file's seed (`resume_state.run_seed`); under a different seed, corpus, size, batching or layout digest it is refused; a `resume.pt` that records no digest of a registered list is refused by its name. Every `TrainEffectModelConfig` field is compared except those in `resume_state.RESUME_MAY_CHANGE`, so a new flag is checked by default.
- `--resume` decides under this run's patience and epochs whether anything is left, so a run that stopped early can be continued.
- A new best epoch copies `resume.pt` to `resume-best.pt` (atomically), which another run directory can continue from.
- A resume compares the selection set's digest with the one the run recorded, and `corpus_shards_digest`, the hash of the manifest's `shards` listing (`CorpusManifest.shards_digest`), which the corpus digest leaves out: a corpus rebuilt with the same decisions but other shards is refused, and so is a `resume.pt` recording none (`ResumeMismatchError`, "The resume file was written under other settings: corpus_shards_digest: resume file …, this run …").
