# Ability text: sidecars, tokenization, vocabulary and the ability cache

Rules to respect when touching provenance sidecars, the tokenizer, the vocabulary, keyword definitions, the ability cache or the variant-script tree, and when running `extract-keyword-definitions`, `build-vocab` or `encode-abilities`.

- Sidecar contract: `specs/023-ability-effect-model/contracts/provenance-sidecar.md`.
- Code: `domain/ability_tokenizer.py`, `domain/script_regions.py` (the script surface's whole-token regions), `domain/keyword_formatting.py`, the sidecar cache, and Java `ProvenanceResolver` and `VariantSidecarMain`.

## Provenance sidecars

`<name>.provenance.json` sits beside each converted `.txt`, written by `python -m price_predictor convert`. It is the join between runtime Forge trait objects and converted ability lines.

- A sidecar names no conversion. The conversion's `run.json` does: the Forge commit it converted at and a digest of its sidecars (`conversion`, `src/price_predictor/CLAUDE.md`), which every collection checks against the connector's Forge commit before it starts (`docs/collection-runs.md` § The conversion the keys join against).

- The key is printed provenance, `(script_file, face, trait_kind, index_within_kind, option?, built?)`, never a converted-line ordinal. The converter runs one per-face counter across five mixed line kinds, emits keyword-derived lines first though Forge appends them last, and merges and deduplicates relative to the runtime objects.
- `script_file` includes its tree: `cardsfolder` is letter-keyed, `tokenscripts` and `variant-scripts` are flat, and one filename occurs in more than one.
- `option` is a charm mode's 0-based position in its root's `Choices$`, written only when set.
- A line can carry several keys, where it merged several traits.
- `built` is set only on a `keyword` key and names one trait that keyword instance built: `{"kind","index"}`, the trait's kind and its position in the instance's list of that kind (`KeywordInterface.getTriggers()`, `getReplacements()`, `getStaticAbilities()`, `getAbilities()`). It is written only when set, after `option`, and Java `ProvenanceKey` and Python `ProvenanceKey` spell it alike; two keys differing only in it are different keys.
- No key is declared by two lines of one face. A keyword that prints one line declares its bare key there. A keyword that prints several (a saga's chapter lines, a dungeon's room lines, haunt's two lines) declares on each line the `built` keys of the traits that line renders, and its bare key on no line. A keyword whose script text only names SVars prints the descriptions of the triggers it built (`ability/TriggerDescribedKeyword`): a dungeon one line per room in room order (`cave entrance — scry 1.`), Prize its one line (`prize — create two treasure tokens, …`). The kind-indexed keys (`trigger n`, ...) of a keyword-built trait are declared nowhere and never emitted. How a `built` key and a bare keyword key join: the table below. A reader refuses a sidecar declaring one key on two lines of a face (`SidecarError` from `read_sidecar`, naming the file and the key): the join would have to pick a line, and picking the first read every saga chapter as chapter I. Reconvert such a tree; no reader keeps a lenient path for it.
- Java `ProvenanceRecorder.attributeKeyword` applies that rule. A description that runs onto several lines is folded into one line (`RenderedLine.appendLine`), so a Class level whose text runs on prints one line and declares its bare key there. A keyword-built trait that prints a line of its own (Tribute's unpaid-tribute trigger) declares the keyword's key with its `built` there. A multi-line keyword none of whose built traits has a line declares its bare key on its first line. The mode lines of a one-line keyword's charm (an Attraction's visit) declare its bare key with their `option`.
- A record naming only a saga's bare keyword key (one collected before the `built` member) names no chapter: acting, it resolves `AMBIGUOUS` against a reconverted sidecar and has no text. Only a record carrying a `built` key joins a chapter to its own line.
- `prose_offset` says where a line's prose starts after its `kind[n]: ` prefix. Do not cut at the first `": "`: the prose can hold a `{T}: ` of its own. A sidecar written before the fold, whose continuation lines repeat their first line's keys, is refused as declaring a key twice. A sidecar without it is refused (`SidecarError`); reconvert the tree.
- A spell prints one line (`ability/SpellLine`): its additional cost's sentence, under a `cost` role span, then every sentence of its chain in chain order, with a die roll's outcomes as unkeyed `option` lines below it. A line states each sentence once (`ability/RepeatedSentences`, which spell, activated and triggered lines share): a chain node's sentence the line already states is left out (Chill of the Grave's sub-ability restating "it doesn't untap ...", a spell description restating its additional cost), while a repeat the script writes stays, inside one description (Rally the Horde) or as a sub-ability declaring its parent's printed description word for word (Common Bond). A spell whose chain states only its additional cost prints that cost alone, keyed, with no `effect` span. A line that states only a cost declares no `spell` key; the spell cast for cleave is claimed by the spell line. An instant's or sorcery's spell whose chain states no sentence takes its text from its own `Description$`, else from the face's oracle lines that no other line of the face states (`ability/UndescribedSpellText`); with neither (a cascade card's placeholder spell), it prints no line and its key is in `dropped_keys`. An Adventure or Omen spell is keyed on its own face only, where the collector keys it by its card state. A saga chapter whose chain states nothing completes its numerals with the face's oracle line opening with them (`ability/ChapterAbility`), and an `ETBReplacement` whose effect has no description of its own prints the first oracle line its chain states (`ability/EtbReplacementAbility`, keyed with the keyword's bare key), both read through `ability/FaceOracle`. The cases: the sidecar contract § Rules.
- Role spans (`cost`, `effect`, `trigger-condition`, `target-spec`) are offsets into the prose after `prose_offset`. The line's kind picks the roles (`LineRoleSpans`): a planeswalker loyalty cost (`[+1]:`, `[0]:`) and a level cost (`{1}{B}:`) are `cost`; an additional-cost, alternate-cost or cost-reduction line is `cost` throughout; a triggered line's `trigger-condition` starts after a leading ability word (`landfall — whenever ...`), which stays untagged: on a triggered line the word is any prefix before the first ` — ` without a colon (`descend 4`, `exterminate!`). A planeswalker line's text after its cost and a chapter line are `effect`, so the delayed trigger such a line creates (`[-2]: whenever ...`, `III — whenever ...`) carries no `trigger-condition`. The first span after a cost starts at the cost's end, so the spans partition the prose except an ability word. A `Static$ True` trigger whose prose opens with `when`, `whenever` or `at` (a triggered mana ability) is a `triggered` line; any other is a `replacement` line.
- Row *i* of the ability cache corresponds to `lines[i]`.

How a key resolves, by case:

| Key | Result |
|---|---|
| Declared by a line | That line (`KeyResolution.LINE`). |
| A `built` key no line declares | As the keyword's bare key: the keyword prints one line, which holds the trait's text (a cycling ability on its cycling line). |
| A keyword's bare key no line declares, its keyword printing several lines (a saga, a dungeon, haunt) | On the board, one slot per line in line order, each read through the line's first `built` key: `ProvenanceSidecar.board_keys` decides it, `slot_lines` applies it for the surface builder and the batcher alike. Acting, `AMBIGUOUS`: no text, never the first line's, and tallied as `ambiguous` (`JoinGaps`, the corpus manifest's `join_gaps`). |
| A keyword's bare key a line declares, other lines of the keyword declaring `built` keys of it (Tribute's unpaid-tribute trigger) | On the board, that line, then each such other line in line order, one slot each (`board_keys`). Acting, the declaring line. |
| In `dropped_keys` | A trait no line states: one with no text, such as the implicit permanent spell on every permanent, or one whose text the converter does not render, such as a secondary trigger that is static. No line. A secondary trigger whose text another line of the face restates prints no line either, but its keys are claimed by that line, not dropped (`DuplicateLines`, the one place a left-out line's keys move to the line that stays; `RepeatedLines`; the sidecar contract § Rules). |
| Inside a declared `(face, trait_kind)` range, in neither list | Fails loudly: the sidecar does not describe the card the record was collected against. |
| Outside every declared range | A trait Forge attached at runtime. No line; the record is kept. |
| Names a script file with no sidecar | `UNCONVERTED`: does not fail; the ability contributes no text, tallied per script file as `unresolved`. |
| Names a source tree the run has no root for (a variant key without `--variant-scripts`) | `UNCONFIGURED_TREE`: does not fail; the ability contributes no text, tallied per tree as `unconfigured` and logged once per tree. |

- `SidecarCache.join(key) -> Joined(resolution, line)` is the one key-to-line lookup, and the one tally: every other lookup (`line_for`, `line_or_none`, `first_line`, `script_text`, `prose_for`, `resolution_of`) reads through it, and it counts every answer that yields no text (`UNCONVERTED`, `UNCONFIGURED_TREE`, `AMBIGUOUS`, `RUNTIME_ONLY`, `DROPPED`), and each in-range mismatch before raising it, in one `JoinGaps` field per case (`unresolved`, `unconfigured`, `ambiguous`, `runtime_only`, `dropped`, `undescribed`); `runtime_only` and `dropped` are expected answers, logged at info level, the rest are damage. A board line's slots come from `board_keys` (rule 3 above), each slot then joined. A count kept beside it would miss the lookups that bypass it.
- `line_text.encoding_text` is the one place that decides a line's text, in training and in the ability cache alike: two definitions would give one line two texts. A line with prose reads its prose on the prose surface and its script (else its prose) on the script surface. A line with no prose reads its script reading on either surface, and a line with neither reads the empty string.
- A script reading (`script_text.script_reading`) is the line's script opened by `[SCRIPT]`, with every free-text parameter dropped from each segment: every `...Description$`, `TgtPrompt$`, `SelectPrompt$`, `ChoiceTitle$`, `CostDesc$` and `RepeatOptionalMessage$`. A variant's perturbation rewrites one `Key$ value` and leaves these stating the original card's numbers. It takes no role spans, which index a prose the line does not have. A lethality copy of a line reading its script reading reads the edited script's reading (`lethality_counterfactuals.amount_edit`).
- `sidecar_roots` refuses two `--cards-folder` values of one source tree (`ValueError` naming both): keyed alike, one tree would shadow the other's every card.
- `build-corpus` refuses a resolution record acting only through dropped keys, except a permanent spell's, which it keeps keyed to the permanent's card.
- `build-corpus` refuses an in-range unjoinable record as `unjoinable-key` and fails only past 20 of them and 0.1% of the records read. A charm cast through Flashback produces a few legitimately.
- The no-sidecar case is mostly token entities: the collector files a token's provenance under `cardsfolder/<letter>/<sanitized token name>.txt` while tokens convert into the token tree (`tokenscripts/` beside `cardsfolder/` in a generation's `converted/`) under Forge's own script filenames. The trainer logs the tally; a conversion that broke would raise it without otherwise changing the shape of a run.
- The collector counts a trait's index over the list as the card prints it, not the live one. A line a static took away stays in its place, and a trait a type change attached (Blood Moon's Mountain mana ability on a nonbasic land) is counted past every printed line and flagged `granted`. Counted over the live list, such a trait would take a printed line's key.
- A trait a card grants itself keys to the line that granted it, and to its index only when no line is found (Java `ProvenanceResolver.keyInState`). Forge lists such a trait in the card's own live list, past the printed lines and before the keyword-built ones, where its index names no line or another one. It is one that list holds and `get...WithoutChanges()` does not, or a stack copy of one (`getOriginalAbility`): a Class level's trait, a "has ... as long as" trigger (Expedition Diviner), a manland's animated trigger (Raging Ravine) or activated ability (Lavaclaw Reaches' `Abilities$`, which leaves no back-reference to its `Animate`). The granting line is the one naming the SVar the trait was parsed from; several naming lines are accepted when they key alike, or differ only in `built`, which gives the bare key. A Class level's trait therefore keys to its `Class:N` keyword's bare key, named by the level's static and by its level-up ability.
- A keyword of a state that is not its card's printed one keys where it is printed (Java `KeywordPrinters`); numbered among that state's own keywords, it names another keyword's line. A copy's keywords (a Clone's) key into what it copied as that showed them when the copy was made, through a copy of a copy, and are printed: the original's clone states filed before the copy's, else its printed state (Java `CopyHistory`), so a later copy effect on the original (Cytoshape on the Clone's Moldering Karok) leaves the Clone's keys as it leaves its keywords (707.2). A copy effect on the original that has ended since (Cytoshape's, until end of turn, on the Grizzly Bears a Clone copied as Moldering Karok) took its clone state away, so where the walk misses the card the copy's clone states name as their printer (the patch's `CardCloneStates.getEffectRecordPrinter`, which `CardFactory.getCloneStates` sets to `Card.getEffectRecordPrinter` of the original as the copy is made and `GameCopier` carries as its counterpart), it reads that card instead: the Clone's keywords keep Karok's lines. `Card.getEffectRecordPrinter` of a copy is its latest clone states' own note, so a copy of a Clone notes what the Clone copied as of the Clone's copy: a Clone of a Clone of Moldering Karok, or Kiki-Jiki's token of it, made while Cytoshape has Karok a Grizzly Bears, keys to Karok's lines, and a copy effect on the Clone itself (Cytoshape on the Clone) is its latest clone states, whose note names what that effect copied. A keyword a copy effect added (it carries no granting static) keys to that effect's line, the copied copy's for a Clone of Dack's Duplicate; a keyword another permanent's static grants a copy (Blue Ward on a Clone, a lord's islandwalk) keys to that static, as on a creature that copies nothing. A mutated permanent's merged state keys each keyword into the merged card that brought it, the top card first, a mutated Clone's through what the Clone copied. A token or spell copy's state holds its copy effect's added keywords beside the original's, so its keywords are numbered against the face its card's rules print (`FaceOrder.printedFace`, which the converter renders faces from too), and an added one keys to no line. A token copy of a Clone (Kiki-Jiki's) is built from the Clone's card, whose rules print none of its keywords: its keywords are read through the printed state of what the Clone copied when the token was made, keyed and printed there (`KeywordPrinters.printingSourceOf`, through the patch's `Card.getEffectRecordCopySource` on the token's prototype, which `CopyPermanentEffect.getProtoType` sets to `Card.getEffectRecordPrinter` of the copied permanent), so a later copy effect on the Clone (Mirrorweave) leaves the token's keys as they were, as it leaves its keywords (707.2). A keyword the Clone's own copy effect added as an exception (707.9b: Dack's Duplicate's haste and dethrone) keys to that copy line of the Clone's own printed state, the `Clone` clause whose `AddKeywords$` lists it (`KeywordPrinters.copyClauseOf`, reaching the Clone through the patch's `Card.getEffectRecordCopiedPermanent` on the prototype); one only the token's own copy effect added (Kiki-Jiki's haste beside a plain Clone) keys to no line. A trait Forge builds on a Clone's copy state rather than parsing it (a land copy's mana ability, a copied planeswalker's loyalty replacement) keys to no line, not to the copy effect's.
- A meld half whose script does not hold the melded face (The Mightstone and Weakstone) prints it as its face 1, read from its meld partner's rules (`FaceOrder.printedFace`), as Forge's `CardFactory` reads that half's Meld state; the collector keys that state's traits as face 1 of the half's own file. Both halves of a pair print the melded face, each in its own file. A sidecar without that face leaves those keys past every declared face, runtime-only.
- A trait built by a keyword the card does not print (one a static granted) keys to the granting static's line (`ProvenanceResolver.keywordGrantor`), the card's own or another's. A keyword a resolved effect granted has no static to follow, and its traits' records say `granted_keyword` (`UnresolvedReason`).
- A dungeon's room trigger keys to its dungeon keyword in the dungeon's token script, `(tokenscripts/<dungeon>.txt, 0, keyword, 0, built = trigger i)`, the room's line. A dungeon is a token card with a script; only an effect card (`GamePieceType.EFFECT`: The Monarch, The Initiative) is engine-built, and its traits' records say `engine_effect` (`ProvenanceResolver.isScriptless`).

## The text a line encodes to

- A sidecar line's `script_text` is the whole chain of the trait that first claimed the line (root segment, a trigger's `Execute$` ability, every sub-ability, a replacement's `ReplaceWith$` ability, each result ability of a die roll, every trait a naming parameter names) joined by ` [SEG] `.
- A parameter naming SVars that hold traits (a static's `AddTrigger$`, `AddStaticAbility$`, `AddReplacementEffect$`, `AddAbility$`; Animate's `Abilities$`, `Triggers$`, `Replacements$`, `staticAbilities$`; Effect's `Abilities$`, `Triggers$`, `StaticAbilities$`, `ReplacementEffects$`; a copy's `AddTriggers$`, `AddAbilities$`, `GainTextAbilities$`, `AddStaticAbilities$`; a static's `GainTextAbilities$`) adds a segment per named SVar, in the order it lists them, with that trait's own chain (`effects/GrantedTraits`). So does each parameter naming one SVar that holds a trait Forge sets up when the trait applies or resolves: an exert cost's `Trigger$`, a mana ability's `TriggersWhenSpent$`, `PreventionSubAbility$`, `StaticEffect$`, `ExtraTurnDelayedTrigger$` and `ExtraTurnDelayedTriggerExecute$`, `ExtraPhaseDelayedTrigger$` and Forge's spelling `ExtraPhaseDelayedTriggerExcute$`. Forge builds these traits only when they apply, so without these segments a perturbed SVar of an anthem's granted trigger or a manland's animated ability reaches no line's script.
- A die roll's `ResultSubAbilities$` (`1-9:SV1,10-19:SV2,20:SV3`) renames the label after each range and adds that result's ability as a segment with its own chain (Java `TraitScript`). A die roll's outcome rows are `option` lines with no script, so its spell, activated or triggered line is the only one carrying the results.
- Chain labels are renamed `SV1…` by first appearance per line, so two cards differing only in an author's SVar name share a text.
- A charm root carries its own segment, and each mode is an `option` line with its own chain and API type.
- A charm's root line is the kind of line its root is (`ability/CharmAbility`): a modal spell's is a `spell` line, an activated charm's an `activated` (or `planeswalker`) line opening with its cost, which takes the `cost` role span. Its prose is the charm's header, never the bare continuation of one, and a charm with no description still prints it, keyed with the spell.
- Every path that prints a charm's choice (a modal spell's or activated charm's root, a trigger's `ABILITY` placeholder, a chapter, an Attraction's visit) prints one header, `ability/CharmHeader`, built as Forge's `CharmEffect.makeFormatedDescription` builds it: who chooses ("an opponent chooses"), the count ("one or both", "up to two", "any number", "X"), Forge's wording of `ChoiceRestriction$` ("that hasn't been chosen this turn"), "at random", "you may choose the same mode more than once", an activation limit, then `AdditionalDescription$`, unless that states the choice itself or the card is Spree or Tiered. An em dash closing the choice is dropped; one closing a sentence of the card's own that the modes complete stays (Common Black Removal `choose one. destroy target creature, then —`). A count only a game can work out reads as the card prints it: `CharmNum$ X` is "X" ("choose X", "choose up to X, where X is…") unless `AdditionalDescription$` opens a sentence of its own (Atlantis Attacks), and any other expression reads as its minimum ("choose one. If it was kicked, choose both instead.", "choose one or more"), "up to that many" when the minimum is 0.
- A chapter executing a charm prints its chapter line and one `option` line per mode, keyed like a trigger's.
- A trigger executing a charm prints one `option` line per mode whether or not its description holds the `ABILITY` placeholder (`ability/TriggeredAbilityEntry`), each keyed under every root key the trigger's line carries plus its `option`; a mode line missing would leave its mode key in range and in neither list.
- A line merged from several traits carries its first claimant's chain alone; a one-line keyword's line carries the keyword's own script text (`Ward:2`), unless the line is the text of a trait the keyword built, which the keyword's renderer names (`KeywordRendering.scriptTraitsOf`: an `ETBReplacement` or `etbCounter` replacement, a saga whose chapters print one line, a Visit's, Prize's or Backup's trigger, a `MayEffectFromOpeningHand` effect): that line carries the first such trait's chain, followed by the chain of each trait the renderer chains to the line (a Class level's line: its level-up ability, then the static granting what the level adds). A line of a keyword printing several lines carries the chain of the trait the renderer names for it in the same way, whichever built trait claims it first in index order (`ProvenanceRecorder.attributeBuiltTraits`): haunt's line carries the haunting trigger's chain, not that of a description-less trigger ending the haunting, and a dungeon's room line its room trigger's chain.
- A trigger or replacement whose effect Forge set directly, with no `Execute$` or `ReplaceWith$` naming it (a chapter, a haunt trigger, an ETB replacement), carries that effect's chain after its root segment, and an ability Forge chained a sub-ability below with no `SubAbility$` naming it (Backup's granted abilities below its counter) carries that sub-ability's chain (`TraitScript`), so a perturbed SVar of such a trait reaches the script surface.
- The synthetic land-mana line (`{T}: add {G}.`) stands for the mana abilities a face's basic land types build (`CardState.getLandManaForColor`) and claims their keys; a mana ability the script writes on a basic-typed land prints its own line under its own key (`FaceParser`).
- A line's prose writes the face's own name as `CARDNAME` where Forge's description writes the literal name, in its own case, as whole words (`OwnName`, applied while the face is parsed by `OwnNameScope`): the same word in another case is prose (Turn's "until end of turn"), and a face named by a creature type, keyword, keyword action or set name (Aurochs, Fear, Exile, War of the Spark), a legendary card's short name, and a match inside a longer card's or token's name (Stangg Twin) keep their words. The header's `name:` line keeps the name.
- A line break inside a description, Forge's line-break marker (a run of three or more commas: `,,,`, `,,,,,,`) included, reads as one space, and a run of blanks as one (`RenderedLine.appendLine`): a line is one ability's whole text.
- The converted `.txt` changes only on purpose: the connector's `golden-024` tests compare it byte for byte with expected text maintained by hand.

## Tokenization

- There is one grammar, `tokenize`, for both surfaces. The surface is fixed at construction from the vocabulary file's header (§ Vocabulary).
- A text opening with `[SCRIPT]` (a script reading) is read by the script surface's rules on either surface, so the prose surface splits a variant's API names and parameter keys at camel case instead of reading each as `[UNK]`. A keyword line inside it is recognised after the `[SCRIPT]` opener, so a variant's `Protection from blue` still expands with its own quality.
- A checkpoint records the tokenizer rules it trained under, and every loader picks the grammar through `tokenizer_surface`. A checkpoint that records none, or rules other than `TOKENIZER_RULES`, is refused (`UnknownRecordedVersion`).
- On the script surface camel case splits and `$` is always its own token. These stay whole: the values of `Execute$`, `SubAbility$`, `RepeatSubAbility$`, `ReplaceWith$` and `CounterType$`, segment openers, every renamed chain label (`SV#`) wherever it stands (after `AddTrigger$`, `Trigger$`, `ResultSubAbilities$`'s `range:` and any other parameter the converter follows; `domain/script_regions.py` `_CHAIN_LABEL_RE`), and `Choices$` items of the five chooser APIs (`Charm`, `GenericChoice`, `AssignGroup`, `VillainousChoice`, `Vote`). Elsewhere `Choices$` is a selector.
- A keyword line expands by its display name, filled through `domain/keyword_formatting.py`, which mirrors Forge's per-`Keyword.type` formatting.
- On the prose surface a parameterised keyword line is recognised by `KeywordExpander.line_of` as the line is printed (`ward {2}`, `protection from red`, `hexproof from black`): a run of cost symbols or a `from` quality after the name, read back to Forge's `details` (`{W/B}` as `W/B`), so it expands with its values and `hexproof from black` never reads as plain hexproof. Other prose that merely starts with a keyword name is no keyword line.
- `domain/keyword_formatting.py` reads Forge's hybrid and Phyrexian shard spellings (`WB`, `WP`, `BGP`, `CW`) as `{W/B}` and so on, and joins several ward costs as `Lang.joinHomogenous` does: `a`, `a or b`, `a, b or c`.
- Validation, evaluation and the cache expand at `INFERENCE_KEYWORD_EXPAND_P = 0`, so only unknown keywords expand there.

## Keyword definitions

- The keyword-definition file `extract-keyword-definitions --output` writes is keyed by display name, because that is what a card's keyword line and the converted text both spell.
- The encoder expands an unknown keyword unconditionally. This file is what makes a set the vocabulary predates readable rather than a bare `[UNK]`.
- Both surfaces expand a keyword to its reminder template.
- `load_definitions` reads a file: an absent path, or none (`None`), is no table, since a checkpoint trained before the table existed recorded none; a directory is refused (`FileNotFoundError` naming it). The freeze's scoring step (`selection_deviance.scoring_targets`) passes none: it reads targets only, which the table does not change.

## Vocabulary

- `build-vocab` scans three sources: converted cards, converted token scripts and the keyword-definition file. Unscanned reminder text would expand to `[UNK]`, so `--keyword-definitions` at a path with no file is refused (`FileNotFoundError` from `load_definitions`, exit 1, before any vocabulary is written), never read as no definitions.
- Both surfaces also stage the sidecars' script lines and API types (`build_vocab.staged_lines`): the script surface as written, counted before the prose so a truncation drops prose first; the prose surface as script readings, the text a line with no prose reads, counted after the prose. Without them a variant's every API name and parameter key reads `[UNK]` on the prose surface.
- The multi-word keywords of the vocabulary are derived from the keyword definitions' names (`price_predictor.domain.keyword_tokens.multi_word_keywords`: a name with a space or hyphen, lower case, apostrophes dropped, spaces and hyphens as `_`), so `Beam me up`, `Jump-start` and `Web-slinging` are `beam_me_up`, `jump_start` and `web_slinging`; the tokenizer's merge step joins `jump - start` into `jump_start`. A build given no definitions seeds `MULTI_WORD_KEYWORDS` (`price_predictor.application.build_vocabulary`) instead. A vocabulary built before this derivation lacks the three tokens and must be rebuilt to merge them; a rebuilt one shifts the ids after them, so it is not interchangeable with the checkpoints and ability caches of the old one.
- `[PAD]`, `[UNK]`, `cardname`, `[MASK]`, `[CLS]`, `[SEG]` and `[SCRIPT]` are seeded at low ids so `--target-size` cannot truncate them away. So are every template word and, on both surfaces, the staged lines' `sv1…svN`, every key part and every part of an API name, trigger or static mode and replacement event, and the build fails when a definition would expand to `[UNK]`.
- Set codes are not seeded: an ability line never names a set.
- The vocabulary file's line 0 is its header, `# effects vocabulary, surface: prose` (or `script`), and line `n + 1` is token id `n` (`infrastructure/vocabulary_file.py`). Every reader takes the surface from the header (`vocabulary_surface`, `read_vocabulary`) and from nothing else, whatever the file is named. A file without the header is refused (`VocabularyHeaderError`, naming the file); rebuild it with `build-vocab`. The header takes the line where the price and sealed vocabularies hold `[PAD]`, so neither package's loader reads the other's file.
- The two surfaces' vocabularies are two files, so a script-surface rebuild never overwrites the vocabulary a prose-surface checkpoint recorded and can still load against.

## Ability cache

- The cache directory (`encode-abilities --output-root`, a `cache` run named after the checkpoint's run) holds under `<tree>/…` one `.npz` per source file, a `float32` array `(n_lines, e_dim)` under the key `e`, row-aligned with that source's sidecar.
- `encode-abilities` computes it once, offline; every downstream consumer reads the cache rather than the encoder.
- `--variant` resolves the checkpoint and the output suffix together, so a baseline is never encoded with another variant's weights and never lands on the shipping cache. A variant writes `<name>.{variant}.npz` beside the shipping file.
- The `taxonomy` variant has no encoder and emits a hash embedding into the same row layout, so every geometry check reads one file shape. A keyword line has no sidecar line, so it hashes the one fixed feature `keyword line` (`KEYWORD_LINE_FEATURE`), whether it is staged for training or written to the cache.
- The vocabulary and keyword-definition hashes are checked against the checkpoint before anything is written.
- `--variant identity` and `--variant state-only` are refused, exit 1 (`UnencodedVariantError`): neither model reads the encoder's output (identity's `e` is the free table its checkpoint carries, state-only zeroes every `e`), so the evaluation reads them through `--variant-checkpoint` alone.
- Each variant's cache has a stamp at the cache root, `ability-cache.stamp.json` (`ability-cache.{variant}.stamp.json` for a baseline; `ability_cache_layout.stamp_path`): a `CacheStamp` of the checkpoint file's sha256, the vocabulary's encoding surface, the checkpoint's recorded `vocab_hash` and the converted trees' sidecar digest (`SourceTrees.converted_sidecar_digest`, `--cards-folder` alone). `encode-abilities` removes it before the first cache file is written and writes it, atomically, after the last, so a run cut short leaves a cache with none.
- Every reader opens a cache through `ability_cache_store.require_cache_stamp`, which refuses (`CacheStampError`, exit 1 from `evaluate-effect-model`) a variant's files with no stamp, or a stamp differing from the reader's checkpoint, naming both values of each member; a root holding none of the variant's files needs none. Row counts alone would let a cache another arm, surface, vocabulary or conversion wrote pass for this checkpoint's. A baseline's cache is compared with that baseline's checkpoint and refused without one, except the taxonomy cache, compared on everything but the checkpoint hash, since no weights enter it. The readers: the evaluation (`evaluate_effect_model.cache_store`), the embedding probes (`common.require_cache_stamps`) and the knowledge probes (`common.checked_cache`).

## Variant scripts

- The variant tree (`--variant-scripts`, one `inputs` run directory every variant run of a generation extends) holds the perturbed Forge source scripts, flat. The filename is the path a variant's provenance key resolves to, so it cannot be derived from the source file's stem. The name is `sanitize(card name)` alone, with no `a-` case: a variant of `A-Acererak the Archlich` is `a_acererak_the_archlich_variant_<digest>.txt`, as `write_variant` writes it, `ConvertedCardLocator(tree="variant-scripts")` reads it and `CardFilenames.variantScriptFile` keys it (an ordinary rebalanced card keeps Forge's `a-` stem). `loadable.lst` is the only file in the tree that is not a variant script.
- A script with more than one face is not eligible: `is_multi_face` tests both separators, `ALTERNATE` and `SPECIALIZE:` (Specialize cards), and `renamed_script` rewrites only the first `Name:` line.
- Each variant gets its sidecar from `VariantSidecarMain`, which runs the ordinary converter with the text output suppressed. A key's `index_within_kind` is the trait's position in Forge's runtime trait list, so only the parser that builds that list can number it the way a record will.
- The tree has no prose surface: `SidecarCache.prose_for` returns None for it, so its lines read their script reading on either surface (§ The text a line encodes to). A converted tree's lines all have prose.
- Variants are staged into Forge's custom-cards directory before `FModel.initialize`. The card database is read once at startup, and a script that appears afterwards is invisible for the life of the JVM.
- Staging registers every name with `VariantRegistry`, which is what makes `ProvenanceKey` say `variant-scripts/`. Once loaded, a variant is an ordinary non-token card and nothing on it says otherwise.
