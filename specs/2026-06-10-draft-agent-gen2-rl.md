# Draft agent — RL self-play fine-tuning (generation 2)

This spec is **normative** — it specifies *what* to build and *how it behaves
from the outside*: the new training capability, the self-play generation loop,
the command-line surface and user-visible output, and the on-policy RL update
contract. It deliberately stops short of an implementation manual — internal
component design, module layout, and the step-by-step build plan come later via
speckit. Design rationale and rejected alternatives live in
[`../experiments/2026-06-10-draft-agent-gen2-design.md`](../experiments/2026-06-10-draft-agent-gen2-design.md).

It is the RL fine-tuning capability deferred by
[`2026-05-28-draft-agent.md`](2026-05-28-draft-agent.md) (which trained the
two-headed agent offline and left "RL fine-tuning of the policy" to gen 2), and
it consumes the self-play corpus produced by
[`2026-06-04-draft-agent-live-play.md`](2026-06-04-draft-agent-live-play.md)
(which lets a trained agent pilot live seats and emit `drafts.jsonl`).

**Generation convention** (the agent lineage, not a phase number): **gen-0** is
the Forge AI; **gen-1** is the offline imitation+critic agent
([`2026-05-28`](2026-05-28-draft-agent.md)); **gen-2** is the first agent trained
by this spec — the gen-1 weights fine-tuned by RL on self-play rollouts. The same
machinery produces gen-3 from gen-2, and so on; "gen-2" below means "the next
generation" generically.

# 1. What this feature does

Fine-tune the trained draft agent with **on-policy actor-critic reinforcement
learning** on its own self-play rollouts, so the policy improves *past* the
imitation ceiling gen-1 reached — letting the **critic's advantage steer the
picks** instead of only imitating Forge.

A training run:

- starts from a **reference checkpoint** (gen-1, or the current champion),
  warm-starting both the actor (policy) and the critic;
- consumes a self-play corpus generated by that same checkpoint (via the
  live-play command);
- updates the policy by a policy gradient weighted by **GAE advantages** from the
  critic, **anchored to the reference policy by a KL penalty**;
- writes a **new agent checkpoint** (the next generation).

Iterating this — generate, train, evaluate, promote — is the self-play loop
(§ 5). The deliverable is a trained gen-2 checkpoint that beats gen-1 (and Forge)
on a cross-generation evaluation yardstick (§ 6).

# 2. Scope

**In scope:**

- A new training command that performs the on-policy actor-critic update from a
  self-play corpus + its generating checkpoint, and writes a new generation's
  checkpoint (§ 4, § 7).
- The on-policy RL update contract: how a recorded corpus is turned into
  per-pick advantages and the policy/critic/entropy/KL loss (§ 4).
- A **cross-generation evaluation yardstick** (a fixed-mix, randomly co-seated
  run) and the comparison + promotion rule it supports (§ 6).
- The operator-driven self-play loop that chains live-play generation, this
  trainer, and evaluation across generations (§ 5).

**Out of scope (later specs / unchanged):**

- The model architecture, the typed-token state representation, the recency
  scheme, the `.npz` embedding cache, and the `drafts.jsonl` schema — all
  **unchanged** from gen-1 / live-play.
- The live-play rollout mechanism itself (`generate-draft-data --agent-checkpoint`)
  — **reused as-is** to produce rollouts; this spec adds no new data-generation
  path.
- Using the critic head *inside* a live draft to pick — the policy alone selects
  during rollouts; advantages are computed **after** the draft, from the corpus.
- A fully **automated** multi-generation loop — this spec produces one new
  generation per operator-run cycle; chaining is operator-driven (as live-play
  left it).
- The Bradley-Terry temperature fit and the product ("beat the whole pod")
  objective — the reward stays the gen-1 pod-relative **mean** form; the product
  objective is a future option, noted in the rationale.
- Joint encoder fine-tuning (Phase B analogue) and any change to the picker /
  scorer.

# 3. How it works (overview)

```
   freeze reference checkpoint πₖ  (gen-1 the first cycle, the champion thereafter)
            │
            ▼
   generate-draft-data --agent-checkpoint <label>=πₖ --pick-mode sample …
            │  self-play rollouts: πₖ pilots seats vs Forge + a random-bot minority
            ▼
   output/draft/drafts-genK.jsonl   (unchanged schema; one corpus per cycle)
            │
            ▼
   train-draft-agent-rl --checkpoint πₖ --drafts-path drafts-genK.jsonl …
            │  recompute logπ, V, GAE advantages from the corpus + πₖ
            │  KL-anchored policy-gradient + value + entropy update
            ▼
   models/draft/agent/{timestamp}.pt   ← candidate πₖ₊₁
            │
            ▼
   evaluate on the cross-generation yardstick (§ 6) → promote πₖ₊₁ if it beats πₖ → repeat
```

The crucial property is that **the trainer never runs inside the Forge draft
loop**. The live-play corpus already records every seat's full pick sequence and
which agent piloted it, and the gen-1 state reconstruction (`build_state` /
the online tracker) rebuilds the exact typed-token state at any
`(seat, pack, pick)`. So given the checkpoint **that generated the corpus**, the
trainer recomputes — in a batched post-rollout pass — the behaviour log-probs,
the critic values, and hence the advantages. Live play (019) is unchanged; the
only new code is the trainer and the loop orchestration.

**The core correctness property** (on-policy pairing): the policy gradient is
genuine only when the corpus was produced by the checkpoint passed as
`--checkpoint`, at the temperature passed as `--rollout-temperature`. This
pairing is an **operator responsibility** — the corpus stores no
generating-checkpoint provenance (operator convention only, § 8), so the trainer
does **not** hard-reject a mismatched corpus. As a safeguard it recomputes the
behaviour log-probs from the reference checkpoint at the rollout temperature and
**warns** when picks look anomalous under that distribution (a possible
wrong-checkpoint/wrong-temperature pairing), then proceeds regardless. A run
trains the policy gradient **only** on the corpus passed as `--drafts-path`.

# 4. The RL update contract

This is the primary review surface. Inputs: a reference checkpoint (warm-start +
KL anchor) and a self-play corpus generated by it.

**Per learner seat, per pick `t`** (a "learner seat" is one whose mix label is in
the `--learner-agents` whitelist — the generation being trained; § 7):

| Quantity | Definition |
|----------|------------|
| state `sₜ` | the typed-token state at `(seat, pack, pick)`, reconstructed exactly as gen-1's loader builds it (§ 1, § 3 of the gen-1 spec). |
| action `aₜ` | the card recorded as taken at this pick. |
| behaviour log-prob `bₜ` | `log πref(aₜ | sₜ)` under the generating checkpoint at the **rollout** temperature (recomputed; not stored in the corpus). Used only for the § 3 on-policy anomaly **warning**, not the gradient. |
| value `V(sₜ)` | the current critic on `sₜ`. |
| reward `R` | the seat's **pod-relative leave-one-out** `deck_score` — `deck_score_seat − mean({other non-failed seats' deck_score})` — the same terminal reward gen-1's critic regressed (§ 4.2 of the gen-1 spec). Mean form (expected match wins); the product objective is out of scope here. |
| return / advantage | `Gₜ` (discounted-to-terminal return; draft reward is terminal so `Gₜ = R`) and the **GAE(λ)** advantage `Aₜ` computed from `V` and `R`. |

**Loss** (per learner pick, averaged):

```
L =  − ρₜ · Aₜ                          policy gradient
  +  value_weight · MSE(V(sₜ), Gₜ)      critic regression toward the return
  −  entropy_coef · H(π(·|sₜ))          exploration bonus
  +  kl_coef · KL(π(·|sₜ) ‖ πref(·|sₜ)) anchor to the reference policy
```

- `ρₜ = log π(aₜ|sₜ)` is the policy-gradient weight. The behaviour log-prob `bₜ`
  is **not** a gradient input under on-policy REINFORCE; it is recomputed only to
  **warn** when the corpus looks off-policy for this checkpoint/temperature (the
  § 3 safeguard), never to block training.
- The **policy-gradient term uses only the on-policy corpus** (the one
  `--checkpoint` produced). Earlier generations' corpora may be supplied as
  **critic-only** coverage (`--critic-corpus`, § 7): they contribute to the value
  regression and preserve low-end / bad-region coverage, but never to the policy
  gradient.
- The critic regresses on the policy's own rollouts, so it predicts `V^π`.
- Optimisation reuses gen-1's conventions: AdamW, per-group max-norm clip,
  linear-warmup-then-constant LR, and early stopping. Because the corpus is fixed
  and a candidate's true strength is judged externally by the yardstick (§ 6),
  in-run best-checkpoint selection and early stopping use the **held-out RL
  objective** (the same `L` above evaluated on a held-out split of the corpus) as
  a guard, not a strength measure. `kl_coef` and `entropy_coef` follow a schedule
  (heavier early, relaxed as the critic proves out).

**Failure / integrity.** A learner seat with a failed build (`deck = []`,
`deck_score = null`) is excluded from the reward, the pod mean, and the gradient
(as in gen-1). On-policy pairing is the operator's responsibility: the corpus
carries no generating-checkpoint provenance (operator convention, § 8), so a
mismatched corpus is **not** auto-rejected — the § 3 anomaly warning is the only
safeguard.

# 5. Self-play generation loop

One **cycle** = one new generation, operator-driven:

1. **Freeze** the reference checkpoint `πₖ` (gen-1 the first cycle; the current
   champion afterward).
2. **Generate** a self-play corpus with the existing live-play command, `πₖ`
   piloting one or more seats against Forge and a **minority of random bots**
   (via `--agent-mix`), in `--pick-mode sample` for exploration, seeded for
   reproducibility. One corpus file per cycle (e.g. `drafts-genK.jsonl`).
3. **Train** `πₖ₊₁` with `train-draft-agent-rl --checkpoint πₖ --drafts-path
   drafts-genK.jsonl` (§ 4, § 7).
4. **Evaluate** `πₖ₊₁` against the cross-generation yardstick (§ 6).
5. **Promote** `πₖ₊₁` to champion iff it beats `πₖ` beyond noise; otherwise keep
   `πₖ` and adjust (more data, schedule, λ/KL). Repeat from 1.

The loop is **operator-run scripts** around `generate-draft-data`,
`train-draft-agent-rl`, and the evaluation — no automated daemon (mirroring
live-play's "chaining generations is operator-driven"). The random-bot minority
is retained **every** cycle for low-end critic coverage; old corpora are kept for
critic coverage, never concatenated into the policy gradient (§ 4).

# 6. Evaluation: cross-generation yardstick + promotion

Generations are compared by mean `deck_score`, on a **single evaluation run with
one fixed agent mix** holding every generation being compared (the candidate,
gen-1, Forge, and the random-bot minority), each **randomly co-seated** into pods
over a large pod count:

- The metric is the **per-agent mean `deck_score`** (raw, on the frozen scorer's
  absolute scale).
- A candidate is **promoted** only if its mean beats the current champion's beyond
  the run-to-run noise band.

Composition across generations (creature count, colour balance, curve) can be
inspected with `analyze-generated-decks` (descriptive only).

# 7. CLI

A new subcommand `train-draft-agent-rl` on `python -m draft`. Rollout generation
reuses the unchanged `generate-draft-data` (§ 5 of the live-play spec).

| Flag | Default | Meaning |
|------|---------|---------|
| `--checkpoint` | _(required)_ | The reference checkpoint: warm-starts actor + critic, is the KL anchor, **and** is the policy that must have generated `--drafts-path` (on-policy requirement). |
| `--drafts-path` | _(required)_ | The on-policy self-play corpus generated by `--checkpoint`. The sole source of the policy-gradient term. |
| `--critic-corpus` | _(none; repeatable)_ | Additional (off-policy) corpora used for critic regression / coverage only — never the policy gradient. |
| `--learner-agents` | _(required)_ | Whitelist of mix labels whose seats are the policy being trained (the generation's own label). Other seats (Forge, random bots) supply critic coverage only. |
| `--gae-lambda` | `0.95` | GAE λ (near 1 leans on Monte-Carlo, matching the gen-1 critic target). |
| `--kl-coef` | _(scheduled; nonzero)_ | Coefficient of the KL anchor to `--checkpoint`'s policy. |
| `--entropy-coef` | _(scheduled)_ | Entropy-bonus coefficient. |
| `--value-weight` | `1.0` | Critic-regression coefficient. |
| `--rollout-temperature` | _(required; no default)_ | The temperature the corpus was generated at; all policy distributions use it. The corpus stores no temperature (§ 8), so it must be supplied and positive — required (not defaulted to 1.0) so a forgotten flag fails fast instead of silently training an off-policy gradient. |
| `--lr`, `--warmup-frac`, `--batch-size`, `--max-grad-norm`, `--epochs`, `--val-fraction`, `--evals-per-epoch`, `--patience`, `--lr-decay-*` | _(gen-1 defaults)_ | Same optimisation/validation knobs and semantics as `train-draft-agent`. |

A run validates at startup: `--checkpoint` exists and its architecture matches
the `.npz` width; `--learner-agents` is non-empty; and `--rollout-temperature`
is supplied and positive. On-policy pairing of `--drafts-path` to `--checkpoint`
is not validated (no stored provenance, § 8) — it is the operator's
responsibility, with the § 3 anomaly warning as the only safeguard. Failures
exit nonzero with a clear message.

# 8. Records and artifacts

- **Rollout corpora** are the **unchanged** `drafts.jsonl` (live-play § 7) — no
  schema change at all, no provenance field. On-policy pairing is kept
  unambiguous by **operator convention** (e.g. a per-cycle corpus filename such
  as `drafts-genK.jsonl` plus the existing per-run `run_id`); the trainer does
  not read or verify a stored generating-checkpoint id (§ 3, § 4).
- **Checkpoints** are written to `models/draft/agent/` as `{timestamp}.pt` +
  `latest.pt`, in the gen-1 agent checkpoint format (trunk + policy + critic +
  recency/context tables, `config`, `epoch`, `best_val_loss`), with added RL
  metadata: the generation index, the reference-checkpoint identity, and the RL
  hyper-parameters (`algorithm`, `gae_lambda`, `kl_coef`, …) so a checkpoint is
  self-describing for the next cycle. No encoder weights (Phase A only).

# Out of scope

- Automated, unattended multi-generation training (the loop is operator-driven).
- Live in-draft use of the critic to pick (the policy alone picks during
  rollouts; advantages are post-hoc).
- The Bradley-Terry temperature fit and the product-of-`P(beat i)` objective
  (reward stays the gen-1 pod-relative mean).
- PPO (clipped-ratio, multi-epoch corpus reuse) — a future sample-efficiency
  upgrade; gen-2 uses REINFORCE + a GAE baseline.
- Surgical pack-2 forking / vine advantage estimation (an optional later
  sharpener; GAE is the estimator here).
- Joint encoder fine-tuning, picker/scorer changes, and any `drafts.jsonl`
  schema change (on-policy pairing is by operator convention, not a stored
  provenance field).
- Shipping the agent into the Forge client (TorchScript/ONNX) — a separate
  deployment concern.
