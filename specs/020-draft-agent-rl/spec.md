# Feature Specification: Draft Agent — RL Self-Play Fine-Tuning (Generation 2)

**Feature Branch**: `020-draft-agent-rl`  
**Created**: 2026-06-13  
**Status**: Draft  
**Input**: User description: "create a new feature based on the description in ./specs/2026-06-10-draft-agent-gen2-rl.md"

## Overview

The draft agent today is a generation-1 model: a two-headed (policy + critic) network trained **offline** to imitate Forge AI's picks while a critic estimates each seat's eventual deck quality. Imitation caps the agent at "as good as Forge". This feature adds the capability deferred by gen-1: **reinforcement-learning fine-tuning on the agent's own self-play rollouts**, so the policy can improve *past* the imitation ceiling by letting the critic's advantage signal steer picks rather than only copying Forge.

The deliverable is an operator-runnable training capability that turns one self-play corpus (already producible today by a trained agent piloting live draft seats) plus the checkpoint that generated it into a **new generation** of the agent — a candidate that, once it beats its predecessor on a cross-generation yardstick, becomes the next champion. Iterating "generate → train → evaluate → promote" is the self-play loop.

**Generation convention** (agent lineage, not a phase number): gen-0 is Forge AI; gen-1 is the offline imitation+critic agent; gen-2 is the first agent this feature trains (gen-1 weights fine-tuned by RL on self-play). The same machinery produces gen-3 from gen-2, etc. — "gen-2" below means "the next generation" generically.

## Clarifications

### Session 2026-06-13

- Q: How is the on-policy pairing between a corpus and its generating checkpoint recorded/verified? → A: Operator convention only — no corpus schema change; the trainer trusts the supplied `--checkpoint`/`--drafts-path` pairing and does not auto-reject a mismatched corpus.
- Q: The trainer runs offline on a fixed corpus, so true strength is judged externally by the yardstick — what selects the in-run "best" checkpoint / drives early stopping? → A: The held-out RL objective (policy + value + entropy + KL sum on the validation split), reusing gen-1's val-loss/early-stop plumbing; in-run selection is only a guard.
- Q: What happens when the on-policy gating check finds the recomputed behaviour distribution diverging from the recorded sampling distribution? → A: Warn and continue — log anomalous picks (a possible wrong-pairing signal) but never abort; on-policy correctness is the operator's responsibility.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Fine-tune a new generation from a self-play corpus (Priority: P1)

An operator has a frozen reference checkpoint (gen-1, or the current champion) and a self-play corpus that this exact checkpoint generated. They run one training command, passing the checkpoint and the corpus, and receive a new candidate checkpoint whose policy has been updated by an on-policy actor-critic step (advantage-weighted policy gradient + critic regression + entropy bonus + KL anchor to the reference policy).

**Why this priority**: This is the core deliverable — the RL update itself. Without it there is no new generation. Everything else (the loop, the yardstick) exists to feed or judge this step. It is a viable standalone MVP: an operator can run it once on a hand-made corpus and inspect the resulting checkpoint.

**Independent Test**: Provide a reference checkpoint and a small corpus generated by it; run the trainer; confirm it produces a well-formed new checkpoint that is loadable, carries RL metadata identifying its reference and generation, and reports a decreasing training objective over epochs on a held-out split.

**Acceptance Scenarios**:

1. **Given** a reference checkpoint and an on-policy corpus it generated, **When** the operator runs the RL trainer with that checkpoint and corpus, **Then** the system produces a new candidate checkpoint warm-started from the reference, applies the advantage-weighted policy update only to the learner seats' picks, and writes the checkpoint with RL metadata (generation index, reference identity, RL hyper-parameters).
2. **Given** the same inputs, **When** training runs, **Then** the policy gradient is computed only from the on-policy corpus while the critic regresses toward each learner seat's pod-relative return, and a held-out split is used to select the best checkpoint and drive early stopping.
3. **Given** an invalid startup configuration (missing reference checkpoint, architecture/embedding-width mismatch, empty learner whitelist, or no available rollout temperature), **When** the operator runs the trainer, **Then** it exits with a nonzero status and a clear message before training. (A corpus generated by a *different* checkpoint is not auto-rejected — on-policy pairing is the operator's responsibility — but anomalous picks under the reference checkpoint are warned about; see scenario 4.)
4. **Given** a corpus whose recorded picks look anomalous under the reference checkpoint (e.g. the reference assigns near-zero probability to a recorded action, a possible wrong-pairing signal), **When** the trainer recomputes behaviour distributions, **Then** it logs a warning summarizing the anomalies and proceeds to train (it does not abort).
5. **Given** learner seats whose draft produced a failed deck build, **When** advantages and rewards are computed, **Then** those seats are excluded from the reward, the pod mean, and the policy gradient.

### User Story 2 - Compare generations and decide promotion (Priority: P2)

An operator has a candidate checkpoint from User Story 1 and wants to know whether it is actually better than the current champion (and better than Forge). This is an **evaluation procedure assembled entirely from existing commands — no new code**: the operator runs one self-play data-generation pass in greedy (deterministic, no-temperature) mode with a single fixed agent mix that co-seats the candidate, the prior champion, Forge, and a random-bot minority into shared pods across many drafts, then runs the existing deck-composition analysis once per agent to read each generation's mean deck quality and makes a manual, noise-aware promotion judgment.

**Why this priority**: Without an apples-to-apples yardstick, an operator cannot tell improvement from noise, and promotion would be guesswork. It depends on US1 producing a candidate but is independently demonstrable on any two checkpoints, and it ships as an operator convention over commands that already exist.

**Independent Test**: Take any two checkpoints (e.g. gen-1 and a candidate), run the greedy fixed-mix data-generation pass followed by the per-agent analysis, and confirm the report gives a per-agent mean deck-quality score on one shared absolute scale, plus a clear "beats / does not beat beyond noise" verdict for the candidate vs the champion.

**Acceptance Scenarios**:

1. **Given** a candidate, the champion, Forge, and a random-bot minority in one fixed agent mix, **When** the operator runs the data generator in greedy mode and the per-agent analysis, **Then** every agent is randomly co-seated across a large pod count (so each faces the same opponent distribution and the opponent-strength confound cancels) and the report shows each agent's raw mean deck-quality score on the same absolute scale.
2. **Given** the yardstick report, **When** the operator inspects the per-agent means, **Then** they make a manual promotion judgment (the system does not auto-promote) — keeping the candidate as the new champion only if its edge over the incumbent looks convincing against run-to-run noise.
3. **Given** the evaluation procedure, **When** it is run, **Then** it uses only the existing data-generation and deck-composition-analysis commands (it introduces no new evaluation engine).

---

### User Story 3 - Run an operator-driven self-play cycle (Priority: P3)

An operator wants to advance the agent one generation end to end: freeze the reference, generate a fresh self-play corpus with it, train a candidate, evaluate it, and promote on their judgment — then repeat from the new champion. This is a **manual runbook, not an orchestration deliverable — it introduces no new code**: the generation step is the existing data-generation command run with the appropriate parameters (sample mode, the reference checkpoint in the mix), the train step is User Story 1's trainer, the evaluate step is User Story 2's procedure (existing commands), and promotion is the operator's manual decision.

**Why this priority**: This ties US1 and US2 into the repeatable cycle that actually grows the lineage. It is lower priority because there is nothing new to build for it — every step is either an existing command run with the right parameters or User Story 1's trainer, sequenced by hand. Each cycle step is already independently usable.

**Independent Test**: Following a documented runbook, an operator can complete one full cycle — freeze, generate, train, evaluate, promotion decision — using only existing commands plus the US1 trainer, with no orchestration script and no hand-editing of corpus or checkpoint files, and end with a clearly identified champion (new or retained).

**Acceptance Scenarios**:

1. **Given** a champion checkpoint, **When** the operator runs the cycle, **Then** the corpus is generated by that frozen checkpoint with exploration sampling against Forge and a random-bot minority, the candidate is trained only on that corpus (older corpora used only for critic coverage), the candidate is evaluated on the yardstick, and the operator manually decides whether to promote the candidate based on that comparison.
2. **Given** a candidate that fails to beat the champion, **When** the cycle completes, **Then** the incumbent champion is retained and the operator is left able to adjust (more data, schedule, λ/KL) and rerun.

### Edge Cases

- **Off-policy corpus**: the corpus's generating checkpoint differs from the reference. The trainer cannot auto-detect this (no provenance is stored — pairing is an operator convention), so it does not hard-reject; it warns on anomalous picks and proceeds. Avoiding off-policy training is the operator's responsibility.
- **Mismatched rollout sampling settings**: the rollout pick-mode/temperature used to recompute behaviour distributions differs from what the corpus was actually drawn at → behaviour probabilities are wrong; the trainer warns on the resulting anomalies but still proceeds. The operator must supply the correct rollout temperature (or rely on the value read from the corpus).
- **Failed builds among learner seats**: seats with an empty deck / null score must drop out of reward, pod mean, and gradient without aborting the run.
- **A pod where only one non-failed seat remains**: the leave-one-out pod mean has no "other seats" to average → that seat's reward is undefined and it is excluded.
- **Critic-only (off-policy) corpora supplied**: must contribute to the value regression and coverage but never to the policy gradient.
- **Architecture / embedding-width mismatch**: a reference checkpoint whose architecture disagrees with the embedding cache must fail fast with a clear message, not a low-level shape error.
- **Empty learner whitelist**: no learner seats → reject at startup.
- **Trailing partial line in a corpus** (a generator crash mid-write) → tolerated by the reader, as in the existing corpus format.

## Requirements *(mandatory)*

### Functional Requirements

**Training command & inputs**

- **FR-001**: The system MUST provide a new training command that performs an on-policy actor-critic update from a self-play corpus and its generating reference checkpoint, and writes a new generation's checkpoint.
- **FR-002**: The command MUST require a reference checkpoint that simultaneously serves as (a) the warm-start for both the policy and the critic, (b) the KL anchor, and (c) the policy that must have generated the on-policy corpus.
- **FR-003**: The command MUST require an on-policy corpus path that is the sole source of the policy-gradient term.
- **FR-004**: The command MUST accept zero or more additional (off-policy) corpora used for critic regression / coverage only, never for the policy gradient.
- **FR-005**: The command MUST require a non-empty whitelist of learner agent labels identifying which seats are the policy being trained; seats outside the whitelist (Forge, random bots) supply critic coverage only.
- **FR-006**: The command MUST reuse the existing self-play data-generation path unchanged to produce rollouts; it MUST NOT introduce a new data-generation mechanism.

**On-policy RL update contract**

- **FR-007**: For each learner seat and pick, the system MUST reconstruct the typed-token state exactly as the gen-1 loader builds it for that `(seat, pack, pick)`.
- **FR-008**: The action for each pick MUST be the card recorded as taken at that pick.
- **FR-009**: The system MUST recompute, from the reference checkpoint at the corpus's rollout pick-mode/temperature, the behaviour distribution for the recorded picks. It MUST surface a warning summarizing anomalous picks (e.g. near-zero probability of the recorded action — a possible wrong-checkpoint/wrong-temperature pairing) but MUST proceed to train regardless (no hard reject). On-policy correctness is the operator's responsibility (pairing the matching checkpoint, corpus, and temperature). The recomputed behaviour log-prob is used only for this warning, not as a gradient input.
- **FR-010**: The reward for a learner seat MUST be its pod-relative leave-one-out deck-quality score: the seat's score minus the mean score of the other non-failed seats in its pod (the same terminal reward the gen-1 critic regressed). The draft reward is terminal.
- **FR-011**: The system MUST compute a GAE(λ) advantage and a discounted-to-terminal return per learner pick from the critic value and the terminal reward, with λ operator-configurable.
- **FR-012**: The training loss MUST be the sum of: an advantage-weighted policy-gradient term (using the trained policy's log-prob of the taken action, over the on-policy corpus only), a critic regression term toward the return, an entropy bonus, and a KL-divergence anchor to the reference policy.
- **FR-013**: The policy-gradient term MUST draw only from the on-policy corpus; the critic regression term MAY additionally draw from the off-policy critic-only corpora.
- **FR-014**: The KL-anchor and entropy coefficients MUST follow a schedule (heavier early, relaxed later); the critic-regression weight and GAE-λ MUST be operator-configurable.

**Failure handling & integrity**

- **FR-015**: Learner seats with a failed build MUST be excluded from the reward, the pod mean, and the gradient, without aborting the run.
- **FR-016**: On-policy pairing is an **operator responsibility**: because no generating-checkpoint provenance is stored in the corpus (operator convention only — see FR-021), the system MUST NOT attempt to hard-reject a corpus on a provenance mismatch. Its only safeguard is the FR-009 anomaly warning.
- **FR-017**: At startup the system MUST validate that the reference checkpoint exists and its architecture matches the embedding-cache width, that the learner whitelist is non-empty, and that a rollout pick-mode/temperature is available (read from the corpus or supplied explicitly); failures exit nonzero with a clear message.

**Optimisation & checkpoints**

- **FR-018**: Optimisation MUST reuse the gen-1 trainer's conventions and knobs (adaptive optimiser with per-group gradient-norm clipping, linear-warmup-then-constant learning rate, draft-disjoint held-out validation split, best-checkpoint selection, and early stopping) with the same semantics and defaults. Because the corpus is fixed and the candidate's true strength is judged externally by the yardstick (§ FR-022), in-run best-checkpoint selection and early stopping MUST use the **held-out RL objective** — the same policy-gradient + value + entropy + KL sum used for training, evaluated on the validation split — as a guard, not a strength measure.
- **FR-019**: The new checkpoint MUST be written in the gen-1 agent checkpoint format (trunk + policy + critic + recency/context tables, config, epoch, best held-out RL objective) plus RL metadata: the generation index, the reference-checkpoint identity, and the RL hyper-parameters, so the checkpoint is self-describing for the next cycle. Encoder weights are not trained or stored.
- **FR-020**: Checkpoints MUST be written to the existing agent checkpoint location, producing both a timestamped file and a "latest" pointer, consistent with gen-1.

**Records & provenance**

- **FR-021**: Rollout corpora MUST remain in the **unchanged** self-play corpus schema — no provenance field is added. On-policy pairing is handled by **operator convention** (e.g. a per-cycle corpus filename such as `drafts-genK.jsonl` plus the existing per-run identifier); the trainer does not read or require a stored generating-checkpoint id.

**Cross-generation evaluation & promotion** *(an operator procedure over existing commands — introduces no new code)*

- **FR-022**: Comparing generations MUST be done as a single self-play data-generation pass, run in greedy (deterministic, no added sampling temperature) mode using the existing data-generation command, with one fixed agent mix holding every generation being compared (the candidate, the prior champion, Forge, and the random-bot minority), each randomly co-seated into shared pods over a large pod count.
- **FR-023**: The fixed-mix single shared run with randomized co-seating is the load-bearing property: every compared agent MUST face the same opponent distribution (so the opponent-strength confound cancels in the difference). Comparing each generation over its own training corpus MUST NOT be used.
- **FR-024**: The evaluation metric MUST be the per-agent mean deck-quality score on the frozen scorer's raw absolute scale, obtained by running the existing deck-composition analysis command once per agent label over the single yardstick corpus.
- **FR-025**: Promotion is a **manual operator judgment**, not a codified rule the system enforces. The procedure's job is to surface the comparison (the per-agent mean `deck_score` on a shared scale from one fixed-mix run); the operator decides whether the candidate's edge over the champion is convincing enough — typically by eyeballing it against the run-to-run noise — and which checkpoint becomes the next champion. The system does not auto-promote.
- **FR-026**: Descriptive cross-generation composition (creature count, colour balance, curve) MUST be inspectable with the same existing deck-composition analysis command (descriptive only, not a promotion gate).

**Self-play loop**

- **FR-027**: The self-play loop MUST be a manual operator runbook — the existing data-generation command, this trainer, and the FR-022 evaluation procedure run in sequence by hand — with no automated unattended daemon and **no new orchestration code**; one cycle produces one new generation. The loop is documented (e.g. in the feature's quickstart) so an operator can follow it, but introduces no code of its own: the generation and evaluation steps are existing commands run with the appropriate parameters and the training step is User Story 1's trainer.
- **FR-028**: A cycle's two data-generation passes MUST differ by pick-mode: the training-corpus pass uses sampling at the exploration temperature (seeded), and the FR-022 yardstick pass uses greedy/deterministic mode.
- **FR-029**: Every cycle MUST retain a random-bot minority for low-end critic coverage, and MUST keep old corpora available for critic coverage without ever concatenating them into the policy gradient.

### Key Entities *(include if data involved)*

- **Reference checkpoint (πₖ)**: the frozen agent (gen-1 or current champion) that warm-starts the candidate, anchors the KL penalty, and must have generated the on-policy corpus. Carries policy + critic + recency/context tables, config, and (for RL-produced ones) generation index, reference identity, and RL hyper-parameters.
- **On-policy self-play corpus**: a per-cycle file of draft records generated by πₖ piloting one or more learner seats against Forge and a random-bot minority, with exploration sampling. Each record reconstructs every seat's full pick sequence, the piloting agent per seat, and each seat's built deck and deck-quality score. The sole source of the policy gradient.
- **Critic-only (off-policy) corpus**: an earlier-generation corpus supplied for value-regression coverage; never enters the policy gradient.
- **Learner seat**: a seat whose mix label is in the learner whitelist — the generation being trained. Its picks and pod-relative reward drive the policy and critic updates.
- **Per-pick training quantity**: for each learner pick — state, action, recomputed behaviour distribution (anomaly-warning only, not a gradient input), current critic value, terminal pod-relative reward, GAE advantage, and return.
- **Candidate checkpoint (πₖ₊₁)**: the trainer's output — the next generation, evaluated against the champion before promotion.
- **Cross-generation yardstick run**: a single fixed-mix, randomly co-seated evaluation producing each agent's mean deck-quality score for the promotion decision.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: On the cross-generation yardstick, a trained gen-2 candidate achieves a higher mean deck-quality score than gen-1 by more than the measured run-to-run noise band.
- **SC-002**: On the same yardstick, the promoted generation's mean deck-quality score also exceeds Forge's (gen-0).
- **SC-003**: 100% of runs with an invalid startup configuration (missing/architecture-mismatched checkpoint, empty learner whitelist, or no available rollout temperature) fail fast before any training step, with a clear message.
- **SC-004**: For every run, the trainer reports a summary of behaviour-distribution anomalies (count/fraction of learner picks the reference checkpoint assigns implausibly low probability), so the operator can spot a wrong corpus/checkpoint/temperature pairing; training proceeds regardless.
- **SC-005**: Learner seats with failed builds are excluded from reward, pod mean, and gradient in 100% of cases, and their presence never aborts an otherwise valid run.
- **SC-006**: An operator can complete one full self-play cycle (freeze → generate → train → evaluate → promotion decision) using documented commands with no manual editing of corpus or checkpoint files, ending with an unambiguously identified champion (new or retained).
- **SC-007**: Across a promotion, the candidate's deck composition does not collapse to a degenerate distribution (the KL anchor keeps composition statistics within an operator-inspectable, plausible range relative to the reference), as confirmed by the descriptive composition analysis.

## Assumptions

- **Reward unit**: the established pod-relative leave-one-out **deck-quality score** (the frozen scorer scalar the gen-1 critic regressed) is the reward and the promotion metric. The Bradley-Terry temperature fit and the "beat the whole pod" product objective are explicitly out of scope; the reward stays the gen-1 pod-relative **mean** form.
- **On-policy estimator**: gen-2 uses REINFORCE with a GAE baseline. PPO (clipped-ratio, multi-epoch corpus reuse) and vine/pack-2-forking advantage estimation are deferred to later generations.
- **Provenance mechanism**: pairing a corpus to its generating checkpoint is handled by **operator convention** (corpus filename + per-run id) — no provenance field is added to the corpus and the trainer performs no hard provenance check. Its only safeguard is the FR-009 behaviour-anomaly warning. (Clarified 2026-06-13.)
- **Unchanged components**: the model architecture, typed-token state representation, recency scheme, embedding cache, and corpus schema (no change at all) are reused from gen-1 / live-play. The live-play rollout command is reused as-is.
- **Phase A only**: the encoder is frozen; no joint encoder fine-tuning and no picker/scorer changes.
- **Only new code is the trainer and its multi-corpus input**: the genuinely new artifacts in this feature are User Story 1's RL trainer and the trainer's multi-corpus (critic-only) input. No corpus schema change and no provenance field are added (pairing is by operator convention). The cross-generation yardstick (US2) and the self-play loop (US3) introduce **no new code** — they are operator runbooks/conventions over **existing** commands (the data generator in greedy or sample mode, and the per-agent deck-composition analysis) plus the US1 trainer, run by hand. They are kept in the spec so they flow into the quickstart documentation, not because they require a build.
- **Yardstick is greedy, single shared run**: the evaluation pass runs the data generator in greedy/deterministic mode (measuring deployed strength, no sampling noise) as one fixed-mix run with randomized co-seating; per-agent mean raw `deck_score` is read from the existing analysis command. Greedy mode for the yardstick is an inferred evaluation convention (the design rationale mandates the fixed-mix randomized co-seating explicitly but does not literally pin the pick-mode).
- **Critic predicts Vπ**: because the critic regresses on the policy's own rollouts, its values estimate the on-policy value function for advantage computation.

## Dependencies

- The offline gen-1 draft agent (two-headed policy + critic) and its checkpoint format.
- The live-play self-play data generation that lets a trained agent pilot live seats and emit the corpus (including the typed-token state reconstruction and the online state tracker used to rebuild any `(seat, pack, pick)` state).
- The frozen deck scorer that produces each seat's deck-quality score (the reward source).
- The existing deck-composition analysis tooling (descriptive cross-generation inspection).

## Out of Scope

- Automated, unattended multi-generation training (the loop is operator-driven).
- Live in-draft use of the critic to pick (the policy alone picks during rollouts; advantages are computed post-hoc from the corpus).
- The Bradley-Terry temperature fit and the product-of-`P(beat i)` objective.
- PPO and vine/pack-2-forking advantage estimation.
- Joint encoder fine-tuning, picker/scorer changes, and any corpus schema change (including any stored generating-checkpoint provenance — pairing is by operator convention).
- Shipping the agent into the Forge client (a separate deployment concern).
